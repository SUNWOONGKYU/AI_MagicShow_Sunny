SUNNY AI MAGIC 50 · #25

미니 풀스택 5시간 이내 제작

DB → API → UI/UX → E2E → Vercel 배포까지 5시간 안에 끝내기
G4 · 결과물 및 품질관리 A타입

한 줄 정의

DB 스키마 → API 라우트 → UI/UX → E2E 테스트 → Vercel 배포까지 5시간 안에 끝내는 1인 풀스택 단위 작업. 이건 단순 속도전이 아니라 본인이 #10에서 정의한 "포크레인·트랙터 운전" 능력 — AI를 운전하는 자가 풀스택 종합 능력자임을 입증하는 시간 척도다. 4시간 미만이면 신호기·UI 정합성·검증이 깨지고, 6시간을 넘기면 운전이 아닌 노가다가 된다. 5시간 ±10%가 본인 4,000시간 누적에서 도출된 풀스택 단위 시간 벤치마크다.

왜 이 노하우가 중요한가

"AI 시대에 개발자는 무엇을 잘해야 하는가" 라는 질문에 본인은 단 하나로 답한다 — 풀스택을 5시간 안에 묶는 능력. 이게 #10 트랙터 운전 비유의 정량적 증명이다. 트랙터 운전자는 트랙터의 동력을 알고, 흙의 점성을 알고, 작물의 깊이를 안다. 마찬가지로 1인 풀스택 운전자는 DB의 인덱스를 알고, API의 응답 형식을 알고, UI의 접근성 기준을 알고, E2E의 클릭 시나리오를 안다. 이 넷을 머릿속 한 좌표계에 동시에 띄울 수 있는 사람만이 5시간 안에 묶는다.

기존 회사 조직에선 이 5시간이 5주가 됐다. 백엔드 1주, 프론트 1주, QA 1주, 배포 1주, 회의·재작업 1주. 본인이 누적 운용에서 검증한 사실은 — "5주가 5시간이 되는 순간, 사업 모델 자체가 바뀐다." 아이디어 → 동작하는 MVP까지 5시간이면, 하루 8시간 작업으로 1.5개의 MVP를 매일 찍어낼 수 있다. 본인이 운영 중인 다수 동시 프로젝트 중 절반 이상이 이 5시간 단위로 잉태됐다.

5시간이 가능한 이유는 도구의 혁신이 아니라 스킬의 묶음이다. 본인은 헌법(#32)에서 자동 발동되는 4개 스킬을 묶어 놓았다.

스킬 담당 영역 예상 시간
db-schema-기본 Supabase 스키마·마이그레이션·RLS 30~60분
api-builder-기본 RESTful 라우트·검증·에러 핸들링 60~90분
ui-ux-builder-기본 67 styles·96 palettes·접근성 90~120분
e2e-test-기본 Playwright 5브라우저 회귀 30~60분

이 네 스킬 + #18(Vercel 신속 배포) + #49(스크린샷 자율 검증) + #25(챗봇 통합)까지 일곱 무기가 한 손에 들어오면, 5시간은 더 이상 도전이 아니라 표준 단위가 된다.

핵심 개념

5시간의 분배 — 1:2:1.5:0.5 비율

본인 누적 운용에서 도출된 시간 분배.

0:00 ─────────────────────────────────── 5:00
│ DB    │       API        │   UI/UX    │ E2E │
│ 0.5h  │       1.5h        │   2.0h    │ 1.0h│
└───────┴──────────────────┴─────────────┴─────┘

DB가 30분 안에 안 끝나면 그날 5시간은 망한다. ERD가 막히면 API·UI도 막힌다. 반대로 DB가 30분에 끝나면 나머지 4.5시간은 폭발적 가속이 시작된다 — API와 UI가 같은 데이터 모델 위에서 자동 생성되기 때문이다. DB 30분 룰이 미니 풀스택의 첫 게이트다.

4 스킬 결합 패턴

결합 1 — db-schema-기본 (30~60분)

db-schema-기본은 Supabase(PostgreSQL) 전문 스킬이다. AI-only 원칙이 강제된다.

허용: supabase db push, supabase/migrations/*.sql, supabase start 금지: Supabase Dashboard에서 수동 테이블 생성, SQL Editor 직접 실행, GUI로 RLS 정책 생성

이 금지 조항이 핵심이다. 30개 동시 프로젝트에서 GUI 클릭으로 만든 테이블은 추적 불가능하다. 마이그레이션 파일로만 관리해야 다른 환경에 재현된다. 본인은 빈 폴더에서 시작해 30분 안에 5~7개 테이블 + RLS 정책 + 인덱스를 마이그레이션 파일로 떨어뜨린다.

결합 2 — api-builder-기본 (60~90분)

api-builder-기본은 RESTful 표준 7동사를 자동 적용한다.

GET    /api/items        # 목록
GET    /api/items/[id]   # 단일
POST   /api/items        # 생성
PUT    /api/items/[id]   # 전체 수정
PATCH  /api/items/[id]   # 부분 수정
DELETE /api/items/[id]   # 삭제

응답 형식도 표준화돼 있다.

// 성공
{ "data": { ... }, "pagination": { ... } }

// 에러
{ "error": { "code": "VALIDATION_ERROR", "message": "...", "details": { ... } } }

이 표준이 박혀 있으니, 5개 테이블 × 5개 라우트 = 25개 엔드포인트를 90분 안에 짠다. 그것도 Zod 검증 + 에러 핸들링 + 페이지네이션까지 갖춰서. 표준이 없으면 라우트마다 5분씩 고민하다가 90분이 5시간이 된다.

결합 3 — ui-ux-builder-기본 (90~120분)

UI/UX 스킬은 67 styles · 96 palettes · 57 font pairings · 25 charts · 13 stacks를 색인하고 있다. 핵심은 CRITICAL 우선순위 8단계다.

우선순위 카테고리 영향도
1 Accessibility CRITICAL
2 Touch & Interaction CRITICAL
3 Performance HIGH
4 Layout & Responsive HIGH
5 Typography & Color MEDIUM
6 Animation MEDIUM
7 Style Selection MEDIUM
8 Charts & Data LOW

CRITICAL 1·2가 통과 못 하면 #29 스크린샷 검증에서 자동 차단된다. 색대비 4.5:1 미만, 터치 타겟 44×44px 미만, cursor-pointer 누락, <div>로 만든 클릭 영역 — 이게 본인이 "curl 200 ≠ 동작함" 사건에서 직접 겪은 원인이었다(#32 UI 검증 철칙 참조). UI 스킬의 8단계 우선순위는 그 사건을 헌법에 박은 결과물이다.

결합 4 — e2e-test-기본 (30~60분)

e2e-test-기본은 Playwright 기반이며, 5브라우저 매트릭스가 기본이다.

// playwright.config.ts
projects: [
  { name: 'chromium',     use: devices['Desktop Chrome']  },
  { name: 'firefox',      use: devices['Desktop Firefox'] },
  { name: 'webkit',       use: devices['Desktop Safari']  },
  { name: 'mobile-chrome',use: devices['Pixel 5']         },
  { name: 'mobile-safari',use: devices['iPhone 12']       },
]

5브라우저 × 회귀 시나리오가 30~60분 안에 돈다. curl 금지 — 헌법 가드 3 직접 적용. "브라우저 수동 테스트, GUI 도구 수동 사용, 사용자에게 수동 시나리오 요청" 모두 금지. 자기 검증 금지(Task Agent ≠ Verification Agent). E2E 결과 12/12 통과해야 비로소 Verified.

#18 · #25 · #49과의 결합 — 7무기 합산

항목 역할 결합 효과
#18 HTML+Vercel 신속 배포 vercel-private-url-배포로 URL 아는 사람만 접근 5시간 안 마지막 30분 압축
#25 지능형 챗봇 도우미형 챗봇 1개 자동 임베드 UI 본문에 즉시 합류
#49 스크린샷 자율 검증 E2E 통과 후 시각적 회귀 1회 더 UI 변형 회귀 0건 보증

이 셋이 4 스킬에 더해지면 5시간 단위가 단발 MVP가 아니라 재현 가능한 발사대가 된다. 본인이 30개 프로젝트를 동시 운용하면서 같은 7무기 패턴을 30번 재실행한다. 매번 5시간 ±10%.

5시간 KPI — 사용자 여정 + 데이터 레이어 양면

5시간 안에 다음 KPI가 동시에 충족돼야 한다("데이터 레이어 KPI만으론 부족" 원칙).

사용자 여정 KPI - 랜딩 페이지 주요 버튼 4개 이상 클릭 시 각각 올바른 라우트 - 폼 제출 → 성공/에러 메시지 적절한 위치 노출 - 모바일 뷰 가로 스크롤 0건 - 키보드 Tab 순서가 시각 순서와 일치

데이터 레이어 KPI - DB 마이그레이션 멱등성 보장(2회 실행도 안전) - API 응답 시간 P95 < 500ms (Vercel Edge 기준) - E2E 12/12 통과 (Chrome·Firefox·Safari·iPhone·Pixel) - Lighthouse Performance 80 → 95 향상 (목표값 ≥ 90)

양면 KPI가 동시 충족돼야 5시간 단위가 "운전(#10)" 자격을 얻는다. 한쪽만 충족되면 그건 트랙터가 아니라 자전거다.

실전 사용법

1단계 — 30분 ERD 스프린트 (DB)

빈 폴더에서 시작.

📁 supabase/migrations/
📄 20260506_001_create_items.sql
📄 20260506_002_rls_policies.sql
📄 20260506_003_indexes.sql

db-schema-기본 스킬을 호출 — "이 프로젝트는 X 도메인. ERD를 5~7테이블로 그리고 마이그레이션 파일 떨어뜨려". 30분 안에 끝나지 않으면 도메인이 너무 크다는 신호 — 즉시 분할.

2단계 — 90분 API 일괄 생성 (Backend)

api-builder-기본 스킬 호출 — "DB 스키마 5개 테이블 기반으로 RESTful 7동사 라우트 25개 생성. Zod 검증 포함. 페이지네이션 표준 적용." 라우트 25개를 90분 안에 일괄 작성. 이 단계의 핵심은 표준 응답 형식 강제.

3단계 — 120분 UI/UX 빌드 (Frontend)

ui-ux-builder-기본 스킬 호출 — "이 도메인에 어울리는 스타일 1개 추천(67 styles 중), palette 1개(96 중), font pair 1개(57 중). CRITICAL 1·2(접근성·터치)는 무조건 통과. 페이지 5개 빌드." shadcn/ui MCP가 컴포넌트 검색을 자동화하므로 120분 안에 5페이지가 떨어진다.

4단계 — 60분 E2E + 시각 회귀 (Verification)

e2e-test-기본 + #49 스크린샷 자율 검증 동시 호출.

npx playwright test
# 5브라우저 × 회귀 시나리오 자동 실행

12/12 통과 + 스크린샷 베이스라인 일치. 미통과 시 5times-debug-loop-코어3로 자동 재진입(최대 5회). 여기서 자기 검증 금지 — 이전 단계를 만든 에이전트와 다른 에이전트가 검증한다(헌법 가드 3, 청룡 §7.1).

5단계 — 30분 Vercel 배포 (#18과 결합)

vercel-private-url-배포 스킬 호출.

vercel --prod
# 한글 폴더명 자동 처리, 비밀번호 보호 옵션 적용

URL 발급 즉시 G드라이브 .txt로 떨어뜨려 폰에서 확인(헌법 가드 6). 배포 후 첫 액션은 curl이 아니라 브라우저 클릭 테스트 — 헌법 가드 3 재확인.

6단계 — 결과 종합 보고

5시간 타이머 마감 5분 전, MBO 결과보고서 자동 생성. 양면 KPI 표 + Lighthouse 점수 + E2E 결과 + 배포 URL. 통과 못 한 항목은 다음 5시간 사이클로 이월. 이월은 실패가 아니다 — 5시간 단위가 깨지는 게 실패다.

7단계 — SAL Grid 기록 (필수)

5시간 사이클이 끝나면 반드시 SAL Grid에 기록. grid_records/{TaskID}.json에 22속성 갱신. node scripts/build-progress.js 실행. 헌법의 "SAL Grid 반영 의무 — 예외 없음" 가드(#32)가 강제. 기록 없으면 미완료 간주.

본인 운용 패턴

10에서 "포크레인·트랙터 운전" 능력을 비유로 정의했다면, 이 #6는 그 비유의 정량적 증명서다. 5시간 안에 풀스택 1개를 묶지 못하는 사람은 트랙터를 운전한다고 주장할 수 없다. 반대로 5시간 안에 묶는 사람은, 풀스택 종합 능력 + AI 운용 능력 + 헌법 운용 능력을 동시에 입증한 것이다. 본인이 채용·외주·협업에서 단 하나의 시간 척도로 이 5시간을 본다.

추가 확장 — 본인은 5시간 × 6사이클 = 30시간 = 1주일 1프로젝트 패턴으로도 운용한다. 첫 5시간은 MVP, 두 번째는 결제·인증, 세 번째는 챗봇 통합(#25), 네 번째는 데이터 분석 대시보드, 다섯 번째는 SEO·접근성 풀튜닝, 여섯 번째는 운영자 대시보드. 30시간 끝에 상용 가능한 SaaS 1개가 떨어진다. 이게 30개 동시 운용의 시간 단위 증명이다 — 5시간이라는 원자가 있어야 30시간·150시간·900시간이 의미를 갖는다.
