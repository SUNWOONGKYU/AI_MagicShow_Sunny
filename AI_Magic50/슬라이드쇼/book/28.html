AI 결과물 품질 보장의 4종 도구 — 가벼운 평가부터 시작해 무거운 쪽으로 escalate

📺 영상 — AI 결과물 품질을 어떻게 보장할 것인가 — Sunny's QC 4종 스킬 소개 (와이저_WiZER, 2026-04-29, 10분)

한 줄 정의

본인이 직접 정의해 4,000시간 누적 운용으로 검증한 4종 품질관리 스킬(QC) — review-evaluate-코어1(가벼움) · pro-persona-debate-코어6(중간) · 주작-sal-da(무거움) 평가 3종 + 5times-debug-loop-코어3(디버깅 1종) — 을 산출물 무게에 맞춰 가장 가벼운 것에서 시작해 부족하면 무거운 쪽으로 escalate 하는 사다리식 검증 운용 체계. "AI는 자신감 있게 틀린 답을 낸다" 라는 출발점 위에 세워졌고, 자기 칭찬이 아니라 자기 비판하게 시키는 운용 이며, "Task Agent ≠ Verification Agent" 원칙을 4종 모두에 박아넣은 본인 시그니처 검증 패키지. 영상 발표문 v7(대본 7섹션 10분 50씬)이 4종의 정식 공개 자료다.

왜 이 노하우가 중요한가

출발점 — "AI는 자신감 있게 틀린 답을 낸다"

AI 산출물의 가장 위험한 함정은 "잘 돌아 보이는 거짓말" 이다. Claude로 사업계획서를 쓰든, 코드를 짜든, 진단 보고서를 만들든, 결과물을 검증하지 않고 그대로 쓰는 건 위험하다. 한 번에 그럴듯한 출력이 실제로는 사실과 다르거나, 한쪽으로 편향되거나, 빌드조차 안 될 수 있다. AI가 자신감 있게 틀린 답을 내는 경우가 적지 않다 — 영상 발표문 도입부의 첫 문장이 곧 본 챕터의 전제다.

SKILL_ATLAS S5 사건이 본인 4,000시간 누적의 가장 비싼 교훈으로 박혀 있다 — 배포 후 curl 200 으로 확인하고 Verified 처리했는데, 사용자가 실제 브라우저에서 보니 "시작하기"·"더 알아보기" 버튼은 href가 없어 무반응, 4개 은하 원은 <div> 라 클릭 불가, "View All"은 존재하지 않는 /rankings 로 404, 랭킹 카드는 /skills/${uuid} 경로·파라미터가 전부 틀린 상태. HTTP 200 ≠ 동작함. 글로벌 CLAUDE.md "UI 검증 철칙" 5개 조항이 이 사건에서 직접 도출됐다.

단일 검증 도구의 한계 → 무게 계층 사다리

이 사고는 단일 검증 도구의 한계를 보여준다. "문법은 맞는가" 만 보면 "의도대로 도는가" 를 놓치고, "의도대로 도는가" 만 보면 "이해관계자 다관점에서 타당한가" 를 놓치고, "다관점에서 타당한가" 만 보면 "실제 산출물이 사양·규정과 일치하는가" 를 놓친다. 단일 도구로 모든 차원을 잡으려 하면 어느 차원이든 얕아진다. 매 차원마다 한 번씩 호되게 당하고 그 사고를 스킬로 박제한 결과가 4종 패키지다.

본 운용의 핵심 발상 세 가지.

  1. 무게 계층 사다리 — 검증을 단일 도구가 아니라 무게별 사다리로 운용한다. "가장 가벼운 리뷰 이밸류에이트에서 시작합니다. 단일 파일이나 문서 광택이면 여기서 끝냅니다. 굳이 무거운 도구를 부를 이유가 없습니다. 부족하다 싶으면 프로 퍼소나 디베이트로 에스컬레이트합니다. 그래도 부족하면 살다로 에스컬레이트합니다." (영상 §6 통합 워크플로)
  2. 검증자·작업자 물리 분리 — Task Agent ≠ Verification Agent. 자기가 한 일을 자기가 검증하면 안 된다. 4종 모두에 "수정한 사람과 평가하는 사람을 분리하여 자기 평가 편향을 방지한다"(review-evaluate)·"Judge 평가 Subagent 분리(Self-Grading 폐쇄 루프 차단)"(pro-persona-debate v1.1)·"런타임 검증 없이는 진단 완료 선언 불가"(주작-sal-da v4.0) 가 명문 규정으로 박혀 있다.
  3. 비대칭 권한 + 자동 체이닝 금지 — 평가 3종은 PO 명시 승인 없이 호출 불가, 5times-debug만 SA 자동 호출 가능. 무거운 스킬을 자동 체이닝하면 운영 비용이 폭발하므로 PO 게이트가 비용을 통제한다.

핵심 개념

review-evaluate-코어1 가벼움 검토→수정→평가 루프 (최대 10회) 100/100 도달
pro-persona-debate-코어6 중간 3 전문가 + DA 5단계 토론 + Fix (최대 5 Cycle) rubric 100/100 + 외부 게이트

5times-debug-loop-코어3 단발 (계층 외부) 분석→수정→검증 5회 + Playwright 자동 버그 해결 / 5회 소진

3종 평가 스킬은 위계 사다리 다. 단순 코드·문서면 1번, 다관점 판단이 필요한 사업·특허·UX는 2번, 규정 준수·법률·구조화 산출물은 3번. 디버깅 1종은 사다리 외부 — 명확한 단일 버그 박살용으로 어느 평가 스킬이든 위임할 수 있다 (review-evaluate Phase 2 "명시적 증상 → /5times-debug-loop 위임").

자기 비판 운용 (가장 중요한 한 가지)

종합정리 #28의 한 줄 — "스스로 비판시키기(약점·빠진 것·반박점 찾아내기)가 4종 검증에 반영되도록" — 이 운용의 본인 시그니처다. 디폴트로 두면 AI는 "잘 돌아갑니다" 라는 칭찬을 흘리게 되어 있다. 4종 모두에 비판 메커니즘이 강제 내장돼 있다.

  • review-evaluate: Cross Validator가 "리뷰어가 놓친 문제점" 섹션을 의무 작성.
  • pro-persona-debate: DA(Devil's Advocate) 가 4번째 페르소나로 강제 투입. v1.1에서 "BPI 공식에 DA_penalty 항 추가 — DA 무력화 결함 보정".
  • 주작-sal-da: Pending Critical 1건이라도 있으면 진단 완료 선언 불가. "Pending Critical ≠ Acceptable"(v4.0).
  • 5times-debug-loop: Playwright 스크린샷이 사람 눈을 대신해 "실제로 안 되는 부분" 을 자기 검증.

review-evaluate-코어1 — 100점 ABSOLUTE RULE + 파일 타입별 루브릭

5기준 루브릭(문법·실행 / 보안 / 코드품질 / 테스트 / 완성도) + 사양 충족률 25점 = 100점. Round < 10 AND 점수 < 100 → 다음 라운드 강제 진입. 95점·97점·99점이라도 임의 종료 금지. SKILL.md 명문: "2026-05-03 김부겸 보고서 사건 — Round 2에서 97점 받고 '배포 가능 수준' 권고에 동조하여 임의 종료. 사용자가 '100점이 안 났는데 중단했냐'고 지적해야만 Round 3 재개되어 100점 달성. 이 경험을 ABSOLUTE RULE로 격상."

영상 §2의 핵심 세 가지가 곧 운용 원칙이다.

  1. 파일 타입별 전문 서브에이전트 — 코드/문서로 나뉘고, 리포트·사업계획서·법률 문서도 모두 "문서의 한 종류". 코드는 가독성·테스트·보안·성능, 문서는 구조·일관성·사실성·완결성. 같은 잣대를 모든 파일에 들이대지 않는다.
  2. Cross Validator — 같은 LLM이 자기 출력을 채점하면 점수가 후하게 나오는 "자기 강화 편향" 을 차단하기 위해 평가자와 별도의 검증자를 둔다. 검증자는 점수에 동의 또는 반려.
  3. 자동 종료 조건 — 100점 도달 또는 10라운드 소진. 라운드별 점수 변화 그래프로 어디서 진척이 막혔는지 추적. 무한 루프·비용 폭주 차단 안전장치.

또 하나의 보완 — Phase 1.5 사양-구현 대조. "코드가 잘 돌아가는가" 와 "코드가 사양대로 돌아가는가" 를 분리해 사양 충족률 25점을 별도 채점. 사양 동떨어지면 75점 상한. 2026-03-26 "100점을 줬는데 인스트럭션-스크립트 간 근본 격차를 못 잡았다" 사고의 직접 교훈.

pro-persona-debate-코어6 — 6요소 페르소나 + DA 중립 + 두 지표 분리

같은 도메인 동료 3명 + DA(Devil's Advocate) 1명 = 4 페르소나. 5단계 토론(S1 독립 → S2 교차 → S3 사실 확인 → S4 반론 → S5 수렴). rubric 100점 도달까지 최대 5 Cycle. 절대 규칙: "4 페르소나 발언은 반드시 4개의 Subagent(Agent tool) 호출로 생성한다. '비용 합리화', '시뮬레이션 모드', '소대장 모드'라는 명목으로 SA가 직접 작문하면 해당 Cycle은 무효." — 가장 흔한 우회를 차단한 조항.

영상 §3에서 강조된 세 가지 결정적 디테일이 본 스킬의 본질을 정의한다.

  1. 페르소나는 이름표가 아니라 BuzzLab 6요소 시트 — 정체성·신념·규칙·프레임워크·말투·워크플로우. 이 6요소가 일관되게 묻혀 있어야 발언이 그 사람답게 나온다. "단순 이름표만 붙이면 결국 같은 모델이 같은 톤으로 대답합니다. 6요소가 살아 있어야 진짜 다관점 토론이 됩니다."
  2. DA = 스탠스 0 중립 챌린저 — -1(반대)이 아니라 0(중립)이 진짜 재고를 유발한다는 의사결정론 연구 기반. 한쪽 입장을 연기하지 않고 모든 팀의 논증 약점을 중립적으로 검증.
  3. 두 지표 분리 — rubric_score(0~100, 산출물 품질, Fix 루프 종료 조건)와 BPI(-100~+100, 페르소나 스탠스 가중평균, 토론 방향성). "점수가 높아도 BPI가 한쪽으로 쏠리면 편향 신호. BPI가 균형 잡혀 있는데 점수가 낮으면 양쪽 다 약하다는 뜻."

여기에 할루시네이션 가중치 도 들어간다 — FACT 1.0 / DOUBT 0.80 / FALSE 0.50. 거짓 발언은 절반 페널티, 의심 발언은 0.8배 감산, 사실 발언만 그대로 반영.

종료 조건은 rubric 100점 + 외부 게이트 통과. v1.2에 외부 게이트 신설 — "rubric_score 100 ≠ 출원/배포/실행 보증." 도메인별 외부 표준(KIPO·빌드·접근성·재무 일관성) 검증 강제. v1.3에는 "의미 일관성 게이트(Semantic Coherence Gate)" — DID 특허 v2.0 사례에서 "명칭='데이터 처리·정보 산출·의사결정 지원', 요약서='데이터 통합 진단(Diagnosis)' 모순. rubric 100/100인데도 미검출" 사고를 보완.

주작-sal-da — P0 런타임 우선 + SAL Grid 3D + 두 트랙 동시 운영

본인 SAL Grid(#2)의 역방향 적용. 기존 산출물을 S0에서 분해해 SAL ID를 부여하고, S1~SN Stage 루프에서 카드별 "진단→개선안→개선→재진단" 을 완결한다. 영상 §4가 정의한 세 가지 핵심 차별점.

  1. P0 런타임 베이스라인 — 빌드·서빙·스모크 테스트·DB 스키마 검증·환경변수. "실제로 작동하는지를 확인하지 않으면 진단 자체가 시작되지 않는다. 정적 분석만으로 합격을 줄 수 없다는 철학." 런타임 검증 패스 없이는 진단 완료 선언 불가. 실패 1건이라도 있으면 시스템 등급 상한 3/10, 리포트 품질 상한 60/100 강제 캡.
  2. SAL Grid 3D 좌표계 — Stage(의존성 레이어), Area(보안·성능·접근성·DB·API·법적유효성·절차완전성 등 19개 도메인), Level(그리드 깊이). 구조화된 산출물을 그리드 단위로 분해, 각 그리드 안에서 진단~재진단 자가 수렴. DB 그리드가 끝나야 그 위 API 그리드가 진단되는 의존성 순서.
  3. 두 트랙 동시 운영 + 두 점수 분리 — Diagnosis(품질)·Audit(규정 준수) 두 트랙. 시스템 등급과 리포트 품질이 분리 보고된다. "리포트가 100점이어도 시스템이 D면 D로 보고된다. 잘 쓴 리포트가 망가진 시스템을 가리는 일을 막는 안전장치."

진단 대상은 소프트웨어·법률 문서·절차 문서 세 분류. 각각 전용 트랙. 법률 트랙은 조항 의존성·무효 사유, 절차 트랙은 단계 누락·책임자 부재. 진단 종료 시 4파트 리포트(Executive Summary / Technical Detail / Action Plan / Verification Log) 자동 생성, 마지막에 /review-evaluate 자동 호출로 리포트 자체 품질 검증. P0 Fail 그리드에 명확한 증상 있으면 /5times-debug-loop 위임 권장. 20속성 6그룹(식별→진단기준→진단결과→개선안→개선실행→재진단)이 SAL Grid의 22속성과 짝을 이룬다 — 동일 좌표계, 다른 방향. 개발(#2) ↔ 감사(주작) 가 한 쌍.

5times-debug-loop — 객관 도구만 신뢰하는 단발성 디버깅

"분석 → 수정 → 검증" 5회 반복. 명확한 증상이 있는 버그 — 빌드 실패, API 500, 렌더 깨짐, 테스트 실패 — 만 처리. 호출 패턴은 단순: "문제 설명 / 수정 대상 파일 / 검증 방법" 세 가지. 검증 방법은 빌드 명령어·테스트 명령어·스크린샷 URL 등 객관적으로 확인 가능한 것이면 충분.

시각 결함은 Playwright 스크린샷 자동 촬영(1440×900 + 모바일 390×844) → Read tool로 PNG 분석. 코드·빌드는 npm run build / npx tsc --noEmit / npm test 자동 실행. 의견이나 점수가 아니라 객관 도구의 통과 여부로만 판정. 통과하면 종료, 실패하면 다음 라운드에서 새 가설로 재시도. 5회 안에 못 풀면 강제 종료 + 사용자에게 에스컬레이션(자동 해결 한계 인정 + 의사결정 권한을 사용자에게 이양). 무한히 같은 문제에 매달리는 사고 차단.

사람의 눈을 대신해 AI가 자기 결과물을 본다 — 이게 #49 "스스로 스크린샷 찍어서 문제점 찾아 스스로 수정하기" 의 실체다. "review-evaluate가 '점수 매기는 도구', 5times-debug가 '박살내는 도구'."

비대칭 권한 — 비용을 좌우하는 한 줄

영상 §5의 마지막 단락이 본 패키지 운영비를 결정한다.

평가 3종 (review-evaluate / pro-persona-debate / 주작-sal-da)
  → PO 명시 승인 없이는 호출 불가 (비용 무거움)

5times-debug-loop
  → SA(Subagent) 자동 호출 가능 (단발성·가벼움)

"이 비대칭 권한이 운영 비용을 좌우합니다. 무거운 스킬을 자동 체이닝하면 비용이 폭발하지만, 가벼운 디버깅 도구는 평가 도중 명확한 버그가 보이면 즉시 위임됩니다." 4종 운용에서 가장 자주 빠지는 함정 — "평가 끝났으니 더 무거운 평가도 같이 돌리자" — 이 비대칭이 차단한다.

두 질문, 두 축 — 평가 vs 디버깅 / 가벼움 vs 무거움

질문 1: "얼마나 잘 됐나?"   →   평가 3종 (review-evaluate / pro-persona-debate / 주작-sal-da)
질문 2: "왜 안 돼?"          →   5times-debug-loop

평가 3종은 무게 계층이다.

가벼움 ──── review-evaluate ──── pro-persona-debate ──── 주작-sal-da ──── 무거움
            (루브릭)              (다관점 토론)            (실측·다차원)

5times-debug는 계층 외부의 단발성 도구 — 어느 단계에서든 버그 보이면 즉시 호출 가능.

4종을 가로지르는 헌법 5조항

본인 글로벌 CLAUDE.md "UI 검증 철칙" 이 4종 모두를 관통한다. ① curl 200 → Verified 금지 ② 배포 후 첫 액션은 직접 클릭 ③ KPI에 사용자 여정 지표 포함 ④ href 없는 버튼·<div> 클릭은 버그 ⑤ 자기 검증 금지. 4종 매핑 — review-evaluate Cross Validator(⑤), pro-persona-debate Judge Subagent 분리(⑤), 주작 P0 런타임(①②③), 5times-debug Playwright 자동(①②④). 헌법 5조항 → 스킬 4종 → 운용. 분리할 수 없는 한 덩어리.

실전 사용법

1단계 — 산출물 무게 진단으로 스킬 선택

산출물 권장 스킬
단일 함수·짧은 스크립트 review-evaluate
미니 풀스택(#6) review-evaluate + 5times-debug-loop
사업 기획서·제안서 pro-persona-debate
특허 명세서 pro-persona-debate + 외부 게이트(KIPO)
대규모 시스템 감사 주작-sal-da
한국 공공 양식(#43) pro-persona-debate + 주작-sal-da
명확한 단일 버그 5times-debug-loop

판단이 흐릿하면 가벼운 쪽부터 — review-evaluate 100점 → pro-persona-debate rubric 100점 → 필요 시 주작. 무거운 쪽부터 시작하면 시간이 폭주한다.

2단계 — review-evaluate 운용

/review-evaluate 호출 → 파일 타입 자동 분류(Code/Document/Report) → 3개 이상이면 풀 서브에이전트 투입(타입별 Reviewer + Cross Validator) → Round 1~10. 100점 미달 임의 종료 금지가 ABSOLUTE RULE. 라운드 중 빌드·테스트 실패는 즉시 /5times-debug-loop 위임.

3단계 — pro-persona-debate 운용

/pro-persona-debate <대상> → 도메인 식별 → 3 페르소나 + DA 캐스팅 → S1~S5 토론 → rubric 채점 → Fix → 외부 게이트. Cycle 1마다 4개 Agent tool 호출 증거가 보고에 반드시 표시. 호출 증거 없으면 SA 직접 작문 의심 — 해당 Cycle 무효 + 재실행.

4단계 — 주작-sal-da 운용

소프트웨어 트랙이면 /software-diagnosis-sal-da 로 4 PART 실행. PART 0 런타임 베이스라인 절대 건너뛰지 말 것 — 정적 분석만 한 진단은 v4.0 정의상 "진단 완료" 가 아니다. S0에서 SAL Grid 역방향 분해, S1~SN에서 카드별 진단~재진단. Stage Gate에서 Pending Critical/High 1건이라도 있으면 차단.

5단계 — 5times-debug-loop 단독 호출

빠른 박살이 필요할 때. "문제: A / 파일: B / 검증방법: C" 3줄 호출. 시각 결과물이면 Playwright가 자동 스크린샷. 사용자 "OK" 또는 5회 소진 시 종료. 미해결이면 잔여 이슈 보고 → 평가 스킬로 회귀.

6단계 — 사다리식 갈아타기 (실제 운용)

영상 §6의 권고 그대로다.

[1] review-evaluate에서 시작
       ↓ 단일 파일·문서 광택이면 여기서 끝.
       ↓ 부족하다 싶으면 ↓
[2] pro-persona-debate로 escalate
       ↓ 다관점 검증, 한 명 시각으로 답 안 나올 때.
       ↓ 그래도 부족하면 ↓
[3] 주작-sal-da로 escalate
       ↓ 실측·다차원 진단, 배포 직전, 규정 준수.

[*] 5times-debug-loop은 계층 외부 — 어느 단계에서든 명확 버그 보이면 즉시 위임

본인 실전 사례: 미니 풀스택(#6) → review-evaluate Round 3에서 97점 정체 → 사양 충족률 GAP 발견 → 빌드 오류는 /5times-debug-loop 위임 → 해결 후 review-evaluate Round 4 재개 → 100점. 한 작업에 평가 1종 + 디버깅 1종이 짝으로 돈다. 사업 기획이 섞이면 추가로 pro-persona-debate. 가볍게 여러 번 갈아탄다.

영상 제작 자체가 이 사다리의 실증 사례다. 본 챕터 영상(pBRsWeN1skY) 제작 과정에서 발표문 v1~v7을 거치며 review-evaluate가 라운드 단위로 반복 호출됐고(존댓말 톤 정렬·전문용어 풀이·섹션 시간 배분), 실측채점표(_mbo/실측채점표.md)가 MBO 6기준 채점을 누적했다. 정확히 본 챕터가 설명하는 운용 그대로다.

7단계 — 자동 체이닝 금지 + Hooks 1차 방어선

영상 §6 마지막: "자동 체이닝은 금지입니다. 평가 3종 사이의 호출은 반드시 PO 승인을 받아야 합니다. 비용 폭발을 막는 안전장치입니다." 4종 사이의 호출은 SA 임의 결정 금지, PO 명시 승인 필수. 단, 5times-debug-loop만 예외 — 단발성·가벼움이라 SA 자동 호출 허용.

추가로 href 없는 버튼·<div> 클릭·존재하지 않는 라우트·자기 검증 — 4가지를 정적 분석 항목으로 박아 settings.json hooks(#26) PreToolUse·PostToolUse에 건다. 4종은 2차 방어선, 헌법 5조항이 1차.

본인 운용 패턴

4종 스킬을 단발성 도구가 아니라 검증 운영체제 로 본다. 가장 큰 인지 전환은 "검증은 작업 끝에 한 번" 에서 "검증은 작업과 동시 진행되는 별개의 운영 트랙" 으로 넘어간 순간이었다. "검증을 미루면 검증 자체가 사라진다" 가 4,000시간에서 가장 비싸게 산 교훈. 미니 풀스택 5시간 작업이라면 5시간 안에 review-evaluate가 3번, 5times-debug가 5번 돌아간다. 작업과 검증이 같은 시간선을 공유한다.

영상 발표문 v7의 마무리(§7) 그대로 — "네 가지가 한 묶음이지만 무게가 다르고 용도가 다릅니다. 상황에 맞게 골라서 쓰십시오. 가벼운 것에서 시작해 부족하면 무거운 쪽으로 가는 것이 원칙입니다." 이 한 문장이 4종 패키지의 핵심 운용 룰이다.

또 하나 — 4종은 본인 특허 SAL Grid(#2)와 한 덩어리다. SAL Grid Stage Gate(§8.2)의 5단계 리포트 — 누락 점검 → 정합성 체크 → AI 자동 검증 → Stage Gate 리포트 → PO 승인 — 의 "AI 자동 검증" 단계가 4종으로 채워진다. MBO와도 결합 — Stage 진입 전 MBO 목표 제시 → 자율 실행 → 4종 검증 → Stage Gate. 4종이 없으면 Stage Gate가 빈 껍데기다. 본인 ax-on.net claude-code-guide.html 7,758줄의 QC 영역 6셀에도 그대로 매핑되어 학습 콘텐츠로 재이식 — "본인이 만들고, 본인이 쓰고, 본인이 가르친다". 영상(pBRsWeN1skY)까지 이어지면서 본인 시그니처 검증 패키지가 강의 → 영상 → 슬라이드쇼의 한 흐름으로 정렬됐다.
