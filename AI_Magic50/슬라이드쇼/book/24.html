SUNNY AI MAGIC 50 · #24

나를 위한 지능형 챗봇 만들어서 키우기

아바타형(전문지식·특기 전수) vs 도우미형(업무·일상)으로 분류, 본인 자료로 학습해 분신으로 키움
G4 · 결과물 및 품질관리 A타입 📜 특허 10-2026-0038658

한 줄 정의

목적별로 챗봇을 아바타형(전문지식 제공·특기 전수)과 도우미형(업무용·일상생활용)으로 갈라 설계하고, 본인 자료(WiKi LLM·NeMoTron 한국인 데이터셋·Obsidian 지식베이스)로 학습·튜닝하며, CPC(Claude Platoons Control) 웹챗봇 UI 위에 다중 챗봇을 묶어 MyChatbot World라는 단일 운영 자산으로 키우는 본인의 챗봇 자산화 노하우.

왜 이 노하우가 중요한가

챗봇은 한 번 만드는 것이 아니라 키우는 것이다. ChatGPT·Claude·Gemini 같은 범용 모델을 그대로 쓰는 것과, 본인 도메인 지식·말투·결정 기준이 박힌 챗봇을 운영하는 것은 4,000시간 누적 운용 관점에서 완전히 다른 자산이다. 전자는 사용량만큼 비용이 나가고, 후자는 시간이 갈수록 축적된다. 챗봇이 자산이 되는 임계점은 분명하다 — 내 결정 기준을 모르는 챗봇은 도구지만, 내 결정 기준을 학습한 챗봇은 분신이다.

본인이 챗봇을 단일 인스턴스가 아닌 MyChatbot World라는 다중 운영 자산으로 묶는 이유가 여기에 있다. 한 명의 사용자에게 필요한 챗봇은 1개가 아니라 영역별로 N개다. 특허 검토용·여론 분석용·일상 메모용·코드 리뷰용·학습 코칭용 — 모두 프롬프트만 다른 같은 모델이 아니라, 학습 자료·말투·결정 기준·외부 도구 연결이 모두 다른 별개 챗봇이다. 이 N개를 흩어놓으면 관리 비용이 폭증하고, 한 곳에 묶으면 시너지가 누적된다. CPC 웹챗봇 UI가 그 한 곳이다.

기존 챗봇 빌더 — Custom GPT, Poe, Coze — 가 본인 운용 기준에서 부족한 두 지점이 있다. 첫째, 본인 기록 자동 흡수. 어제 쓴 슬래시 명령어·MBO 결과보고서·Stage Gate 리포트가 오늘 챗봇의 학습 자료가 되는 흐름을 폐쇄형 빌더에서 구축하기는 까다롭다. 둘째, 본인 인프라와의 직접 결합. 본인 챗봇이 Claude Code의 슬래시 명령(/youtube-기본, /weekly-opinion-report)이나 MCP 서버(windows-mcp, stitch, cpc-channel)를 본인 환경 안에서 직접 호출해야 하는데, 폐쇄형 빌더의 Actions/플러그인 통로로는 본인 로컬 명령·로컬 MCP까지 닿지 않는다. 본인이 CPC + Vercel + Supabase 조합으로 직접 인프라를 깐 이유가 이 둘이다 — 폐쇄 SaaS에 종속되면 챗봇이 본인 운용 자산으로 키워지지 않는다.

키우지 않는 챗봇은 죽은 챗봇이고, 키우는 챗봇만이 분신이 된다. 1년 운용한 챗봇 1개가 새로 만든 10개를 이긴다 — 이 단순한 사실이 챗봇 자산화의 전부다.

핵심 개념

두 가지 기본 분류 — 아바타형 vs 도우미형

종합정리 #25 원문 그대로:

"아바타형(전문지식 제공용 or 특기 전수용)·도우미형(업무용 or 일상생활용) 구분. 단순 사용 넘어 본인만의 챗봇을 점진적으로 학습·개선시키며 자산화."

이 분류가 챗봇 설계의 첫 단추다.

분류 하위 목적 본인 사례
아바타형 전문지식 제공 본인의 전문 영역을 대신 답변 "SAL Grid 방법론 챗봇" — 특허 출원번호·청구항·운용 사례 학습
아바타형 특기 전수 본인의 운용 노하우를 전수 "Claude Code 운용 노하우 챗봇" — 본인 settings.json·hooks·슬래시 명령 학습
도우미형 업무용 일·프로젝트 관리 보조 "Stage Gate 리뷰 챗봇" — MBO 결과보고서 자동 검토
도우미형 일상생활용 메모·일정·생활 관리 "일일 회고 챗봇" — 매일 저녁 그날 결정 기록

분류가 다르면 학습 자료·말투·외부 도구 연결이 모두 다르다. 아바타형은 본인 자료를 가르쳐 본인을 흉내내게 하고, 도우미형은 본인 작업 패턴을 학습해 본인 보조에 최적화시킨다. 둘을 섞으면 양쪽 다 어정쩡해진다 — 본인이 두 번 시도하고 두 번 실패한 뒤 분리 운용으로 정착시켰다.

4단계 자산화 사이클

챗봇 1개를 자산으로 만드는 표준 사이클.

1. 정의   — 분류(아바타/도우미) + 목적 한 문장 + KPI 1개
2. 학습   — Obsidian Wiki + WiKi LLM + NeMoTron 한국인 합성 데이터셋
3. 운영   — CPC 웹챗봇 UI에 등록 → 일일 사용
4. 개선   — 사용 로그 → 약점 추출 → 학습 자료 보강 → 재배포

3단계까지는 누구나 한다. 4단계 개선 루프가 자산화의 본질이다. 사용 로그를 안 보면 챗봇은 그 자리에 머문다. 본인 운용에서는 주 1회 챗봇별 약점 회고를 강제한다 — 이 회고가 없으면 키우는 챗봇이 아니라 방치된 챗봇이다.

학습 자료 3종 (#48, #46 결합)

자료 용도 출처
Obsidian Wiki + WiKi LLM(#48) 본인 전 분야 지식베이스 본인 Wiki 저장소
NeMoTron 한국인 합성 데이터셋(#46) 한국어 자연스러운 어조 보강 엔비디아 공개 100만 샘플
본인 작업 기록 MBO 결과보고서·Stage Gate 리포트·grid_records JSON Process/·grid_records/

세 자료의 결합이 핵심. 본인 지식(Wiki) + 한국어 어조(NeMoTron) + 본인 작업 기록의 3축이 모이면 챗봇이 본인 어조로 본인 일을 본인처럼 답한다. 한 축만 빠져도 챗봇은 남의 챗봇처럼 답한다.

CPC 인프라 위에 얹기

cpc-setup SKILL.md(SSOT)의 핵심 구조:

소대장(Claude Code) ←─ engage ──→ 웹챗봇 UI(CPC Web UI)
       │                              │
       └────────── CPC API ───────────┘
                     │
              ┌──────┴──────┐
              │  Supabase   │  cpc_platoons (15개)
              │  (서울)      │  cpc_commands (명령 큐)
              └─────────────┘

3단 분리 원칙:

스킬 역할 시점
/cpc-setup 인프라 구축(Supabase + Vercel + 웹챗봇 UI) 최초 1회
/platoon-formation 소대 편제 팀구성 프로젝트 시작
/cpc-engage 소대장 접속 매 세션

본인 챗봇은 이 인프라 위에 소대로 얹힌다. 챗봇 1개 = 소대 1개. MyChatbot World는 N개 소대의 모음이며, 한 웹 UI에서 모두 호출 가능하다. 모바일에서 원격 데스크탑 없이 챗봇만 쓸 때도 이 UI 하나면 끝난다.

deploy-skill-기본 5대 철칙 적용

본인 챗봇을 키울 때 그대로 쓰는 5대 철칙(deploy-skill-기본 SKILL.md SSOT):

  1. 분대장 주도 — 챗봇은 본인의 도구, 능력 확장 수단
  2. 기존 우선 — 이미 있는 챗봇 최우선 활용 (새로 만들기 전 검색)
  3. 커뮤니티 활용 — 없으면 외부에서 검색/다운로드 (#11과 결합)
  4. 신규 생성 — 그래도 없으면 직접 만들기
  5. 비용 최소화 — 챗봇은 무료 (코드일 뿐, API 비용은 사용량 기반)

이 5단계가 기존 → 외부 → 신규 순으로 작동해야 챗봇 수가 폭주하지 않는다. 본인이 처음 1년간 챗봇 50개를 만들었는데, 5대 철칙 도입 후 핵심 7개로 압축했다 — 적게 가지되 깊이 키운다가 자산화의 마지막 룰이다.

3단 분리: 챗봇 ≠ 슬래시 명령 ≠ 서브에이전트

본인 운용에서 가장 자주 혼동되는 경계.

도구 정체 사용 시점
챗봇 대화형 인터페이스(웹 UI) + 학습된 페르소나 사람이 직접 말 걸 때
슬래시 명령(#21) ~/.claude/commands/*.md 단축 워크플로 Claude Code 내 반복 작업
서브에이전트(#39) Task tool로 스폰되는 하위 작업자 큰 작업 위임

챗봇이 슬래시 명령을 호출하고, 슬래시 명령이 서브에이전트를 호출하는 3단 위임이 본인 운용의 표준이다. 챗봇이 직접 모든 일을 하면 컨텍스트가 폭발하고, 챗봇이 슬래시 명령을 호출하면 작업이 캡슐화된다.

실전 사용법

1단계 — 챗봇 정의서 작성 (5분)

새 챗봇 1개당 5분짜리 정의서를 먼저 쓴다. 이게 없으면 키우지 못한다.

name: SAL_Grid_아바타
type: 아바타형/전문지식
purpose: SAL Grid 방법론에 대한 모든 질문에 본인을 대신해 답변
KPI: 주 5회 이상 호출, 답변 만족도 4.0/5.0 이상
학습_자료:
  - 본인 Wiki/SAL_Grid 분류
  - 특허명세서 통합본
  - 청룡-sal-grid-dev 스킬 정의서
말투: 본인 1인칭, 사례·수치 우선, 슬로건 회피
연결_도구:
  - /sal-grid-task-create
  - cpc-channel MCP

2단계 — /cpc-setup으로 인프라 1회 구축

/cpc-setup           # 인프라 전체 설치(Supabase + Vercel + 웹챗봇 UI)
/cpc-setup check     # 상태 점검만

CPC가 처음 1회 깔리면 그 후 챗봇 추가는 등록만 하면 된다. 본인은 claude-platoons-control.vercel.app 도메인에 15개 소대 슬롯을 미리 잡아두고 챗봇별로 슬롯 1개씩 점유한다.

3단계 — 학습 자료 3종 통합

my-chatbot/
├── corpus/
│   ├── wiki/            ← Obsidian Wiki 심볼릭 링크
│   ├── records/         ← MBO 결과보고서·Stage Gate 리포트
│   └── nemotron-ko/     ← 한국어 어조 샘플
├── persona.md           ← 말투·결정 기준·금지사항
└── tools.yml            ← 연결할 슬래시 명령·MCP 서버 목록

persona.md에 본인 시그니처(1인칭, ax-on.net, 본인 특허)를 박아둔다. 슬로건 회피·사례 우선·수치 우선의 3원칙도 명문화. 이걸 안 박으면 챗봇은 교과서 답변만 한다.

4단계 — CPC 소대로 등록 + 모바일 접속

웹챗봇 UI에서 챗봇 1개를 소대 슬롯 1번에 등록. 모바일 Google 드라이브 앱처럼, 폰 브라우저로 claude-platoons-control.vercel.app을 열면 어디서든 본인 챗봇과 대화 가능. 원격 데스크탑 거치지 않는다 — 챗봇 자산화의 외부 가용성이 이 단계에서 확보된다.

5단계 — deploy-skill-기본 5대 철칙으로 도구 장착

챗봇이 단순 대화 봇에 머무르지 않게 하려면 능력 확장을 강제한다.

# tools.yml
slash_commands:
  - /sal-grid-task-create   # 본인 정의 슬래시 명령
  - /youtube-기본            # 영상 자동화 직결
  - /weekly-opinion-report  # 보고서 → 영상 파이프
mcp_servers:
  - cpc-channel             # 다른 소대(챗봇)와 메시지 교환
  - windows-mcp             # 로컬 파일·앱 제어
  - stitch                  # 디자인 시스템 호출

이 시점부터 챗봇이 대화형 인터페이스를 넘어 실행 컨트롤러가 된다. "유튜브 영상 1편 만들어줘" 한 마디에 챗봇이 /youtube-기본 슬래시 명령을 호출, 50씬 영상이 나온다. 챗봇은 더 이상 채팅창이 아니라 작전실이다.

6단계 — 주 1회 약점 회고 (개선 루프)

grid_records/{ChatbotID}.json에 주간 약점을 기록.

항목 예시
답변 실패 "특허 청구항 7번 질문에 일반론으로 회피"
어조 깨짐 "슬로건 답변 3건 — 사례·수치 우선 룰 위반"
도구 미호출 "유튜브 요청에 슬래시 명령 호출 누락 2건"
학습 자료 부족 "Cluster Mode 설명 빈약 — Wiki 미동기화"

회고 후 학습 자료 보강 → 재배포. 이 주간 사이클이 빠지면 챗봇은 그 자리에 머문다. 본인은 매주 일요일 저녁 30분을 챗봇 7개 회고에 고정 배정한다 — 시간 단위로 보면 큰 투자처럼 보이지만, 1년 누적 시 챗봇 1개당 26시간 학습이며 분신 수준에 도달한다.

7개 챗봇을 한 화면에서 본다.

[일일_회고]          호출  7회/주  만족도 4.5   학습  5시간

호출 빈도 5회/주 이하면 통폐합 또는 폐기 후보. 7개 룰을 지킨다. 늘리지 않고 깊게 키우는 것이 MyChatbot World의 운영 헌법이다.

본인 운용 패턴

챗봇 자산화의 본질은 사용 로그가 학습 자료가 되는 폐회로다. 어제 챗봇과 나눈 대화가 오늘 챗봇 학습 자료로 들어가고, 내일 답변 품질이 그만큼 올라간다. 이 폐회로가 닫히지 않으면 챗봇은 늙지 않고 죽는다. 본인 운용에서 매일 저녁 자동 스크립트가 그날 챗봇 대화 로그를 corpus/records/로 자동 동기화한다 — 사람이 잊어도 시스템이 잊지 않게.

또 하나 — 챗봇은 자기 자신을 검증하지 않는다. SAL Grid의 Task Agent ≠ Verification Agent 원칙이 챗봇 도메인에 그대로 적용된다. 챗봇 답변 품질은 별도 채점 챗봇이 평가한다. 본인이 만든 코드_리뷰_봇이 SAL_Grid_아바타의 답변을 채점한다 — 자기 검증 금지. 그래야 curl 200 ≠ 동작함과 같은 답변 200 ≠ 정확함 사고가 막힌다.

마지막으로 — MyChatbot World는 공유 가능한 자산이다. 7개 챗봇 정의서·학습 자료·CPC 소대 등록 정보를 통째로 다른 분야에 이식하면 그 분야의 MyChatbot World가 빠르게 복제된다. 챗봇이 단일 인스턴스가 아니라 운영 시스템으로 자산화되는 지점이 여기다. 누적 운용의 결론 — 챗봇은 도구가 아니라 분신이며, 분신은 시스템으로 키운다.
