# 5. Dual Mode 실행

## 한 줄 정의

한 가지 작업에 *A 인스턴스*와 *B 인스턴스* 두 놈을 동시에 투입하는 **쌍두마차** 운용 패턴. 귀찮고 토큰 비용이 조금 더 들어가더라도 품질 관리를 위해 상시 적용한다.

## 왜 필요한가

Claude Code 한 인스턴스만 굴리면 네 가지가 한꺼번에 무너진다. 검증할 사람이 본인 하나뿐이고, 관점이 한 방향에 갇히며, 일이 직렬로만 진행되고, 한 인스턴스가 Rate Limit이나 Compact에 걸리면 그 자리에서 멈춘다. 본인이 다인스턴스 동시 운용에서 도달한 결론은 단순하다. *한 작업에 두 놈을 동시에 태운다.* 두 인스턴스가 같은 자료를 보고 같은 일을 다르게 굴리면 위의 네 약점이 동시에 사라진다.

## 네 가지 효능

쌍두마차에는 본인이 직접 확인한 네 가지 효능이 있다. 각각이 단독으로도 듀얼을 정당화하지만, 본인은 한 작업에서 보통 둘 이상이 동시에 발생한다.

**첫째, 크로스 체킹.** A가 만든 결과를 B가 같은 자료를 보고 독립적으로 검증한다. Task Agent ≠ Verification Agent 원칙이 한 사람의 머리 안이 아니라 두 인스턴스 사이에서 자연스럽게 성립한다. A가 자기 코드를 자기가 통과 처리하는 자기검증 폐쇄 루프가 구조적으로 차단된다.

**둘째, 관점 종합.** 같은 문제를 A에게는 *어떻게 해결하나*, B에게는 *어떻게 우회하나*처럼 서로 다른 각도로 던지면 두 결과의 합집합이 한 인스턴스의 단일 풀이보다 풍부해진다. 사고용·실행용으로 가르는 것은 이 효능의 한 변형일 뿐이고, 본인은 *공격적 안*과 *보수적 안*, *최단경로*와 *우회로*, *Top-down*과 *Bottom-up* 같은 대비축으로 자주 가른다.

**셋째, 병렬 분담.** 하나의 PHASE 안에 독립 작업이 둘 이상 있을 때 A와 B에 각각 던지면 시간이 절반으로 줄어든다. SAL 좌표상 같은 Level의 Variant a·b가 듀얼의 자연스러운 분담 단위가 된다. 30개 동시 운용의 가장 작은 단위가 이 듀얼이다.

**넷째, 연속성 유지.** A가 Rate Limit·Compact·세션 단절에 걸려도 B가 같은 PHASE 파일을 보고 있으므로 즉시 일을 흡수한다. 단절 0회를 본인은 운용 KPI로 잡는다. 페이스북 노트에 본인이 *귀찮고 토큰 비용이 조금 더 들어가도 꼭 해야 한다*고 적은 이유가 이 네 번째다. 한 번이라도 큰 작업이 중간에 끊겨 본 사람은 비용 차이가 위험 차이를 못 따라온다는 것을 안다.

## 핵심 운용 원칙

쌍두마차는 두 인스턴스가 *같은 자료를 본다*는 한 가지 전제 위에서만 작동한다. PHASE 파일·MBO 목표서·SAL Grid Stage 카드 같은 진실 소스를 양쪽이 동일하게 Read하지 않으면 둘은 다른 문제를 푸는 두 사람이 되어 버린다. 본인 운영 규칙은 다음 세 가지로 압축된다.

| 항목 | A 인스턴스 | B 인스턴스 |
|------|-----------|-----------|
| 자료 | 동일 PHASE / MBO / SAL Grid Read | 동일 PHASE / MBO / SAL Grid Read |
| 역할 | 효능에 따라 가변 (검증자·다른 관점·병렬 짝·생존자) | A의 짝 — 반대 축 담당 |
| 모델 | 보통 Opus 또는 Sonnet | 보통 Sonnet 또는 Haiku |

역할은 효능에 따라 매번 다르게 캐스팅된다. 크로스 체킹이면 *생산자·검증자*, 관점 종합이면 *공격·수비*, 병렬 분담이면 *Variant a·Variant b*, 연속성이면 *주·예비*다. 고정된 역할 한 쌍을 박아 두지 않는 것이 본인 운용의 특징이다.

## 실전 사용법

먼저 작업 시작 전에 PHASE 파일을 만들어 양쪽이 같은 진실 소스를 본다 (`zz_KingFolder/_TalkTodoPlan/YYYY_MM_DD__HH.MM_PHASE_*.md`). 다음 그 작업에서 네 효능 중 어느 것이 가장 필요한지 한 번 정한다. 정하지 않으면 둘 다 같은 일을 두 번 하는 낭비가 된다.

크로스 체킹이라면 A에 생산을 시키고 B에는 *A의 결과만 받아 검증* 지시를 따로 내린다. 관점 종합이라면 A와 B에 각자의 축을 부여한 뒤 산출물을 본인이 합치거나 셋째 인스턴스에 합치게 시킨다. 병렬 분담이라면 SAL Variant a·b를 그대로 한 쪽씩 던진다. 연속성이라면 한쪽이 컨텍스트 80%에 도달했을 때 즉시 다른 쪽으로 작업을 옮기는데, **#40 HUD**의 LINE2 막대가 그 시점을 미리 알려준다.

## 비용과 가치

토큰 비용은 단순 계산으로는 두 배다. 그러나 본인 실측 기준 단절 1회 복구 비용·자기검증 폐쇄로 인한 버그 1건 비용·단일 관점 결정으로 인한 재작업 비용이 듀얼 1회 비용보다 거의 항상 크다. 페이스북 노트에 본인이 *상시 적용하기로 결정*이라고 못 박은 이유가 이 비교다. 작업 단위가 작을수록 듀얼 비용 비중이 커 보이지만, 큰 작업 한 건에서 막힘이 발생하는 순간 단일 운용은 듀얼보다 훨씬 비싸진다.

## 주의

쌍두마차가 무력화되는 두 경우가 있다. 첫째, A와 B가 같은 모델·같은 프롬프트·같은 컨텍스트에 들어가면 두 인스턴스가 사실상 한 머리가 되어 크로스 체킹이 무력화된다. 둘째, 본인이 A 결과를 보고 B 지시를 만들면 본인의 사각지대가 양쪽에 그대로 옮겨간다. 본인 규칙은 *A 결과를 B에 던지기 전 사람이 다시 정리하지 않는다* — 원문을 그대로 넘긴다.

또 하나의 함정은 자기검증 폐쇄 루프다. 본인이 시간을 아끼려고 A에게 *네 결과 네가 검증해라*고 시키면 듀얼은 무너진다. Task Agent ≠ Verification Agent. 검증은 반드시 B 인스턴스가 받는다.
