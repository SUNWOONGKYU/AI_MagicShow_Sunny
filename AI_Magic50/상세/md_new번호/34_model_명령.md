# 34. `/model` 명령으로 작업에 맞는 모델 선택하기

## 한 줄 정의

작업 성격에 따라 Opus·Sonnet·Haiku를 의식적으로 갈아끼우는 운용 — **모델은 무료가 아니라 자원**이라는 인식.

## 왜 이 노하우가 중요한가

기본값 하나로 30개 인스턴스를 다 굴리면 비용도 낭비, 속도도 낭비다. 단순 요약을 Opus에 시키는 것은 트랙터로 모종 옮기는 격이고, 특허 차별점 도출(#27)을 Haiku에 시키는 것은 삽으로 댐 쌓는 격이다.

본인 운용에서 모델 배정은 **역할 = 모델**의 1:1 매핑에 가깝다. 소대장(주력 사고)·분대장(중간 조율)·분대원(반복 실행)이 #14 편제로 정해지면, 그에 맞춰 #4가 모델을 박는다. 이 매핑이 없으면 #23(API 비용 최적화)는 슬로건일 뿐이다.

## 핵심 개념

`/model` 명령은 대화 중 즉시 모델을 바꾼다. 헤드리스는 `--model` 플래그.

```bash
/model opus           # 대화 중 전환
claude --model sonnet
claude -p "..." --model haiku
```

본인 매핑 표:
| 작업 | 모델 | 이유 |
|------|------|------|
| SAL Grid 설계, 특허 차별점 도출, 풀스택 설계 | **Opus** | 깊은 추론 필요 |
| 일반 코딩, 리팩토링, 문서 작성, 토론 진행 | **Sonnet** | 균형 |
| 요약, 변환, 분류, 파일 일괄 처리 | **Haiku** | 속도·비용 |
| 30개 운용 중 분대원 다수 | **Sonnet/Haiku 혼합** | 비용 통제 |
| 소대장 1개 | **Opus** | 의사결정 품질 |

가격 차이는 입력 토큰 기준으로 Opus가 Haiku의 약 15~20배다. 30개 중 1개만 Opus로 두고 나머지를 Sonnet/Haiku로 배분하면 같은 throughput에서 비용이 큰 폭으로 떨어진다.

## 실전 사용법

**1단계** — 작업 시작 전 자문: "이 작업은 깊이 사고가 필요한가, 빠른 변환이 필요한가?" 답이 모델을 정한다.

**2단계** — 30개 인스턴스 시작 시 모델 의식적 분배. 본인 표준은 Opus 1, Sonnet 6~8, Haiku 나머지.

**3단계** — 같은 세션 안에서도 단계별 전환. 기획 단계 Opus → 실행 단계 Sonnet → 정리·요약 단계 Haiku.

**4단계** — 헤드리스(#12) 크론에 `--model` 명시. 자동화는 단순 변환이 많아 Haiku가 기본값으로 적합하다. 단순 변환이 아닌 자동화는 Sonnet.

**5단계** — `.claude/settings.json` 프로젝트별 기본 모델 설정. SAL Grid 같은 깊이 작업 폴더는 Opus 기본, 단순 문서 폴더는 Haiku 기본. worktree(#41)별로도 다르게 둘 수 있다.

**6단계** — 본인 측정 패턴. 같은 작업(예: 슬라이드 50장 마크업 정리)을 Opus·Sonnet·Haiku로 한 번씩 굴려보고 결과물 차이와 비용을 표로 정리해둔다. 누적 운용의 상당 부분이 이 측정으로 모인다. 본인 패턴은 SAL Grid 설계는 Opus가 압도적, 일반 리팩토링은 Sonnet이 가성비 1위, 50개 파일 일괄 요약은 Haiku가 Sonnet 대비 6~8배 빠르고 결과 차이 미미.

**주의** — 모델을 바꿨다고 모든 게 해결되지 않는다. Opus도 틀린다. **#17 AI 오류 인정 + #49 자율 검증**이 필수. 모델 선택은 비용·속도 레버일 뿐, 검증 책임은 항상 사용자(또는 Verification Agent)에게 남는다.
