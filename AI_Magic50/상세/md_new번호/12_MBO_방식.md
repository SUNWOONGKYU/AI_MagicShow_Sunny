# 12. MBO 방식으로 작업시키기

## 한 줄 정의

작업 시작 전에 **목표·KPI·실행계획·리스크를 4표 양식으로 구조화한 MBO 목표서를 PO에게 제시·승인받아야** 실행이 시작되며, 완료 시 목표 달성 여부를 KPI 실측으로 보고하게 만드는 — Claude Code 작업 합의 골격. 경영학의 Management by Objectives를 1인-AI 협업 구조에 이식한 것.

## 왜 이 노하우가 중요한가

MBO는 **1954년 피터 드러커가 *The Practice of Management*** 에서 제시한 경영 철학이다. "조직 구성원 각자가 상위 조직의 목표와 자신의 목표를 정렬하고, 정해진 목표 대비 결과로 평가받는다"는 원리에 기반한다. 70년이 지난 지금도 OKR(Objectives and Key Results)·SMART(Specific Measurable Achievable Relevant Time-bound)·KPI 체계의 뿌리이며, 본질은 **합의된 목표·자율 실행·결과 책임** 세 단어로 압축된다.

OKR과의 차이는 분명하다 — OKR은 *Aspirational*(도전 목표·달성률 70%면 성공)이고, MBO는 *Committed*(합의 목표·100% 달성 의무). 1인-AI 협업 구조에 더 적합한 쪽은 MBO다. 이유는 단순하다 — AI에게는 "도전"이 의미가 없다. AI는 합의된 목표를 100% 달성하든가, 못하든가 둘 중 하나다. 절반 달성은 사실상 미달성이며, 그 사실을 솔직히 보고하게 만드는 구조가 필요하다.

이 원리를 Claude Code에 적용해야 하는 이유는 명확하다. AI에 일을 시키면 빠르게 뭔가가 만들어지지만 **"내가 시킨 게 정말 그거였나"** 가 절반쯤 어긋난다. AI는 모호한 지시를 자기 식으로 해석하고, 결과물을 내놓고, 사용자는 그제야 깨닫는다. 30개 동시 운용에서는 이 어긋남이 30배로 곱해진다. 본인이 SKILL_ATLAS S5에서 겪은 사고("curl 200 OK"로 Verified 처리했지만 사용자가 브라우저로 보니 버튼 4개 모두 무반응) 가 정확히 이 어긋남이다 — *데이터 레이어 KPI는 달성했지만 사용자 여정 KPI를 합의하지 않았기 때문*.

원인은 합의 부재다. 기존 흐름 "지시 → 실행 → 결과"에는 *지시 내용을 PO·AI 양쪽이 동일하게 이해했는지 검증하는 단계*가 빠져 있다. MBO는 이 사이에 **"목표서 제시 → PO 승인"** 한 단계를 끼워 넣는다. 4표(현재vs목표·KPI·실행계획·리스크)를 PO가 보고 승인하면 합의된 계약이 되고, 완료 시 **목표서를 그대로 가져다가 O/X로 표기한 결과보고서**가 나온다 — 변명이 아닌 결과로 책임이 정리되는 구조다.

## 핵심 개념

### PO 철학 (스킬 헤더 인용)

> *"과정은 너의 마음대로 진행해도 좋다. 그러나, 나랑 합의를 해서 사전에 설정한 목표는 무조건 달성해야 한다. 단, 품질은 최고로, 비용은 합리적 수준으로, 투입시간은 적절하게."*

한 문장에 **자율과 책임**이 짝으로 묶여 있다. 자율 = "방법은 마음대로", 책임 = "목표는 무조건". 이것이 1인-AI 협업의 가장 효율적인 계약 형태다.

### 3 PHASE 구조

| PHASE | 단계 | 핵심 |
|-------|------|------|
| **1. 목표 정의** | 맥락 분석 → AS-IS 조사(코드 Read·배포 확인) → TO-BE 정의 → KPI 설정 → Task 도출 → **PO 승인 대기** | 승인 없이 PHASE 2 진입 절대 금지 |
| **2. 실행** | 목표서 파일 저장(`_TalkTodoPlan/YYYY_MM_DD__HH.MM_MBO_{작업명}.md`) → Task 순서대로 실행 → 필요 시 중간 점검(KPI 현황표) | PO 간섭 없음, 합의 범위 이탈 시 즉시 보고 |
| **3. 결과 보고** (`/mbo report`) | AS-IS/TO-BE/실제 결과 O·X 표 + KPI 실측 + 미달성 사유·후속조치 + 총평 | 같은 MBO 파일 하단에 추가 기록 |

3 PHASE는 분리되지 않는다. PHASE 1만 하고 끝내면 합의는 됐지만 결과가 없고, PHASE 2부터 시작하면 합의가 없으니 결과가 어긋난다. 셋이 한 묶음이어야 의미가 있다.

### MBO 목표서 4표 양식

1. **현재 vs 목표** (AS-IS / TO-BE 항목별 대비)
2. **측정 지표 KPI** (지표·현재값·목표값·측정 방법) — *"좋게 만든다"가 아니라 "Lighthouse Performance 80→95"*
3. **실행 계획** (Task·설명·예상 결과)
4. **리스크 및 대응 방안**

목표서 마지막은 항상 *"이 목표를 승인하시겠습니까?"* 로 끝맺는다. 승인 = 계약 체결.

KPI는 반드시 **데이터 레이어 + 사용자 여정** 양쪽을 포함해야 한다. SKILL_ATLAS 사고 이후 추가된 규칙. 예 — "테이블에 데이터가 있다(데이터 레이어)" + "랜딩 페이지 주요 버튼 4개를 클릭 시 각각 올바른 라우트로 네비게이트(사용자 여정)" 가 둘 다 있어야 합격.

### 9원칙 요지

합의 목표 무조건 달성 / 품질 최고 / 비용 합리적 / 시간 적절 / KPI 측정 가능 수치 / 승인=합의 / 과정 자율 / 결과는 목표 대비 / 미달성도 사유·후속조치 기록.

이 9원칙은 단순한 슬로건이 아니라 **`/mbo report` 양식의 강제 항목**이다. 미달성 항목에 사유와 후속조치를 안 적으면 결과보고서가 거부된다.

### SAL Grid와의 짝

청룡 스킬 §6.0이 *"각 Stage 진입 전 MBO 목표 제시 + PO 승인 필수"* 를 강제한다. SAL Grid가 실행 골격이라면 **MBO는 그 위의 합의 골격**. 두 스킬을 분리해 쓰지 않는다. SAL Grid 프로젝트가 자동 감지되면 Stage 진입 키워드("S2 실행", "다음 Stage", "Stage Gate 통과", "S{N} 진입")에서 자동으로 MBO가 발동한다 — 사용자가 "MBO 해" 라고 말하지 않아도.

## 실전 사용법

### 기본 호출

| 명령 | 동작 |
|------|------|
| `/mbo` | 대화 맥락에서 자동 도출 |
| `/mbo {주제}` | 명시적 주제 지정 (예: `/mbo 디자인 혁신`) |
| `/mbo report` | 진행 중 MBO 달성 여부 보고 |

### 6단계 운용

**1단계 — `/mbo` 발동**. 단순 호출 한 번에 AI가 맥락 분석·파일 Read·배포 확인까지 자동 수행하고 4표 양식의 목표서를 생성한다. 이 한 번의 발동이 수백 줄짜리 합의 명세로 변환된다.

**2단계 — 4표 양식 PO 제시**. *"이 목표를 승인하시겠습니까?"* 로 끝맺고, 수정 요청 시 재제시. 승인 전 코드 한 줄도 건드리지 않는다.

**3단계 — KPI 수치화 강제**. "성능 개선" → **"Lighthouse 80→95"**, "버그 수정" → **"E2E 12개 중 12개 통과"**, "UI 정리" → **"주요 버튼 4개 클릭 시 100% 정상 라우팅"**. 측정 불가능한 KPI는 자동 거부.

**4단계 — 승인 즉시 MBO 파일 저장**. `zz_KingFolder/_TalkTodoPlan/YYYY_MM_DD__HH.MM_MBO_{작업명}.md` 양식으로 자동 저장. 컨텍스트 압축·세션 전환 시 파일 한 번 읽으면 합의 복원. 이 파일이 30개 인스턴스 사이의 단일 진실 원천(SSOT) 역할을 한다.

**5단계 — 자율 실행**. PO 간섭 없음. 단, 합의 범위를 벗어나는 변경은 즉시 보고하고 목표서 갱신 후 재승인. 중간 점검이 필요하면 KPI 현황 미니 표 — `목표 / 현재 / 달성률` — 한 장으로 보고.

**6단계 — `/mbo report`**. AS-IS/TO-BE/실제 결과 O·X 표 그대로 출력, 미달성 항목은 **사유+후속조치 의무 기재**. 실패도 기록돼야 다음번 정확도가 올라간다. 결과보고서는 같은 MBO 파일의 하단에 "## 결과 보고" 섹션으로 추가 — 한 파일에 합의와 결과가 짝으로 남는다.

## 본인 운용 패턴

비표준·창의적 작업은 반드시 MBO 선행, 단순 반복(번역·포맷팅·파일명 변경) 은 생략. 판단 기준은 단순하다 — *"끝나고 PO가 '내가 시킨 게 이거였나' 헷갈릴 가능성이 있는가?"* 가 있으면 MBO, 없으면 생략.

SAL Grid 프로젝트는 Stage 시작마다 자동 발동(§6.0 강제). 일반 프로젝트도 3단계 이상이면 MBO 권장.

미달성 보고가 부끄럽지 않은 문화 — 변명 대신 사유 한 줄, 후속조치 한 줄. 이게 다음 작업의 정확도를 올리는 유일한 방법이다. 본인 누적 운용에서 가장 많이 배운 곳은 100% 달성한 MBO가 아니라 부분달성으로 끝난 MBO들이다.

> 본인 운용 사례: 한 MBO 파일 안에 최상위 목표·KPI·실행 계획·범위 확장 4표를 두고, 그 아래 *"결과 보고 → v5 재빌드 (품질 우선)"* 두 섹션이 이어지는 구조가 자주 등장한다. 한 MBO 파일 안에서 **합의 → 자율 실행 → 결과 보고 → 미달성 시 재빌드**가 단일 파일 단위로 굴러간 흔적이다. 같은 양식이 시뮬레이션·검증·배포 작업에 그대로 이식된다.
