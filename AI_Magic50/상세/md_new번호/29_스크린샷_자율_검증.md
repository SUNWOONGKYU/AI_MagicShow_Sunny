# 29. 스스로 스크린샷 찍어서 문제점 찾아 스스로 수정하기

## 한 줄 정의

Claude Code가 결과물 화면을 **자기가 캡처하고, 자기가 보고, 자기가 결함을 찾고, 자기가 고치는** Playwright 기반 자율 검증 루프. *"curl 200 ≠ 동작함"* 이라는 본인 헌법 1조항을 코드 단에서 직접 실행하는 검증 인프라이며, **시각 결과물(웹 UI·슬라이드쇼·HTML 보고서)을 사람 눈 없이 양산할 때 유일하게 신뢰 가능한 보증 메커니즘** 이다. 본인 운용에서는 5times-debug-loop-코어3 스킬이 1440×900 데스크탑 + 390×844 모바일 듀얼 해상도로 자동 캡처를 띄우고, 그 PNG를 Read tool로 다시 읽어 *"시각 회귀(visual regression)"* 를 자가 판정한다. 사람 눈으로 한 번 보고 끝낼 것을 AI가 5회 루프로 박살내기 때문에 — 결과적으로 사람 눈보다 더 꼼꼼하다.

## 왜 이 노하우가 중요한가 — "curl 200 ≠ 동작함" 사고

본인 글로벌 CLAUDE.md에 박혀 있는 UI 검증 철칙은 실제 배포 사고에서 나왔다. **curl로 200 확인하고 Verified 처리**했지만 사용자가 실제 브라우저에서 보니:

- 주요 버튼들 — `href` 없어서 클릭 무반응
- 카드형 클릭 영역 — `<div>`로 만들어 클릭 불가
- "View All" — 존재하지 않는 라우트로 404
- 상세 페이지 카드 — 경로·파라미터 전부 틀림

데이터 레이어 KPI("테이블에 데이터가 있다")는 통과했지만 **사용자 여정 KPI**(주요 버튼 4개 클릭 시 올바른 라우트로 네비게이트)는 0점이었다. **본 챕터(#29)는 이 사용자 여정 KPI를 자동으로 돌리는 루프**다.

이 사고가 가르친 본질은 단순하다 — **AI는 자기가 출력한 코드의 "보이는 모습"을 사람 눈 없이는 모른다**. HTML이 파싱되고 200을 반환해도, `<Button>`이 href를 안 갖고 있으면 사람 눈에는 "클릭 불가 버튼"으로 보인다는 사실을 AI는 코드만 보고는 알 수 없다. 그렇다고 작업마다 사람이 일일이 클릭해서 확인하면 1일 1영상(#26)·미니 풀스택 5시간(#25)·슬라이드쇼 배포 같은 자동화가 무너진다. 해법은 하나 — **AI에게 눈을 달아준다**. Playwright가 그 눈이다. 캡처한 PNG를 Read tool로 다시 읽으면 AI가 자기 화면을 본다. 그 화면에서 결함을 찾으면 5times-debug-loop이 5회 루프로 고친다. **사람 눈을 AI 눈으로 치환**하는 것이 본 루프의 본질이고, 이게 없으면 같은 사고가 반복된다.

## 핵심 개념 — 본인 글로벌 CLAUDE.md UI 검증 철칙 (인용)

> **"curl 200 ≠ 동작함"** — HTTP 상태코드만 보고 "작동한다"고 판단하지 마라.
>
> 1. UI Task 검증 시 `curl 200` → Verified 금지. 실제 브라우저(또는 Playwright)에서 클릭 테스트 필수.
> 2. 배포 후 첫 액션은 `curl`이 아니라 "배포 URL을 브라우저로 직접 열어 주요 버튼/링크를 모두 클릭해본다" 이다.
> 3. KPI에 사용자 여정 지표를 반드시 포함한다.
> 4. `href` 없는 `<Button>`, 클릭 가능해 보이는 `<div>`는 버그로 간주.
> 5. **자기 검증 금지** — Task Agent가 자신의 UI를 Verified 처리하면 안 된다. 반드시 별도 Verification Agent가 클릭 테스트.

자율 루프 단계:
```
Task Agent: 코드 작성·배포
   ↓
Verification Agent (별도 인스턴스):
   1. Playwright로 URL 접속 (데스크탑 1440×900 + 모바일 390×844 듀얼)
   2. 주요 버튼·링크 모두 클릭 → 라우트 결과·404 검출
   3. 페이지별 PNG 스크린샷 저장
   4. Read tool로 PNG 재독해 → 시각 결함(레이아웃 깨짐·텍스트 잘림·아이콘 누락 등) 탐지
   5. dead-link 정적 분석 (href 없는 a/Button, 클릭 핸들러 없는 클릭 가능 div)
   ↓
재 Task Agent: 검출된 결함 수정 (최대 5회 — 5times-debug-loop)
   ↓
재 Verification Agent: 재캡처 → 재검증 → 통과 시 종료
```

## Playwright 스크린샷 메커니즘 (5times-debug-loop 내장)

본인 운용에서 가장 자주 작동하는 부분이다. 5times-debug-loop-코어3 스킬이 내장한 자동화 절차.

| 단계 | 동작 | 도구 |
|---|---|---|
| 1 | `page.goto(URL)` + 4초 대기 (skeleton/로딩 고착 차단) | Playwright |
| 2 | 데스크탑 1440×900 풀페이지 스크린샷 → `desktop.png` | Playwright |
| 3 | 모바일 390×844 풀페이지 스크린샷 → `mobile.png` | Playwright |
| 4 | 주요 버튼·링크 자동 탐색 → 클릭 → 라우트 결과 기록 | Playwright |
| 5 | PNG 파일을 Read tool에 넘김 → 멀티모달로 화면 인지 | Claude Read |
| 6 | 결함 발견 시 Edit tool로 코드 수정 → Step 1 재진입 | Claude Edit |

핵심은 **5단계**다. Claude는 PNG를 텍스트가 아니라 *이미지로* 본다 — 즉 사람이 화면 보는 것과 본질적으로 같은 정보 입력 채널이다. 텍스트 분석으로는 잡지 못하는 *"버튼 라벨이 카드 박스 밖으로 튀어나옴"*, *"다크 배경에 다크 텍스트라 안 보임"* 같은 결함이 이 단계에서 잡힌다.

## 실전 사용법

**1단계** — `5times-debug-loop-코어3` 스킬 발동. *"문제: A / 파일: B / 검증방법: C"* 3줄 호출. 검증방법에 URL을 넣으면 Playwright가 자동 가동.

**2단계** — 검증용 Playwright 스크립트 자동 생성. `page.goto(URL)` → 데스크탑·모바일 듀얼 스크린샷 → `page.click(<주요 버튼들>)` → URL 체크. 클릭 후 라우트가 404가 아닌지 코드로 확인.

**3단계** — dead-link 정적 분석을 PR/커밋 전 자동 실행. `href` 없는 `<a>`·`<Button>`, 클릭 핸들러 없는 클릭 가능 `<div>`를 코드 단에서 잡아낸다. pre-commit hook(#18)으로 박으면 사람이 잊어도 시스템이 잊지 않는다.

**4단계** — **자기 검증 금지** 강제. Task Agent와 Verification Agent를 다른 인스턴스(#13 편제 / #16 Agent Teams)로 분리. 같은 컨텍스트에서 자기 코드를 자기가 통과시키면 같은 사고가 재발한다.

**5단계** — 모바일·데스크탑 듀얼 검증. 데스크탑만 통과하고 모바일에서 깨지는 케이스가 본인 운용에서 두 번째로 흔한 사고. 두 해상도를 동시에 본다.

**6단계** — 사용자 여정 KPI 명시. 예시 — *"랜딩 페이지 주요 버튼 4개 이상 클릭 시 각각 올바른 라우트로 네비게이트"*, *"Lighthouse 80→95"*, *"E2E 12/12 통과"*, *"4초 내 실제 콘텐츠 렌더 (skeleton 고착 0건)"*.

## 자주 빠지는 함정

1. **헤드리스 모드만 신뢰 금지** — Playwright `headless: true`로만 돌리면 폰트 로딩·애니메이션·일부 JS가 데스크탑 브라우저와 다르게 동작. 본인 운용은 헤드리스 통과 후 한 번은 헤드풀 모드로 재검증.
2. **동적 로딩 대기 부족** — `page.goto` 직후 바로 스크린샷 찍으면 skeleton만 캡처. 반드시 4초 이상 대기 또는 `waitForSelector(핵심 요소)` 명시.
3. **자기 검증** — 코드 쓴 인스턴스가 자기 스크린샷 검증하면 *"잘 됐다고 본다"* 편향이 발생한다. 본인이 *"curl 200 ≠ 동작함"* 사고를 겪은 직접 원인.
4. **모바일 무시** — 데스크탑만 검증하고 모바일은 *"나중에"* 로 미루면 모바일 사용자가 첫 사용자가 될 때 사고 터진다.
5. **HTTP 200으로 끝** — *"HTTP 200 ≠ 동작함"*. 200이어도 페이지 자체가 빈 div + skeleton만 보여주는 경우 다수.
6. **dead-link 정적 분석을 PR 후로 미룸** — PR 머지 후 검출되면 이미 배포됐을 가능성. pre-commit이 정답.

## KPI

- **사용자 여정 KPI 통과율**: 100% (주요 버튼 N개 모두 올바른 라우트)
- **dead-link 검출 0건**: pre-commit hook 통과
- **데스크탑·모바일 듀얼 검증 통과**: 두 해상도 모두 Verified
- **Lighthouse 점수**: 본인 기준 90+ (Performance/Accessibility/SEO/Best Practices)
- **4초 내 실제 콘텐츠 렌더**: skeleton 고착 0건
- **5times-debug-loop 5회 이내 수렴**: 미수렴 시 사용자 에스컬레이션 (#28 비대칭 권한 원칙)

## 본인 운용 패턴

UI 산출물은 *예외 없이* 다른 인스턴스가 Playwright로 클릭 검증한 뒤에야 Verified로 닫는다. 본인이 한 작업을 본인이 통과시키는 순간 같은 사고가 다시 발생한다. 그래서 #13 편제 분대원 슬롯 1개를 *Verification 전담*으로 항상 비워둔다 — 비싸 보여도 무인 자동화의 가장 싼 보험이다.

본인 시그니처 결합 패턴:

- **미니 풀스택 5시간(#25)** — 5시간 안에 review-evaluate가 3번, 5times-debug가 5번 돌고, 그 5번의 5times-debug 중 절반 이상이 본 챕터의 Playwright 자율 검증으로 작동한다.
- **유튜브 1일 1영상(#26)** — 영상 자체에는 스크린샷 루프가 안 들어가지만, 영상 업로드 페이지·썸네일·랜딩 페이지 검증에 본 루프가 가동된다. 본 챕터 영상(#28의 QC 4종 소개)이 유튜브에 올라간 직후에도 동일 루프가 작동했다.
- **슬라이드쇼 배포(현재 챕터들이 배포되는 파이프라인)** — Vercel 배포 후 `https://sunny-ai-magic-50.vercel.app/` 의 50장 슬라이드 각각을 듀얼 해상도로 자동 캡처해 텍스트 잘림·이미지 깨짐을 잡는다.
- **QC 4종(#28)과 결합** — 본 루프는 5times-debug-loop의 핵심 메커니즘. 평가 3종이 *"얼마나 잘 됐나"* 를 묻는 동안 본 루프는 *"실제로 보이는가"* 를 묻는다.

dead-link 정적 분석은 pre-commit hook(#18)으로 박아두면 사람이 잊어도 시스템이 잊지 않는다. `href` 없는 `<a>`·`<Button>`, 클릭 핸들러 없는 클릭 가능 `<div>`만 잡아도 *"curl 200 ≠ 동작함"* 급 사고의 80%는 사전에 죽는다. 나머지 20%는 본 챕터의 Playwright 루프가 잡는다. 그 둘이 같이 작동해야 *"사람 눈 없이도 시각 결과물을 배포할 수 있는"* 자동화가 비로소 성립한다.
