# 20. 문서화는 나중에 하고 일단 만들어보고 테스트해보기

## 한 줄 정의

완벽한 기획·문서를 먼저 갖춰야 시작한다는 강박을 버리고 **빠른 프로토타입 + 즉시 테스트**로 가설을 검증한 뒤 문서화하는 실행 우선 원칙. **#34 Plan Mode와 충돌해 보이지만 작업 규모로 구분 운용한다.**

## 왜 이 노하우가 중요한가

AI 시대 이전엔 문서가 먼저였다. 한 번 잘못 만들면 되돌리는 비용이 컸기 때문이다. AI 시대엔 그 전제가 깨진다. **본인 4,000시간 경험상 프로토타입을 만드는 비용이 문서화 비용보다 낮다.**

#24 미니 풀스택 5시간 제작이 그 증거. 옛날 같으면 요구사항 명세서 1주일, 와이어프레임 3일, DB 설계서 2일을 거친 뒤에야 코딩 시작이었다. 지금은 Claude Code에 5분 설명하고 30분 안에 동작하는 페이지가 나온다. **만들고 보면 빠진 것·잘못된 것이 즉시 드러난다.** 그게 살아있는 명세서다.

문제는 이 원칙을 모든 작업에 적용하면 큰 작업에서 사고가 난다. 그래서 **#34 Plan Mode와의 구분 운용**이 필수다. 잘못 적용하면 SKILL_ATLAS 사고처럼 "curl 200으로 검증 끝" 같은 자기 검증 함정에 빠진다.

## 핵심 개념

**작업 규모별 분기 기준**

| 작업 규모 | 적용 원칙 | 도구 |
|-----------|-----------|------|
| 30분 이하·단일 파일 | **#20 즉시 실행** | Default Mode |
| 2시간 이하·단일 기능 | #20 + 끝나고 #4 Wiki 정리 | Default Mode |
| 5시간 이하·미니 풀스택 | #20 + #46 자율 검증 | Default + Hooks |
| 하루 이상·다중 모듈 | **#34 Plan Mode 필수** | Plan Mode |
| 주 단위·아키텍처급 | **#35 SAL Grid + #10 MBO** | Plan + MBO + SAL |

**#20과 #34가 충돌하지 않는 이유**:
- #20은 *"문서로 시간 낭비 말고 만들어"*
- #34는 *"위험 작업은 만들기 전에 계획부터"*
- 둘은 작업 규모 축에서 다른 구간을 담당. 같은 축의 양극단이 아니라 **상보 관계**.

**문서화의 3 시점**:
1. **사전 문서**(전통적 방식) — AI 시대엔 큰 작업에만
2. **실시간 문서**(코드·테스트·SAL Grid 좌표가 곧 문서) — 본인 표준
3. **사후 문서**(#4 Wiki에 회고로 정리) — 다음 작업 자산

## 실전 사용법

**1단계 — 작업 규모 자가 판정 (10초)**
"이 작업, 망쳐도 되돌릴 수 있나?" 답이 YES면 #20, NO면 #34.

**2단계 — #20 적용 시 최소 입력만**
- 목적 한 줄
- 입력·출력 한 줄씩
- 성공 기준 한 줄
이게 곧 #10 MBO의 미니 버전.

**3단계 — Claude Code에 던지고 즉시 실행**
HTML 페이지·작은 스크립트·데이터 처리 같은 작업은 30분 안에 v0가 나온다.

**4단계 — 즉시 테스트**
- 시각 결과물: 브라우저로 직접 클릭 (curl 200 ≠ 동작함)
- 데이터 작업: 출력 5건 샘플 직접 확인
- 스크립트: 실제 입력으로 한 번 돌려보기

**5단계 — 테스트 후에 문서**
이때 문서화는 #4 Wiki·#23 CLAUDE.md·#39 Slash Commands로 자산화. *"이 작업 다음에 또 할 거면 이 한 줄만 보면 됨"* 수준의 압축 메모.

**본인 운용 사례**: index_테스트버전.html 슬라이드 50장 작업도 명세서 없이 시작. v0 만들고 클릭 테스트하며 50장 채움. 작업 끝나고 수정계획서.md를 사후 정리. 사전 명세 작성 시간 0, 결과물 동일 품질.

**자주 빠지는 함정**:
- 큰 작업에 #20 적용해서 와이프 → **#34 Plan Mode 강제**
- 테스트 안 하고 "AI가 만들었으니 됐겠지" → **#46 자율 검증 + 사람 클릭 테스트 둘 다**
- 사후 문서 안 만들어 다음에 또 처음부터 → **#4 Wiki에 30초만 정리**

> Vault 사례: `ax-practical-project/wiki/2026_05_03_21.06_import_2026_04_12__07_24_PHASE_S9___99_.md` 는 BuzzLab S9 완성도 99점 달성을 12개 Phase로 사후 정리한 노트다 — *Phase 1: 코드베이스 탐색 → Phase 11: SAL Grid 전체 업데이트 + 완성도 재평가 → Phase 12: .env.example 전체 업데이트*. 본 항목 5단계 *"문서화는 나중에"* 의 실증으로, 명세서 없이 만들고 클릭하면서 채운 BuzzLab 145/148 Task가 끝난 다음에 *Phase 11의 재평가* 한 번에 누적 작업이 정리된다. 사전 문서가 아니라 *진행 중 체크박스 + 끝난 뒤 1회 audit*가 정답인 이유의 직접 사례.
