# 6. 작업결과물에 대해서 수시로 4종의 품질관리 스킬을 실행하여 완성도 높이기

## 한 줄 정의

본인이 직접 정의해 4,000시간 누적 운용으로 검증한 **4종 품질관리 스킬(QC) — `review-evaluate-코어1`(가벼움) · `pro-persona-debate-코어6`(중간) · `주작-sal-da`(무거움) 평가 3종 + `5times-debug-loop-코어3`(디버깅 1종)** — 을 산출물 무게에 맞춰 사다리식으로 갈아타며 완성도를 100점까지 끌어올리는 검증 운용 체계. **자기 칭찬이 아니라 자기 비판하게 시키는 운용** 이며, "Task Agent ≠ Verification Agent" 원칙을 4종 모두에 박아넣은 본인 시그니처 검증 패키지.

## 왜 이 노하우가 중요한가

AI 산출물의 가장 위험한 함정은 **"잘 돌아 보이는 거짓말"** 이다. SKILL_ATLAS S5 사건이 본인 4,000시간 누적의 가장 비싼 교훈으로 박혀 있다 — 배포 후 `curl 200` 으로 확인하고 Verified 처리했는데, 사용자가 실제 브라우저에서 보니 "시작하기"·"더 알아보기" 버튼은 href가 없어 무반응, 4개 은하 원은 `<div>` 라 클릭 불가, "View All"은 존재하지 않는 `/rankings` 로 404, 랭킹 카드는 `/skills/${uuid}` 경로·파라미터가 전부 틀린 상태. **HTTP 200 ≠ 동작함**. 글로벌 CLAUDE.md *"UI 검증 철칙"* 5개 조항이 이 사건에서 직접 도출됐다.

이 사고는 단일 검증 도구의 한계를 보여준다. *"문법은 맞는가"* 만 보면 *"의도대로 도는가"* 를 놓치고, *"의도대로 도는가"* 만 보면 *"이해관계자 다관점에서 타당한가"* 를 놓치고, *"다관점에서 타당한가"* 만 보면 *"실제 산출물이 사양·규정과 일치하는가"* 를 놓친다. 단일 도구로 모든 차원을 잡으려 하면 어느 차원이든 얕아진다. 매 차원마다 한 번씩 호되게 당하고 그 사고를 스킬로 박제한 결과가 4종 패키지다.

핵심 발상 두 가지. 첫째, **검증을 단일 도구가 아니라 무게별 사다리로 운용**한다. 가벼운 검증은 가볍게, 무거운 검증은 무겁게. 둘째, **검증자와 작업자를 물리적으로 분리**한다 — Task Agent ≠ Verification Agent. 4종 모두에 *"수정한 사람과 평가하는 사람을 분리하여 자기 평가 편향을 방지한다"*(`review-evaluate`)·*"Judge 평가 Subagent 분리(Self-Grading 폐쇄 루프 차단)"*(`pro-persona-debate` v1.1)·*"런타임 검증 없이는 진단 완료 선언 불가"*(`주작-sal-da` v4.0) 가 명문 규정으로 박혀 있다. 자기가 한 일을 자기가 검증하면 안 된다.

## 핵심 개념

### 4종 위계와 무게

| 스킬 | 무게 | 핵심 메커니즘 | 판정 기준 |
|------|:---:|--------------|---------|
| **`review-evaluate-코어1`** | 가벼움 | 검토→수정→평가 루프 (최대 10회) | 100/100 도달 |
| **`pro-persona-debate-코어6`** | 중간 | 3 전문가 + DA 5단계 토론 + Fix (최대 5 Cycle) | rubric 100/100 + 외부 게이트 |
| **`주작-sal-da`** | 무거움 | SAL Grid 역방향 + 20속성 진단~재진단 + 런타임 베이스라인 | 시스템 등급 + 리포트 품질 분리 |
| **`5times-debug-loop-코어3`** | 단발 (계층 외부) | 분석→수정→검증 5회 + Playwright 자동 | 버그 해결 / 5회 소진 |

3종 평가 스킬은 **위계 사다리** 다. 단순 코드·문서면 1번, 다관점 판단이 필요한 사업·특허·UX는 2번, 규정 준수·법률·구조화 산출물은 3번. 디버깅 1종은 사다리 외부 — 명확한 단일 버그 박살용으로 어느 평가 스킬이든 위임할 수 있다 (`review-evaluate` Phase 2 *"명시적 증상 → /5times-debug-loop 위임"*).

### 자기 비판 운용 (가장 중요한 한 가지)

종합정리 #6의 한 줄 — *"스스로 비판시키기(약점·빠진 것·반박점 찾아내기)가 4종 검증에 반영되도록"* — 이 운용의 본인 시그니처다. 디폴트로 두면 AI는 *"잘 돌아갑니다"* 라는 칭찬을 흘리게 되어 있다. 4종 모두에 비판 메커니즘이 강제 내장돼 있다.

- **review-evaluate**: Cross Validator가 *"리뷰어가 놓친 문제점"* 섹션을 의무 작성.
- **pro-persona-debate**: DA(Devil's Advocate) 가 4번째 페르소나로 강제 투입. v1.1에서 *"BPI 공식에 DA_penalty 항 추가 — DA 무력화 결함 보정"*.
- **주작-sal-da**: Pending Critical 1건이라도 있으면 진단 완료 선언 불가. *"Pending Critical ≠ Acceptable"*(v4.0).
- **5times-debug-loop**: Playwright 스크린샷이 사람 눈을 대신해 *"실제로 안 되는 부분"* 을 자기 검증.

### review-evaluate-코어1 — 100점 ABSOLUTE RULE

5기준 루브릭(문법·실행 / 보안 / 코드품질 / 테스트 / 완성도) + 사양 충족률 25점 = 100점. **Round < 10 AND 점수 < 100 → 다음 라운드 강제 진입.** 95점·97점·99점이라도 임의 종료 금지. SKILL.md 명문: *"2026-05-03 김부겸 보고서 사건 — Round 2에서 97점 받고 ' 배포 가능 수준' 권고에 동조하여 임의 종료. 사용자가 '100점이 안 났는데 중단했냐'고 지적해야만 Round 3 재개되어 100점 달성. 이 경험을 ABSOLUTE RULE로 격상."*

또 하나의 보완 — **Phase 1.5 사양-구현 대조**. *"코드가 잘 돌아가는가"* 와 *"코드가 사양대로 돌아가는가"* 를 분리해 사양 충족률 25점을 별도 채점. 사양 동떨어지면 75점 상한. 2026-03-26 *"100점을 줬는데 인스트럭션-스크립트 간 근본 격차를 못 잡았다"* 사고의 직접 교훈.

### pro-persona-debate-코어6 — 같은 도메인 3 전문가 + DA

같은 도메인 동료 3명 + DA 1명 = 4 페르소나. 5단계 토론(S1 입장 → S2 반박 → S3 종합 → S4 합의 → S5 Fix). 절대 규칙: *"4 페르소나 발언은 반드시 4개의 Subagent(Agent tool) 호출로 생성한다. '비용 합리화', '시뮬레이션 모드', '소대장 모드'라는 명목으로 SA가 직접 작문하면 해당 Cycle은 무효."* — 가장 흔한 우회를 차단한 조항.

종료 조건은 **rubric 100점 + 외부 게이트 통과**. v1.2에 외부 게이트 신설 — *"rubric_score 100 ≠ 출원/배포/실행 보증."* 도메인별 외부 표준(KIPO·빌드·접근성·재무 일관성) 검증 강제. v1.3에는 *"의미 일관성 게이트(Semantic Coherence Gate)"* — DID 특허 v2.0 사례에서 *"명칭='데이터 처리·정보 산출·의사결정 지원', 요약서='데이터 통합 진단(Diagnosis)' 모순. rubric 100/100인데도 미검출"* 사고를 보완.

### 주작-sal-da — SAL Grid 역방향 + 런타임 우선

본인 SAL Grid(#35)의 **역방향 적용**. 기존 산출물을 S0에서 분해해 SAL ID를 부여하고, S1~SN Stage 루프에서 카드별 *"진단→개선안→개선→재진단"* 을 완결한다. v4.0의 보완 두 가지.

- **런타임 우선** — 정적 분석만으로 진단 완료 선언 불가. 소프트웨어 트랙은 P0 런타임 베이스라인(build·serve·smoke·schema↔쿼리 대조·env) 선행 필수. 런타임 실패 1건이라도 있으면 **시스템 등급 상한 3/10, 리포트 품질 상한 60/100 강제 캡**.
- **두 점수 분리** — *"시스템 등급(실제 산출물 품질)과 리포트 품질(진단 문서의 완성도)은 절대 한 숫자로 섞지 않는다."* 두 숫자 분리 표기 의무.

20속성 6그룹(식별→진단기준→진단결과→개선안→개선실행→재진단)이 SAL Grid의 22속성과 짝을 이룬다. 동일 좌표계, 다른 방향. 개발(#35) ↔ 감사(주작) 가 한 쌍.

### 5times-debug-loop — 시각 결과물의 자동 검증

*"분석 → 수정 → 검증"* 5회 반복. 시각 결과물은 Playwright 스크린샷 자동 촬영(1440×900 + 모바일 390×844) → Read tool로 PNG 분석. 코드·빌드는 `npm run build` / `npx tsc --noEmit` / `npm test` 자동 실행. **사람의 눈을 대신해 AI가 자기 결과물을 본다** — 이게 #46 *"스스로 스크린샷 찍어서 문제점 찾아 스스로 수정하기"* 의 실체다. *"review-evaluate가 '점수 매기는 도구', 5times-debug가 '박살내는 도구'."*

### 4종을 가로지르는 헌법 5조항

본인 글로벌 CLAUDE.md *"UI 검증 철칙"* 이 4종 모두를 관통한다. ① curl 200 → Verified 금지 ② 배포 후 첫 액션은 직접 클릭 ③ KPI에 사용자 여정 지표 포함 ④ href 없는 버튼·`<div>` 클릭은 버그 ⑤ 자기 검증 금지. 4종 매핑 — review-evaluate Cross Validator(⑤), pro-persona-debate Judge Subagent 분리(⑤), 주작 P0 런타임(①②③), 5times-debug Playwright 자동(①②④). **헌법 5조항 → 스킬 4종 → 운용**. 분리할 수 없는 한 덩어리.

## 실전 사용법

### 1단계 — 산출물 무게 진단으로 스킬 선택

| 산출물 | 권장 스킬 |
|--------|---------|
| 단일 함수·짧은 스크립트 | `review-evaluate` |
| 미니 풀스택(#24) | `review-evaluate` + `5times-debug-loop` |
| 사업 기획서·제안서 | `pro-persona-debate` |
| 특허 명세서 | `pro-persona-debate` + 외부 게이트(KIPO) |
| 대규모 시스템 감사 | `주작-sal-da` |
| 한국 공공 양식(#29) | `pro-persona-debate` + `주작-sal-da` |
| 명확한 단일 버그 | `5times-debug-loop` |

판단이 흐릿하면 가벼운 쪽부터 — review-evaluate 100점 → pro-persona-debate rubric 100점 → 필요 시 주작. 무거운 쪽부터 시작하면 시간이 폭주한다.

### 2단계 — review-evaluate 운용

`/review-evaluate` 호출 → 파일 타입 자동 분류(Code/Document/Report) → 3개 이상이면 풀 서브에이전트 투입(타입별 Reviewer + Cross Validator) → Round 1~10. 100점 미달 임의 종료 금지가 ABSOLUTE RULE. 라운드 중 빌드·테스트 실패는 즉시 `/5times-debug-loop` 위임.

### 3단계 — pro-persona-debate 운용

`/pro-persona-debate <대상>` → 도메인 식별 → 3 페르소나 + DA 캐스팅 → S1~S5 토론 → rubric 채점 → Fix → 외부 게이트. **Cycle 1마다 4개 Agent tool 호출 증거가 보고에 반드시 표시**. 호출 증거 없으면 SA 직접 작문 의심 — 해당 Cycle 무효 + 재실행.

### 4단계 — 주작-sal-da 운용

소프트웨어 트랙이면 `/software-diagnosis-sal-da` 로 4 PART 실행. **PART 0 런타임 베이스라인 절대 건너뛰지 말 것** — 정적 분석만 한 진단은 v4.0 정의상 *"진단 완료"* 가 아니다. S0에서 SAL Grid 역방향 분해, S1~SN에서 카드별 진단~재진단. Stage Gate에서 Pending Critical/High 1건이라도 있으면 차단.

### 5단계 — 5times-debug-loop 단독 호출

빠른 박살이 필요할 때. *"문제: A / 파일: B / 검증방법: C"* 3줄 호출. 시각 결과물이면 Playwright가 자동 스크린샷. 사용자 *"OK"* 또는 5회 소진 시 종료. 미해결이면 잔여 이슈 보고 → 평가 스킬로 회귀.

### 6단계 — 사다리식 갈아타기 (실제 운용)

본인 운용: 미니 풀스택(#24) → review-evaluate Round 3에서 97점 정체 → 사양 충족률 GAP 발견 → 빌드 오류는 `/5times-debug-loop` 위임 → 해결 후 review-evaluate Round 4 재개 → 100점. 한 작업에 평가 1종 + 디버깅 1종이 짝으로 돈다. 사업 기획이 섞이면 추가로 pro-persona-debate. **가볍게 여러 번 갈아탄다.**

### 7단계 — Hooks로 헌법 5조항 1차 방어선

`href` 없는 버튼·`<div>` 클릭·존재하지 않는 라우트·자기 검증 — 4가지를 정적 분석 항목으로 박아 settings.json hooks(#38) PreToolUse·PostToolUse에 건다. 4종은 **2차 방어선**, 헌법 5조항이 1차.

## 본인 운용 패턴

4종 스킬을 단발성 도구가 아니라 **검증 운영체제** 로 본다. 가장 큰 인지 전환은 *"검증은 작업 끝에 한 번"* 에서 *"검증은 작업과 동시 진행되는 별개의 운영 트랙"* 으로 넘어간 순간이었다. *"검증을 미루면 검증 자체가 사라진다"* 가 4,000시간에서 가장 비싸게 산 교훈. 미니 풀스택 5시간 작업이라면 5시간 안에 review-evaluate가 3번, 5times-debug가 5번 돌아간다. 작업과 검증이 같은 시간선을 공유한다.

또 하나 — 4종은 **본인 특허 SAL Grid(#35)와 한 덩어리**다. SAL Grid Stage Gate(§8.2)의 5단계 리포트 — 누락 점검 → 정합성 체크 → AI 자동 검증 → Stage Gate 리포트 → PO 승인 — 의 *"AI 자동 검증"* 단계가 4종으로 채워진다. MBO와도 결합 — Stage 진입 전 MBO 목표 제시 → 자율 실행 → 4종 검증 → Stage Gate. 4종이 없으면 Stage Gate가 빈 껍데기다. 본인 ax-on.net `claude-code-guide.html` 7,758줄의 QC 영역 6셀에도 그대로 매핑되어 학습 콘텐츠로 재이식 — *"본인이 만들고, 본인이 쓰고, 본인이 가르친다"*.
