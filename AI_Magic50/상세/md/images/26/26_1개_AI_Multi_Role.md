# 26. 1개의 AI에게 Multi Role로 작업시키기

## 한 줄 정의

한 개 Claude Code 인스턴스 안에서 **여러 역할(전문가·검토자·악마의 변호사 등)을 동시 부여**해 다관점 검토를 단일 컨텍스트에 압축하는 기법. **#9 다중 인스턴스(가로 확장)와 짝을 이루는 단일 인스턴스 세로 확장**.

## 왜 이 노하우가 중요한가

본인 30개 동시 운용을 권하지만, 모든 작업을 30개로 풀 필요는 없다. **작은 작업은 1개 인스턴스 안에서 다역할로 충분**하고, 그게 더 빠르다. 30개 운용은 인프라·전기·라이센스 비용이 따라온다.

#26은 이 비용·복잡도 없이 *"한 인스턴스, 여러 모자"* 방식으로 다관점 검토를 얻는다. 본인 4,000시간에서 가장 자주 쓰는 일상 패턴이 사실 #26이다.

#9 군대 소대 편제와의 차이가 핵심이다.

## 핵심 개념

**#9 vs #26 비교**

| 축 | #9 다중 인스턴스 | #26 단일 다역할 |
|----|------------------|-----------------|
| 컨텍스트 | 인스턴스별 독립 | 단일 컨텍스트 공유 |
| 비용 | 인스턴스 × 토큰 | 1 × 토큰 |
| 속도 | 병렬 (빠름) | 순차 (느림) |
| 적용 | 큰 작업·다영역 | 작은 작업·단일 영역 |
| 도구 | Subagent / Agent Teams | Persona 프롬프트 |
| 대표 스킬 | `백호-platoon-formation` | `pro-persona-debate-코어6` |

**Multi Role 3 패턴**:

1. **순차 페르소나 토론** — 전문가A 발언 → 전문가B 반박 → DA 약점 지적 → 합의안. `pro-persona-debate-코어6` 5단계 토론.

2. **역할 스위칭** — 한 작업 안에서 *"지금은 작성자, 다음 턴은 검토자"* 식. 본인은 본 시리즈 본문 작성에서 활용.

3. **다중 모자 동시 출력** — 한 응답 안에 [개발자 관점] [PM 관점] [사용자 관점] 셋을 분리 출력.

**Devil's Advocate 필수**: #13에서도 강조되듯, 약점만 찾는 역할이 없으면 Multi Role도 합창단이 된다.

## 실전 사용법

**1단계 — 역할 정의 명확히**
*"3 역할로 진행: 시니어 개발자(보안·성능), 디자이너(UX), 사용자(초심자). + Devil's Advocate(약점 전담)."*

**2단계 — 출력 포맷 강제**
```
[개발자] ...
[디자이너] ...
[사용자] ...
[DA] (약점) ...
[합의] ...
```

**3단계 — 토론 라운드 지정**
*"3라운드 진행. 각 라운드 후 합의 가능 여부 판단."*

**4단계 — 합의 불가 시 #9로 격상**
한 컨텍스트 안에서 결론이 안 나면 인스턴스를 분리해 #9 다중 인스턴스로 격상. 이게 #26과 #9의 게이트.

**5단계 — 합의안에 #21 창발 신호 적용**
토론 중 *"흥미로운 점은..."* 같은 표현 캡처. Multi Role 토론은 창발 빈도가 가장 높은 환경 중 하나.

**적용 사례**:

- **본 시리즈 본문 검토**: [작성자] 초안 → [편집자] 톤·구조 → [DA] 약점 → 수정안. 1 인스턴스, 1 컨텍스트.
- **특허 청구항 검토** (#7): [발명자][심사관][경쟁사 변리사][DA] 4 역할.
- **#13 페르소나 토론** 자체가 #26의 표준 구현. `pro-persona-debate-코어6`이 곧 #26 자산화.

**자주 빠지는 함정**:
- DA 빠뜨리기 → 모든 역할이 *"좋네요"* 합창
- 큰 작업에 #26 적용 → 컨텍스트 폭주, **#9로 격상해야**
- 역할 정의 모호 → 결과 차별성 사라짐

**언제 #26 vs #9**:
- 결과물 1,000자 이하 → #26
- 결과물 5,000자 이상·다영역 → #9
- 30개 운용 환경 평상시 → #26 우선, 필요 시 #9
