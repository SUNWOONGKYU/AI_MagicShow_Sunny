# 13. 3개 이상의 분야별 전문가 페르소나 AI가 참여해서 토론하여 방안 제시하게 하기

## 한 줄 정의

같은 도메인의 **전문가 페르소나 3명 + Devil's Advocate 1명**(필수)이 단일 LLM에서 **5단계 토론(S1~S5)**을 진행하고, **rubric_score 100점**에 도달할 때까지 산출물을 수정하며 최대 5 Cycle 반복하는 — 다관점 검토 강제 노하우. AI에게 "잘 검토해 줘"가 아니라 *"네 명이 토론하고 합의 도달까지 못 끝낸다"* 는 절차로 박는 방식이다.

## 왜 이 노하우가 중요한가

본인이 4,000시간 누적에서 가장 자주 범했던 실수는 *"AI에게 검토를 맡기면 검토 받은 기분만 들고 실제로는 자기 칭찬"* 이라는 것이다. 단일 AI에게 *"이 기획서 검토해 줘"* 라고 시키면 95% 확률로 *"좋은 기획입니다. 다만 N개 보완할 점이 있습니다"* 식의 안전한 응답이 나온다. 약점은 표면만 건드리고 진짜 치명적 결함은 놓친다 — AI 자신이 *"좋은 답변을 주려는 본능"* 으로 학습되어 있기 때문.

이 한계를 깨는 유일한 방법은 **구조적으로 비판자를 박는 것**이다. AI에게 *"비판해 줘"* 라고 부탁하는 게 아니라, *"비판이 직무인 페르소나"* 를 세우고 그 페르소나가 반론을 *N건 의무 제출*하게 강제한다. 이게 Devil's Advocate(DA)이고, pro-persona-debate-코어6 스킬의 핵심 장치다.

또 하나의 함정 — 페르소나가 1명이면 그 한 명의 시각으로 편향된다. 페르소나 3명을 **다른 축**으로 캐스팅(세부 전문성 / 경력 단계 / 활동 환경)하면 한 산출물을 세 시점에서 동시에 본다. 본인이 SAL Grid 특허출원서 초안을 작성할 때 이 방식으로 *"청구항 변호사 / 명세서 작성 전문가 / 분쟁 실전가"* 3명을 캐스팅했고, 그중 분쟁 실전가만 잡아낸 *"청구항 1의 권리 범위가 너무 좁다"* 는 결함이 결정적이었다. 다른 두 명은 표현·구조만 보고 있었다.

마지막 함정은 *"100점 받았다고 끝난 게 아니다"* 라는 점. SKILL_ATLAS 사건이 이 교훈을 박았다 — *"curl 200 OK"* 받고 Verified 처리했지만 사용자가 브라우저에서 보니 버튼 4개 모두 무반응. 이 사건 이후 **외부 게이트**(External Gate)가 종료 조건에 추가됐다. rubric_score 100 + 외부 표준 통과 둘 다 있어야 진짜 끝.

## 핵심 개념

### 4 페르소나 구성 — DA 필수

| 슬롯 | 역할 | Stance | 비고 |
|------|------|--------|------|
| **E1** | 전문가 1 | ±값 | 캐스팅 축 1번 시점 |
| **E2** | 전문가 2 | ±값 | 캐스팅 축 2번 시점 |
| **E3** | 전문가 3 | ±값 | 캐스팅 축 3번 시점 |
| **DA** | Devil's Advocate | **0.0 고정** | **필수, 검증 전담** |

DA가 Stance 0.0인 이유 — 찬성도 반대도 아닌 **검증자 위치**에 머물러야 3 전문가의 가정·맹점을 객관 비판할 수 있다. DA가 Stance를 가지면 그것 자체가 또 다른 편향이 된다.

### 캐스팅 축 3가지

| 축 | 적용 도메인 |
|---|---|
| 세부 전문성 | 백엔드/프론트/AI/UX/마케팅 — 강점 영역 다른 3명 |
| 경력 단계 | 사업계획서·전략 — 시드/시리즈A/CFO 등 단계 다른 3명 |
| 활동 환경 | 특허·법무·정부지원사업 — 대기업/부띠끄/분쟁실전 등 환경 다른 3명 |

도메인에 따라 축이 달라진다. 특허는 활동 환경 축, 사업계획서는 경력 단계 축, 코드는 세부 전문성 축이 가장 잘 맞는다. 본인 경험상 잘못된 축으로 캐스팅하면 3명이 같은 말을 하고 토론이 죽는다.

### 5단계 토론 (S1 → S5)

| Stage | 이름 | 핵심 |
|-------|------|------|
| **S1** | 독립 발언 (L1→L2→L3) | Kahneman System 1/2/메타인지 — 격리 상태 발언 |
| **S2** | 교차 토론 + 할루시네이션 검출 | 페르소나 간 상호 논박, FACT/DOUBT/FALSE 판정 |
| **S3** | DA 사실확인 질의 | 미검증 가정 3분류(자체 확인/외부 확인 필요/본질 불확실) |
| **S4** | DA 정식 반론 | **반론 3가지 이상 의무**, ③+②부정 항목 대상 |
| **S5** | 반론 토론 + 수렴 판정 | 페르소나 반론 대응, 3조건(ΔStance·Confidence·신규논거) 수렴 판정 |

S1의 L1·L2·L3 분리는 Kahneman *Thinking, Fast and Slow* 의 직관/분석/메타인지를 그대로 옮긴 것. 직관 발언과 분석 발언을 분리해서 받아내야 *"왜 그렇게 생각하는가"* 의 근거가 누락 없이 드러난다.

### rubric_score vs BPI (혼동 주의)

| 지표 | 측정 대상 | 범위 | 역할 |
|---|---|---|---|
| `rubric_score` | 산출물의 절대 품질 | 0~100 | **Fix 루프 종료 조건** |
| `BPI` | 페르소나 stance 가중평균 | -100~+100 | 보조 지표 (방향성) |
| `quality_i` | 발언 논증력 | 0~1 | BPI 가중치 |

본인이 자주 헷갈렸던 것 — *"100점 받았는데 BPI는 -30이네?"* 같은 상황. 이건 *"산출물 자체는 100점 품질이지만, 페르소나들의 종합 평가 방향성은 부정적"* 이라는 뜻. 둘은 차원이 다르다.

### Fix 루프 — 최대 5 Cycle

```
┌──────────────────────────────────────┐
│  Cycle N (최대 5):                   │
│   1. S1~S5 1라운드                   │
│   2. Judge Subagent 평가             │
│   3. BPI + rubric_score 산출         │
│   4. rubric_score < 100 → Fix → N+1  │
│                                      │
│  종료:                               │
│   - rubric_score 100 → 정식 종료     │
│   - Cycle 5 → 강제 종료              │
│   - 연속 수정 0건 2회 → 자동 종료    │
└──────────────────────────────────────┘
```

**1 Cycle = S1~S5 1라운드 + Fix 1회 + 점수 산출 1회.** *"Cycle 3 v2"* 같은 sub-iteration 금지(점수 인플레이션 방지).

### Self-Grading 차단 — Judge Subagent 분리

이 스킬의 가장 정교한 장치. 토론 진행자(SA)가 채점까지 하면 *자기 토론을 자기가 채점*하는 폐쇄 루프가 된다 — Cycle별 점수가 단조 증가(인플레이션). 이를 막기 위해 **Judge는 별도 Subagent**로 분리하고 페르소나 시트를 안 준다(편향 차단). 본인이 이 차이를 직접 본 적이 있다 — Judge 분리 전에는 Cycle 3에서 95점, Cycle 4에서 98점, Cycle 5에서 100점 식으로 매끄럽게 올라갔다. 분리 후에는 Cycle 3에서 87점 받고 Cycle 4에서 84점으로 떨어진 적도 있다. 후자가 정직한 평가다.

### 외부 게이트 (Phase 5.5, V1.2 추가)

rubric_score 100 ≠ 출원/배포/실행 보증. 도메인별 외부 표준을 별도 게이트로 검증한다.

| 도메인 | 게이트 예시 |
|---|---|
| 특허 (KIPO) | 청구항 다중종속 검사, 도면-청구항 부호 매칭, 요약서 길이 200~600자 |
| 코드 | tsc/mypy 통과, eslint error 0건, semgrep high 0건 |
| 사업계획서 | 매출-원가-이익 산식 일치, 일자 일관성, 단위 통일 |
| UX | axe-core 0건, WCAG AA 4.5:1, **Playwright 클릭 테스트 100%** |

UX 도메인의 Playwright 클릭 테스트가 **CLAUDE.md UI 검증 철칙**의 직접 적용. *"curl 200 ≠ 동작함"* 은 페르소나 100점도 무력화한다 — 외부 게이트가 마지막 방어선.

## 실전 사용법

### 1단계 — `/pro-persona-debate [대상]`

대상 = 파일·폴더·주제 자연어 모두 가능. 인자 없이 호출하면 git status·최근 수정 파일·이전 실행 이후 변경분에서 자동 탐지 후 PO 확인. 본인은 거의 *"방금 작성한 기획서 비판해 봐"* 식 자연어로 호출한다.

### 2단계 — 도메인 식별 + 페르소나 캐스팅

SA가 대상 분석 → 도메인 식별(코드·문서·사업·특허·UX) → 캐스팅 축 결정 → 페르소나 3명 + DA 1명 시트 생성(BuzzLab 6요소). 이 단계에서 PO 승인 필수. *"이 캐스팅으로 진행하시겠습니까?"* 에 답이 와야 토론 시작.

### 3단계 — 루브릭 + 외부 게이트 결정

100점 만점 도메인 루브릭 + 외부 게이트 후보를 함께 PO에게 제시 → 승인. 루브릭 항목은 4~6개로 분배(목적 충족도/품질/리스크/차별성/실행성/표현력 중 도메인 우선순위에 맞게). 외부 게이트는 도메인 카탈로그(`external-gates.md`)에서 선택.

### 4단계 — Cycle 루프 (최대 5)

각 Cycle에서 S1~S5 진행. **4 페르소나 발언은 반드시 4개의 Subagent(Agent tool) 호출**로 생성한다. SA가 *"이 페르소나라면 이렇게 말할 것이다"* 라고 직접 작문하면 해당 Cycle 무효 + HALT + PO 보고. 이게 가장 강한 절대 규칙이다.

### 5단계 — Fix 적용 + grep 검증

Cycle 종료 시 rubric_score < 100이면 산출물 수정. 모든 Fix는 Edit 직후 grep으로 본문 반영 여부를 직접 검증해야 한다(`5_fixes/c{N}_verification.json` 기록). 미검증 Fix는 무효 — 과거 *"Fix 완료 기록은 있으나 본문 미적용"* 사건 이후 강제된 규칙.

### 6단계 — 외부 게이트 실행

rubric_score 100 도달 직후 또는 Cycle 5 종료 시 외부 게이트 실행. **반드시 외부 도구 또는 별도 Gate Subagent**로 검증(SA·페르소나·Judge 자가평가 금지). 게이트 실패 시 Case A(Fix 가능)·Case B(본질 충돌, PO 결정)·Case C(Cycle 5 후 게이트 실패, 보고 후 종료) 중 하나로 분기.

### 7단계 — 최종 보고 + 다음 액션

`6_final/result.json` + `report.md` 저장 후 PO에게 다음 액션 묻기 — ① 종료 ② `/주작-sal-da` 실측 검증 추가 ③ `/review-evaluate` 문서 정리 추가. 자동 체이닝 금지, PO 명시 응답 후만 진입.

## 본인 운용 패턴

비표준·창의적 산출물은 거의 모두 이 스킬을 거친다. 사업계획서·특허출원서·아키텍처 결정서 — *"한 번 더 비판받고 싶다"* 라는 직감이 들면 호출. 단순 코드 수정·문서 포맷팅은 review-evaluate-코어1(가벼운 평가)로 충분하지 이 스킬은 무겁다.

가장 자주 마주치는 시나리오는 *"DA가 잡아낸 1건이 결정적"* 이다. E1·E2·E3가 만장일치 100점을 줘도 DA의 반론 한 건이 *"이 산출물의 핵심 가정이 틀렸다"* 를 짚으면 그 한 건 때문에 Cycle 추가 → 산출물 방향 변경. *"AI 3명이 좋다고 해도 1명의 비판이 옳을 수 있다"* — 이게 이 스킬의 본질이며 지구상 거의 유일한 *"AI에게 비판을 시키는"* 메커니즘이다. AI가 틀릴 수 있다는 사실(#21)을 인정하는 데서 출발한다.

미달성 종료 — Cycle 5 도달했는데 rubric_score 87점에 머물렀다면, 그것 자체가 가치 있는 보고다. *"이 산출물에는 13점만큼의 본질적 약점이 있고 그 약점은 N Cycle로도 해소되지 않았다"* 는 정직한 결론. 본인 누적에서 가장 많이 배운 산출물은 87점에서 멈춘 것들이었다.

BPI(BuzzLab Prediction Index)는 4요소 가중 집계(4계층 지휘구조와 변수 산출 주체 / 7-Phase 산출 파이프라인) 위에 Devil's Advocate 에이전트의 기여를 별도 항으로 박아 놓았고, 그 점수를 Logistic Calibration(시그모이드·동적 k값)으로 확률로 변환한다. 본 항목 §외부 게이트(Phase 5.5)에서 *"rubric_score 100 ≠ 출원/배포 보증"* 이라고 한 그 한 줄의 산식적 보강이 두 노트에 들어 있다 — 점수 100점이 곧장 합리적 의사결정으로 이어지지 않는 이유는 *"4요소 분포·DA 가중·확률 변환 곡선"* 까지 봐야 하기 때문이다.
