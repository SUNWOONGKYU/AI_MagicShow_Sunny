# 3. 아젠다별로 AI에게 하나씩 설명듣고 승인하기

## 한 줄 정의

큰 작업을 한 번에 AI에 던지지 않고 **아젠다 단위로 쪼개**, 매 아젠다마다 AI 설명을 듣고 사용자가 명시적으로 승인한 뒤에야 다음으로 넘어가는 통제형 진행 방식.

## 왜 이 노하우가 중요한가

*"전체를 알아서 해줘"* 는 4,000시간 운용 결과 가장 비싼 패턴이다. AI는 막힌 부분을 추측으로 메우고, 사용자는 결과물을 본 다음에야 *"이건 내 의도가 아니었네"* 라고 한다. 그 시점엔 이미 토큰·시간이 다 태워졌다. 반대로 아젠다별 승인은 **사고-실행 사이의 게이트**를 명시적으로 박아 둔다. AI가 *"이 아젠다에서 이렇게 하려고 합니다"* → 사용자 승인 → 실행 → 결과 보고 → 다음 아젠다. *"curl 200 ≠ 동작함"* 의 사고를 작업 단위마다 적용한 것이다. SAL Grid의 Stage Gate·MBO의 PO 승인이 이 패턴의 공식화다.

## 핵심 개념

아젠다 승인 = **MBO Stage Gate의 일상화**.

```
[큰 작업] → 아젠다1 (설명) → [승인?] → 실행 → 결과
                                           ↓
                       아젠다2 (설명) → [승인?] → 실행 → 결과
                                           ↓
                               ...반복
```

| 게이트 단계 | AI 행동 | 사용자 행동 |
|-------------|---------|-------------|
| 설명 | "이 아젠다 목표·방법·예상 산출물·리스크" | 듣기 |
| 승인 요청 | "진행해도 됩니까?" | "Yes" / 수정 / Skip |
| 실행 | 승인된 내용만 | 모니터링 |
| 결과 보고 | 산출물 + KPI | 검수 후 다음 아젠다 |

핵심 규칙: **AI가 승인 요청을 빠뜨리면 즉시 회수**. *"방금 승인 안 받았다, 다시"* 라고 한다. 글로벌 헌법의 *"MBO 승인 없이 Task status 전이 금지"* 와 같은 기제다.

## 실전 사용법

**기본 프롬프트**:
```
지금부터 [작업]을 아젠다별 진행 방식으로 한다.
규칙 1: 아젠다 목록 먼저 5~9개 제시.
규칙 2: 매 아젠다마다 [목표/방법/산출물/리스크] 설명 후 "진행 승인?" 묻기.
규칙 3: 내가 "Yes"라고 하기 전 어떤 파일도 수정 금지.
규칙 4: 아젠다 끝날 때마다 [완료 산출물 + KPI] 보고 후 다음 진행.
```

**본인 운용 패턴**: 글로벌 헌법의 *"멀티 페이즈 작업 행동 규칙"* 그대로 — PHASE 파일을 미리 만들어 아젠다 = Phase로 매핑. *"Phase 완료 즉시 `[ ]` → `[x]` 표시"* 가 곧 승인 기록. **`scripts/task-guard.js`(Tier 3)** 가 이 흐름을 물리적으로 강제하는 SAL Grid 환경에선 AI가 무단 진입조차 못 한다.

**KPI**: 아젠다당 평균 토큰 < 단일 통합 실행의 60%, 사용자 *"내 의도와 다름"* 발생률 0%, 마지막 아젠다 KPI 통과율 100%.
