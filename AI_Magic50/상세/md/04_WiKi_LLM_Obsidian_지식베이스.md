# 4. WiKi_LLM과 Obsidian을 활용한 지식베이스 관리하기

## 한 줄 정의

본인이 4,000시간 동안 쌓은 노하우·검색 결과·세션 기록·특허 자료·스킬 정의를 **Obsidian Vault라는 단일 외부 저장소**에 누적시키고, 그 위에 얹은 **WiKi_LLM(MCP·recall·검색 인덱스의 통합 호칭)** 을 통해 30개 동시 운용 중인 어느 Claude Code 인스턴스에서든 동일 지식을 끌어다 쓰게 만드는 AI 운용의 장기 메모리 인프라.

## 왜 이 노하우가 중요한가

Claude Code의 컨텍스트 윈도우는 길어야 200K 토큰이고, `/compact` 한 번 돌면 그 안의 결정·근거·시행착오가 **압축 손실**을 동반해 사라진다. 30개 인스턴스를 동시 운용하면 이 손실은 30배가 된다 — 본인이 화요일에 A 인스턴스에서 결정한 내용이 목요일 B 인스턴스에서 정반대로 결정되는 사고가 4,000시간 누적 동안 한두 번이 아니었다. 단일 세션을 잘 관리하는 능력(#30 컨텍스트 관리)은 단발성 기억을 다루는 기술이고, 이 항목은 **세션 너머의 기억**을 다루는 인프라다.

기존 도구들 — 메모장·노션·구글독스·VS Code 폴더 — 은 모두 세 가지 한계를 공유한다. 첫째, **AI가 직접 읽지 못한다**. 사람이 복붙해서 컨텍스트에 넣어줘야 한다. 둘째, **링크 그래프가 끊겨 있다**. "이 결정이 어느 결정에서 파생됐는가" 가 보이지 않는다. 셋째, **검색이 키워드 매칭**이라 의미적으로 연결된 과거 기록을 못 찾는다. "그거 저번에 했던 거" 라는 말로 사용자가 가리키는 항목을 본인이 일일이 찾아줘야 한다.

Obsidian + WiKi_LLM 조합은 이 셋을 동시에 해결한다. Obsidian은 마크다운 파일 + 양방향 링크 + 그래프 뷰로 **사람이 보기 좋은 인덱스**를 제공하고, WiKi_LLM 레이어(recall MCP·검색 인덱스·자동 메모리 파일)는 **AI가 보기 좋은 인덱스**를 제공한다. 같은 Vault, 다른 두 진입점. 본인 글로벌 CLAUDE.md에 박혀 있는 *"recall 사용 지침"* — *"recall.search → recall.expand 2단계로 호출. '기억이 없습니다'는 recall.search를 먼저 해보고 나서 말한다. 검색 결과는 응답에 자연스럽게 녹인다."* — 가 이 인프라의 운영 규칙이다.

이 인프라가 있으면 30개 인스턴스가 같은 기억을 공유한다. 이 인프라가 없으면 30개가 서로 다른 30개의 단기 기억으로 흩어진다. 본인이 인스턴스를 늘려도 무너지지 않은 단 하나의 이유는 컴퓨터 5대도 아니고 모델 선택도 아니고, **Vault라는 외부 두뇌 하나를 모두가 공유하기 때문**이다.

## 핵심 개념

### Obsidian Vault — 본인 운용 구조

본인 Vault 루트는 `G:\내 드라이브\Claude-Wiki\` 다. 구글 드라이브 동기화 폴더 안에 두는 이유는 PC 5대 어디서 켜도 동일 상태가 유지되고, 모바일에서 원격 데스크탑으로 접속할 때(#5)도 같은 Vault가 보이기 때문이다. C드라이브 + G드라이브 백업(#36) 원칙의 적용 사례이기도 하다.

Vault 안의 1차 분류는 도메인이 아니라 **시간·결정 단위**다.

| 폴더 | 용도 | 파일 명명 |
|------|------|----------|
| `00_Inbox/` | 떠오른 아이디어 임시 저장 | 자유 |
| `10_Sessions/` | 세션 단위 작업 기록 | `YYYY_MM_DD__HH.MM_<작업명>.md` |
| `20_Decisions/` | 결정 사항 / 기각된 대안 | `YYYY_MM_DD__<주제>.md` |
| `30_Skills/` | 글로벌 스킬 사본·메모 | `<스킬명>_노트.md` |
| `40_Patents/` | 특허 자료·청구항 초안 | `<특허번호>_<주제>.md` |
| `50_Refs/` | 외부 링크·논문 요약 | 자유 |
| `90_Archive/` | 종료된 프로젝트 | 자유 |

날짜 기반 명명은 글로벌 CLAUDE.md *"파일은 날짜 기반으로 생성한다. 날짜가 없으면 인간이 찾을 수 없다"* 규칙의 직접 적용이다. 도메인 분류는 양방향 링크와 태그로 처리한다 — 같은 노트가 `#patent #SAL_Grid #2026Q2` 다중 태그를 갖는 게 자연스럽다.

### WiKi_LLM 레이어 — recall.search → recall.expand 2단계

WiKi_LLM은 단일 도구가 아니라 본인이 *"AI가 Vault를 읽는 방식"* 을 묶어 부르는 호칭이다. 핵심은 2단계 호출.

```
Step 1: recall.search("키워드")  → 제목 + snippet 200자 목록 (경량)
Step 2: recall.expand(threadId)  → 필요한 것만 전문 로드 (선택적)
```

이 분리가 결정적이다. 한 번에 풀텍스트를 가져오면 컨텍스트가 즉시 차고, 200K 윈도우의 절반을 메모리 회상에 써버린다. snippet 단계에서 후보를 좁히고 expand에서 1~2건만 펼치면 컨텍스트 비용이 1/20 수준으로 떨어진다. *"recall은 조용히 사용한다. 'recall에서 찾았는데' 같은 표현 금지. 검색 결과는 응답에 자연스럽게 녹인다"* — 글로벌 헌법의 명시 규칙이며, AI가 자신의 기억 인프라를 굳이 광고하지 않게 만든 운용 미학이다.

### MEMORY.md — 자동 누적 메모리

`~/.claude/projects/<프로젝트>/memory/MEMORY.md` (Windows: `C:\Users\home\.claude\projects\<프로젝트>\memory\MEMORY.md`) 가 프로젝트별 자동 메모리다. 세션이 끝날 때 핵심 결정·실패 사례·재사용 가능한 패턴이 인덱스 형태로 적힌다. 예: *"feedback_playwright_korean_path.md — Playwright 한글 경로 문제: /tmp/ 복사 후 작업 권장."* 한 줄 인덱스가 짧지만, 다음 세션에서 같은 함정에 빠지는 걸 막는다. **Vault가 노하우 도서관이라면 MEMORY.md는 책상 위 메모지**다.

### 양방향 링크 = 의존성 그래프

`[[2026_05_03_김부겸_보고서]]` 형식의 위키 링크가 그대로 그래프 노드가 된다. Obsidian Graph View에서 시각적으로 보면 결정의 가지치기가 한눈에 들어오고, AI가 expand할 때 *"이 노트가 참조하는 다른 노트도 함께 가져와라"* 식으로 1-hop 확장 쿼리가 가능해진다. SAL Grid의 Append-Only ID 체인(#35)이 식별자에 의존성을 박은 발명이라면, **Obsidian 양방향 링크는 콘텐츠에 의존성을 박은 형태**다. 두 메커니즘은 동일 사상의 다른 적용이다.

### 챗봇 학습 데이터 풀

본인 운용 중인 지능형 챗봇(#22) — 아바타형/도우미형 — 이 학습·검증할 때 가장 먼저 보는 데이터가 Vault다. 챗봇은 Vault를 그대로 RAG 소스로 쓴다. 새 챗봇을 만들 때마다 별도 데이터셋을 모으지 않고, **이미 4,000시간 누적된 Vault를 그대로 키운다**. 이게 *"점진적으로 학습·개선시키며 자산화"*(종합정리 #22)의 실체다. 4,000시간 동안 같은 함정에 두 번 빠지지 않는 단 하나의 이유 — 챗봇이 본인 과거 결정을 자동으로 끌어다 보여주기 때문이다. *"저번에 이렇게 결정하셨네요"* 한 줄이 사람의 인지 부하를 가장 크게 줄인다.

### 외부 자산 흡수 통로

`find-skills-기본` 스킬로 revfactory/skills 등 외부 저장소(#28)에서 발견한 스킬·에이전트를 Vault `30_Skills/` 에 사본 + 노트로 박아둔다. 외부에서 들여온 자산을 본인 운용 맥락 — *"이 스킬이 본인의 어느 작업과 짝이 되는가"* — 으로 묶어두지 않으면 발견은 했어도 활용이 안 된다. Vault가 그 묶음의 자리다.

## 실전 사용법

### 1단계 — 매 세션 시작 시 inbox 비우기

`00_Inbox/` 에 쌓인 임시 메모를 5분 안에 분류 폴더로 옮기거나 삭제. 쌓이면 무용지물이 된다. 화요일에 떠오른 아이디어가 금요일에 inbox에 그대로 있으면 이미 죽은 메모다.

### 2단계 — 작업 종료 시 Session 노트 작성

`10_Sessions/2026_05_06__21.30_본문일괄작성.md` 식으로 저장. 내용은 **결정·시행착오·재사용 가능한 패턴** 세 가지 위주. 코드 자체는 git이 보관하니 Vault에는 코드를 적지 않는다. *"왜 그 코드를 그렇게 짰는가"* 만 적는다.

### 3단계 — 결정 노트는 Decisions 폴더 + 양방향 링크

같은 사안을 두 번 결정하지 않기 위한 장치. 결정한 즉시 `20_Decisions/` 에 *"무엇을 / 왜 / 기각된 대안"* 3줄로 적고, 관련 세션 노트와 양방향 링크. 다음에 같은 안건이 올라오면 recall이 즉시 회수한다.

### 4단계 — recall MCP 활성화

`~/.claude/settings.json` 의 `mcpServers` 에 recall MCP 등록. Claude Code가 자동으로 Vault를 인덱싱하고 `recall.search`/`recall.expand` 도구를 노출한다. 활성화 후 글로벌 CLAUDE.md에 *"recall 사용 지침"* 섹션이 있는지 확인 — 없으면 AI가 인프라를 안 쓴다.

### 5단계 — 모바일에서 즉시 회수 패턴

원격 데스크탑(#5)으로 모바일에서 작업하다 화면 텍스트 복사가 안 될 때, *"G:\내 드라이브\<프로젝트>\결과_URL.txt 에 저장해라"* 로 지시하면 폰 Google Drive 앱에서 즉시 확인. Vault 자체가 같은 G드라이브에 있으니 **AI가 적은 결과물도 본인이 폰으로 같은 위치에서 본다**. 이 단순한 원칙이 모바일 운용을 가능케 한다 (글로벌 헌법 *"모바일 원격접속 환경에서 URL/결과물 전달 방법"*).

### 6단계 — 양방향 정기 audit (소급 정리)

월 1회 Obsidian Graph View를 열어 **고립 노드**(orphan, 어디에도 링크되지 않은 노트)와 **유령 링크**(존재하지 않는 노트로의 링크) 를 점검. SAL Grid의 양방향 audit(#35 7단계)와 같은 사상의 정합성 검사. Vault가 무한히 커져도 정합성이 유지되는 유일한 방법.

### 7단계 — 챗봇 RAG 소스로 연결

본인 챗봇(#22)을 새로 만들거나 업데이트할 때, RAG 소스 경로를 Vault 루트로 설정. 챗봇은 *"본인의 4,000시간을 학습한 챗봇"* 이 된다. 단순 질의응답을 넘어 본인 결정 패턴까지 모방하는 분신.

### 8단계 — Vault 자체를 SAL Grid Cluster Mode로 관리

장기 누적이 길어지면 Vault 자체도 SAL Grid 대상이다. 시간 기반 1차 분류 위에 도메인 Stage를 얹는다 — *"30_Skills/"* 를 Stage 1, *"40_Patents/"* 를 Stage 2, *"50_Refs/"* 를 Stage 3 클러스터로 본다. Stage 수가 10 이상으로 늘면 Cluster Mode(#35) 정식 적용. 6단계의 월 1회 수동 audit가 일상 점검이라면, 이 단계는 **Cluster Mode + 자동 audit 스크립트(`scripts/audit.js`)** 로 격상하는 시점. 도메인 인덱스가 분리되어도 양방향 정합성이 자동 유지된다.

## 본인 운용 패턴

Vault를 단순 노트 저장소로 보지 않고 **사고 인프라**로 본다. 가장 큰 인지 전환은 *"중요한 건 머릿속에 둔다"* 에서 *"머리에는 인덱스만, 본문은 Vault에"* 로 넘어간 순간이었다. 4,000시간 동안 사람의 머리는 인덱스 작성에만 쓰고, 본문은 Vault에 둔다. 이 분업이 30개 동시 운용을 가능케 한 실제 골격이다.

또 하나 — Vault는 **본인 특허·사업의 단일 진실 원천(SSOT)** 이기도 하다. 본인 특허 *"10-2026-0009425 SAL Grid"* 의 청구항·도면·실시예 초안이 모두 `40_Patents/` 에 있고, 변리사 검토본이 들어올 때마다 차이만 diff로 본다. 특허 명세서가 변경되면 즉시 챗봇과 SAL Grid 슬라이드(`sal-grid-patent-slideshow.html`)가 같은 source-of-truth를 보고 자동 갱신된다. **외부 두뇌 하나에서 출력 N개가 갈라지는 구조**다.

마지막으로, Vault는 ax-on.net 본인 사이트의 데이터 백엔드 역할도 한다. 본인 자체 SAL Grid Edition 마스터 가이드(`claude-code-guide.html`, 7,758줄)의 콘텐츠 원천 일부가 Vault다. **사이트가 보여주는 학습 콘텐츠는 Vault라는 우물에서 길어 올린 물**이다. 우물이 깊지 않으면 사이트는 금방 마른다.

> Vault 사례: `llmwiki-obsidian-guide/wiki/2026_05_03_15.30_research_wiki-llm-implementation.md` 에는 본인이 Andrej Karpathy의 Wiki-LLM 패턴을 처음 검토하고 RAG와 비교한 표가 그대로 박혀 있다 — *"RAG는 매번 벡터 검색·상태 없음·100+ 문서에서 비효율 / Wiki-LLM은 자체 인덱스 네비게이션·상태 있음·마크다운만 사용·개인 규모 최적화."* 본인이 RAG를 버리고 Vault + recall 2단계 호출로 넘어간 결정의 일자별 근거가 이 노트에 있다. 이 항목의 *"Vault가 없으면 30개가 30개의 단기 기억으로 흩어진다"* 라는 본문 주장의 출발점이 그 결정 노트다.
