# 14. SAL(Stage, Area, Level) 3차원 좌표를 활용해서 대규모 작업 계획 세우기 or 분해하기

## 한 줄 정의

본인이 발명한 **3차원 작업 좌표계** — Stage(절차) × Area(영역) × Level(셀 내 의존성) 에 Variant(병렬 분기)까지 결합한 **개념적 좌표** 체계. 큰 작업을 좌표 위에 매핑하면 *누락 없는 분해 + 의존성 자동 추론 + 진척 한눈에 보기* 가 동시에 달성된다. 본 좌표계의 개발 방법론 응용이 #35 SAL Grid이고, 학습 콘텐츠 응용이 ax-on.net 마스터 가이드의 18셀 그리드다.

## 왜 이 노하우가 중요한가

큰 작업을 분해할 때 사람이 가장 많이 실수하는 것은 **분해 축이 한 개**라는 점이다. WBS(Work Breakdown Structure) 트리 하나, 간트 차트의 시간축 하나, JIRA의 epic-story-task 계층 하나. 1축 분해는 단순하지만 *"이 작업이 어느 영역에 속하는가"* 와 *"이 작업이 다른 작업에 의존하는가"* 가 분리되지 않는다. 결과적으로 누락이 생기고 의존성이 보이지 않는다.

본인이 4,000시간 누적에서 30개 동시 운용을 해보면서 깨달은 것 — *"작업 좌표는 최소 3차원이어야 한다"*. 시간(언제 할 것인가) · 영역(무엇을 할 것인가) · 의존(누구 다음에 할 것인가) 이 세 축이 직교해야 누락도 충돌도 없이 분해된다. 이게 SAL의 출발점이다.

3차원으로 보는 순간 한 작업의 위치가 **유일한 좌표 (S, A, L)** 로 찍힌다. *"S2BI3"* 이라는 좌표 한 줄이 *"Stage 2의 Backend Implementation 영역의 3번째 의존성"* 을 자동 의미한다. 좌표 자체가 의존성을 인코딩하므로 별도 그래프 입력이 필요 없다 — Jira에서 의존성을 일일이 선언해야 하는 것과 정반대.

또 하나의 결정적 통찰은 *"좌표가 같으면 같은 도구·같은 에이전트로 처리할 수 있다"* 는 점. Area가 같은 작업들은 모두 같은 Backend 에이전트가 맡고, Stage가 같은 작업들은 모두 같은 시점에 점검된다. 좌표가 자동으로 작업 배분의 기준이 된다.

이 좌표계는 **개념** 차원의 골격이다. 이 골격 위에 *"Task별 22속성·11 Area 표준·검증 자동화·grid_records JSON"* 같은 운용 인프라를 얹은 것이 #35 SAL Grid 개발 방법론이다. 두 항목의 관계는 명확하다 — **#14는 좌표계 자체, #35는 그 좌표계의 개발방법론 응용**. 같은 좌표계의 다른 응용으로 ax-on.net 마스터 가이드의 18셀 학습 그리드가 있다.

## 핵심 개념

### 3차원 + Variant — 4축 좌표

| 축 | 의미 | 성격 |
|----|------|------|
| **S** (Stage) | 절차적 순서 | 직렬 — S1 완료 후 S2, 건너뛸 수 없음 |
| **A** (Area) | 기능적 영역 | 영역 분류 — 같은 Area는 같은 도구·에이전트 |
| **L** (Level) | 셀 내 의존성 | 직렬 — L1 완료 후 L2 (같은 셀 안에서) |
| **V** (Variant) | 병렬 분기 | 병렬 — `a`/`b`/`c`는 동시 실행 가능 |

**Stage**는 시간축이지만 단순 일정이 아니다 — *완료 → 다음으로* 의 의존 관계가 박힌 시간축. **Area**는 영역축이며 *기능 인접성*에 따라 묶인다(같은 Area = 같은 에이전트가 맡기 좋다). **Level**은 셀 내부의 미시적 의존 — 같은 (Stage, Area) 셀 안에서 작업이 여러 개일 때 그 안에서의 순서. **Variant**는 같은 Level의 병렬 분기로, *동시에 시작해도 충돌 없는 작업들* 의 표시.

### SAL ID 형식 — 좌표가 곧 식별자

`S{Stage}{Area}{Level}{Variant?}` — 정규식 `^S(\d{1,2})([A-Z]{2})(\d{1,2})([a-z])?$`

예 — `S2BI3a`:
- Stage 2
- Area BI (Backend Implementation)
- Level 3
- Variant a

ID 한 줄을 보면 **4가지 정보가 동시에 읽힌다.** 별도 메타데이터 조회가 필요 없다.

### Variant의 본질 — 병렬성을 좌표에 인코딩

Variant가 가장 영리한 부분이다. Stage·Area·Level까지는 모두 *직렬* 의존성이지만, Variant는 *병렬* 가능성을 명시한다. `S2BI3a`·`S2BI3b`·`S2BI3c`가 같은 Stage·Area·Level 안의 세 분기이며, 셋은 동시 실행 가능. 30개 동시 운용에서 *"어떤 작업을 동시에 시킬 수 있는가"* 의 답이 좌표 안에 박혀 있다.

이게 SAL의 핵심 발명점 중 하나 — *병렬 가능성 자체를 식별자의 구조적 속성*으로 만든 것. Jira에서 *"이 두 티켓은 동시 작업 가능"* 을 표시하려면 별도 라벨·태그·코멘트가 필요하지만, SAL에서는 *Variant a·b·c가 같은 셀 아래에 있다* 는 사실만으로 자동 표현된다.

### 좌표 인코딩 → 의존성 자동 생성

같은 좌표계 안에서 **의존성은 좌표만 보면 자동 추론된다**. 규칙은 단순하다.

| 관계 | 의존 |
|------|------|
| Stage 차이 | 낮은 Stage가 선행 (S1 → S2) |
| Area 차이 | 영역 표준에 따라 결정 (예: BA Backend Architecture → BI Backend Implementation) |
| Level 차이 | 같은 셀 안에서 낮은 Level이 선행 (L1 → L2) |
| Variant 차이 | 의존 없음 (병렬 가능) |

이 규칙들을 좌표 파서가 자동 적용한다. *"S1BI2 완료 후 S2BI1 가능"*, *"S2BI3a·S2BI3b 동시 가능"* 같은 의존 그래프가 ID만으로 자동 그려진다. **사람이 의존성을 선언하지 않는다 — 좌표가 의존성이다.**

이게 본인 특허(10-2026-0009425) 청구항 1의 요지이며, 4,000시간 시행착오 끝에 도달한 결론이다. *"의존성 선언을 자동화한 것이 아니라, 의존성 개념 자체를 식별자의 구조적 속성으로 치환했다."* 슬라이드 5의 표현 그대로.

### Stage × Area 매트릭스 — 시각화의 본질

SAL을 시각화하면 N×M 매트릭스가 된다. 행은 Stage, 열은 Area. 각 셀에 그 (Stage, Area) 좌표의 작업들이 채워진다. 빈 셀은 *"그 단계엔 그 영역 작업이 없음"* 이라는 의미. 채워진 셀은 색상으로 진행 상태 표시.

이 한 장의 매트릭스로 프로젝트 전체 진행도가 한눈에 들어온다. *"S2 행은 모두 완료, S3 행은 BA·BI·D만 진행 중, S4 행은 미착수"* 같은 정보가 색상으로 즉시 읽힌다.

### 같은 좌표계의 두 응용 — #35와 ax-on.net 18셀

**응용 1 — #35 SAL Grid 개발 방법론**: 11개 Area 표준(F·BA·BI·S·D·T·M·U·O·E·C) + 22속성 Task 그리드 + grid_records JSON + Stage Gate + audit. 본인 특허 출원의 직접 대상이고, 30개 동시 운용의 골격.

**응용 2 — ax-on.net 마스터 가이드 18셀 학습 그리드**: 같은 좌표계를 *학습 콘텐츠 분류*에 응용한 것. Stage 3개(S1 초급·S2 중급·S3 고급) × Area 6개(CO·ST·WF·TO·QC·CM) = 18셀. 각 셀에 Claude Code 지식이 분류되어 있고, 독자는 *"지금 어디서 무엇을 배우는지"* 좌표로 안내받는다. 7,758줄짜리 마스터 가이드가 좌표 18개로 정리됐다는 점 자체가 **SAL 좌표계의 응용 범용성** 증명이다.

22속성·11 Area는 #35의 운용 인프라 영역이므로 본 항목에서는 다루지 않는다. 본 항목은 *좌표계 자체의 개념·원리* 까지만.

### 응용 가능 도메인

좌표계는 *순서·영역·의존* 이 있는 어떤 작업에도 응용 가능하다.

| 도메인 | Stage 예 | Area 예 |
|--------|---------|---------|
| 개발 (#35) | S0~S5 (계획·기획·구현·검증·배포) | F·BA·BI·S·D·T·M·U·O·E·C |
| 학습 콘텐츠 (ax-on.net) | S1·S2·S3 (초/중/고) | CO·ST·WF·TO·QC·CM |
| 사업계획서 | S0~S4 (시장조사·전략·재무·실행·검증) | M·F·O·R·G (Market·Finance·Op·Risk·Gov) |
| 특허 출원 | S0~S3 (선행조사·청구항·도면·심사대응) | C·F·D·R (Claim·Spec·Drawing·Response) |
| 감사·진단 (주작-sal-da) | S0~SN (역방향 분해) | 도메인별 |

본인이 직접 응용해본 것만 4가지 — 개발·학습·특허·진단. 도메인이 달라도 *3차원 좌표 + Variant* 골격은 동일.

## 실전 사용법

### 1단계 — Stage 결정

작업 전체를 절차적 순서로 N개 단계로 나눈다. 통상 N = 3~10. 각 Stage 사이에는 *"다음 Stage로 가려면 이전 Stage가 완료되어야 한다"* 는 직렬 의존이 박힌다. Stage 수가 많으면 Cluster Mode로 묶어 관리(#35 V3.8).

### 2단계 — Area 결정

작업의 *기능적 영역* 을 M개로 분류한다. 도메인별 표준이 있으면 그것을 쓰고(개발은 11 Area), 없으면 4~7개 영역으로 분해. Area는 같은 도구·에이전트로 처리되는 단위가 되므로 *기능 인접성*이 분류 기준.

### 3단계 — Stage × Area 매트릭스 그리기

N×M 매트릭스 작성. 빈 셀은 *"그 좌표에 작업 없음"*, 채워진 셀에는 작업명을 1개~여러 개 배치. 매트릭스 작성 자체가 누락 점검 도구다 — *"S3의 Frontend 셀이 빈 게 정말 맞는가?"* 같은 질문이 자동으로 떠오른다.

### 4단계 — Level 부여

같은 (Stage, Area) 셀 안에 작업이 여러 개면 그 안에서의 순서를 L1·L2·L3…으로 부여. Level 차이는 직렬 의존(L1 → L2). 셀 안에 작업이 1개면 L1만.

### 5단계 — Variant 식별

Level이 같은 작업 중 *동시 실행 가능* 한 분기가 있으면 Variant `a`/`b`/`c`로 분리. Variant는 병렬 표시 — 30개 동시 운용 시 *"이 작업과 저 작업을 동시에 시켜도 된다"* 의 답.

### 6단계 — SAL ID 부여 + 매트릭스 갱신

각 작업에 `S{Stage}{Area}{Level}{Variant?}` 형식 ID 부여. ID가 좌표이자 식별자이자 의존성 명세. 매트릭스에는 ID와 작업명 함께 표기.

### 7단계 — 응용 인프라 결합 (선택)

좌표계만으로도 분해는 끝나지만 본인 운용에서는 #35의 운용 인프라(22속성 grid_records JSON, Stage Gate 5단계 리포트, sal-guard pre-commit, Verification Agent 자동 투입)를 얹어 30개 동시 운용 골격으로 확장. 단순 작업 분해만 필요하면 본 좌표계까지만 써도 충분.

## 본인 운용 패턴

본 좌표계의 가장 큰 가치는 *"매번 새로 짜지 않아도 된다"* 는 점이다. 한 번 (Stage, Area) 매트릭스를 잡으면 비슷한 도메인의 다음 프로젝트에 그대로 재사용된다. 본인이 운영 중인 SSAL Works Project는 5 Stage × 11 Area = 55셀에 74개 Task를 배치한 매트릭스인데, 후속 프로젝트들은 이 매트릭스를 출발점으로 잡고 차이만 조정한다. *템플릿화된 좌표계*가 매번의 분해 비용을 1/10로 줄인다.

또 하나의 패턴 — *"빈 셀이 보이면 의심한다"*. 매트릭스를 그렸을 때 *"S3 행의 Test 셀이 비어 있다"* 면 둘 중 하나다. ① 정말 그 단계엔 테스트 작업이 없거나, ② 누락. 90% 이상은 ②다. 빈 셀은 *분해의 빈 곳을 보여주는 거울*이며, 1축 WBS에서는 절대 보이지 않는 정보다.

마지막 — *"좌표가 곧 의사소통이다"*. 30개 동시 운용에서 30개 인스턴스에게 작업을 지시할 때 ID 한 줄(`S2BI3a`)만 던지면 *어디·무엇·언제·병렬가능여부* 가 동시에 전달된다. 자연어 지시서를 일일이 작성할 필요가 없다. 좌표가 prompt를 압축한다.
