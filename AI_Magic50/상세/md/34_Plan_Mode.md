# 34. Plan Mode 활용해서 실행 전에 계획부터 세우기

## 한 줄 정의

`Shift+Tab` 두 번으로 진입하는 **읽기·분석·계획만 허용하고 쓰기·실행은 차단**하는 모드. 위험 작업·큰 리팩토링 전 필수 통과 관문이며, 사용자 승인 후 실행 모드로 전환.

## 왜 이 노하우가 중요한가

Claude Code는 강력한 도구 권한을 가지므로 **계획 없이 들어가면 첫 응답이 곧 파괴적 행동**이 될 수 있다. 본인 4,000시간 운용 초기, "리팩토링 해줘" 한 마디에 50개 파일이 즉시 수정돼 git이 살린 적이 있다. 그 사건 이후 큰 작업 전 Plan Mode 통과는 본인 표준 절차가 됐다.

Plan Mode는 #20(문서화는 나중에)과 모순돼 보이지만 **단순 작업은 #20, 큰 작업은 #34**로 구분된다. 차원이 다른 두 모드를 의식적으로 선택하는 것이 핵심.

## 핵심 개념

진입과 동작:

| 항목 | 내용 |
|------|------|
| 진입 | `Shift+Tab` 2회 |
| 표시 | 입력창 좌측 `plan mode` 배지 |
| 허용 도구 | Read, Grep, Glob, WebFetch, Task |
| 차단 도구 | Edit, Write, Bash(쓰기), MCP(쓰기) |
| 종료 | 사용자가 계획 승인 → 자동 실행 모드 |

본인 트리거(필수 진입 상황):
- 50개 이상 파일이 영향받는 리팩토링
- DB 마이그레이션·스키마 변경
- 배포·환경변수 변경
- SAL Grid Stage Gate 통과 직전
- "전부", "일괄", "마이그레이션" 키워드 등장 시

## 실전 사용법

**1단계** — 큰 작업 의뢰 직전 `Shift+Tab` 2회. 입력창 배지 확인.

**2단계** — 자연어로 의뢰. AI가 Read·Grep·Task로 코드베이스를 탐색하고 **변경 계획**을 단계별로 제시.

**3단계** — 계획서를 사용자가 검토. 누락·과잉·위험 단계를 지적해 수정 요구. 이때 #12 3대안+권고안을 강제하면 더 풍성한 결과.

**4단계** — 승인 시 Plan Mode가 자동 해제되며 그대로 실행. 계획에 없던 작업은 실행되지 않음을 보증.

**5단계** — 실행 후 **자기 검증 금지** — 같은 인스턴스가 자기 변경을 검증하면 함정. 별도 Verification Agent(#46)로 사용자 여정 KPI 확인.

**본인 운용 패턴**: SAL Grid Stage 진입 시 MBO 정의 → Plan Mode로 Stage Task 계획 → PO 승인 → 실행. Plan Mode가 Stage Gate의 안전장치 역할을 한다. "curl 200 ≠ 동작함"이 Verification 단의 교훈이라면, Plan Mode는 그 앞단의 사전 차단막.

> Vault 사례: `ax-practical-project/wiki/2026_05_03_21.04_import_PHASE_ROADMAP.md` 는 Plan Mode 산출물이 그대로 PHASE 로드맵 문서로 굳어진 사례다. 동일 폴더의 `2026_04_01__18_00_TASK_PLAN______.md` / `2026_04_01__19_00_TASK_PLAN_________.md` / `2026_04_01__20_00_TASK_PLAN_C____.md` 3개 노트는 같은 날 1시간 간격으로 TASK_PLAN을 *Plan A → Plan B → Plan C* 로 진화시킨 흔적 — 즉 본인은 Plan Mode를 *한 번 짜고 끝* 이 아니라 *18:00 → 19:00 → 20:00 같은 시간 간격으로 3회 갱신* 하면서 PO 승인 직전까지 다듬는다. 본 항목 3단계 *"누락·과잉·위험 단계를 지적해 수정 요구"* 의 정량 증거.
