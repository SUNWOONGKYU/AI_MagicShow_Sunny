6.1 좋은 질문 만들기

LLM위키를 만들었다고 해서 좋은 답이 자동으로 나오지는 않습니다. 위키는 자료를 모아 둔 장소이고, 질문은 그 자료를 업무 결과로 꺼내는 방법입니다.

같은 위키를 두고도 “이거 요약해 줘”라고 묻는 사람과 “이번 주 회의에서 결정할 수 있도록 근거가 있는 선택지 3개로 정리해 줘”라고 묻는 사람은 다른 답을 받습니다. 이 절에서는 위키에 질문할 때 검색어가 아니라 업무 요청으로 묻는 방법을 익힙니다.

단순 검색 질문과 업무 질문의 차이

단순 검색 질문은 정보를 찾는 데 초점이 있습니다. “무엇인가?”, “어디에 있는가?”, “요약해 줘” 같은 질문입니다. 이런 질문도 필요합니다. 다만 업무에서는 정보만으로 끝나지 않습니다. 보고해야 하고, 결정해야 하고, 다음 행동을 정해야 합니다.

업무 질문은 정보를 찾은 뒤 무엇에 쓸지까지 포함합니다. LLM위키에 묻는 좋은 질문은 보통 세 가지를 함께 담습니다.

  • 확인할 주제
  • 사용할 자료 범위
  • 원하는 결과물의 형태

예를 들어 “회의록 요약해 줘”는 단순 검색 질문에 가깝습니다. 반면 “지난 2주 회의록을 바탕으로 고객 문의 자동화에서 아직 결정되지 않은 쟁점을 표로 정리해 줘”는 업무 질문입니다. 같은 자료를 보더라도 답변의 깊이와 형식이 달라집니다.

학습자료: 단순 검색 질문과 업무 질문 비교

질문 유형 질문 예시 답변이 주로 하는 일 업무에서 부족한 점 개선 방향
단순 검색 고객 문의 자동화가 뭐야? 개념 설명 내 업무 맥락이 빠짐 위키의 어떤 자료를 기준으로 답할지 지정
단순 요약 회의록 요약해 줘 핵심 문장 압축 결정, 쟁점, 다음 행동이 섞일 수 있음 목적과 산출물 형식을 지정
업무 질문 지난 2주 회의록에서 고객 문의 자동화의 미결 쟁점을 정리해 줘 자료를 업무 판단에 맞게 재구성 근거 요구가 없으면 검증이 약함 출처, 확인 필요, 다음 행동까지 요청
검토 질문 이 실행 계획에서 근거가 약한 항목을 찾아 줘 답변의 신뢰도 점검 원문 연결이 없으면 확인이 어려움 원천 자료 경로와 판단 이유를 함께 요청

이 표의 핵심은 “좋은 질문은 긴 질문”이 아니라는 점입니다. 좋은 질문은 답변이 해야 할 일을 분명히 합니다. 자료를 찾으라는 요청인지, 판단을 도와 달라는 요청인지, 산출물을 만들어 달라는 요청인지가 드러나야 합니다.

실습: 검색 질문을 업무 질문으로 바꾸기

목표
평소에 LLM에게 던지는 짧은 질문을 LLM위키용 업무 질문으로 바꿉니다.

실행 전제
raw/에 회의록이나 메모가 있고, wiki/에 관련 요약 문서가 있다고 가정합니다. 실제 도구 명령은 사용하지 않습니다.

성공 기준
질문 안에 자료 범위, 업무 목적, 출력 형식이 모두 들어갑니다.

나쁜 질문:
고객 문의 자동화 정리해 줘.

개선한 질문:
wiki/customer-inquiry-labeling.md와 raw/meeting-notes/2026-05-* 회의록을 기준으로,
고객 문의 자동화에서 아직 결정되지 않은 쟁점을 정리해 줘.
결과는 '쟁점 / 관련 근거 / 결정에 필요한 추가 확인 / 다음 행동' 표로 써 줘.
근거가 부족한 항목은 '확인 필요'로 표시해 줘.

개선한 질문은 LLM에게 “무엇을 읽을지”와 “무엇을 만들지”를 함께 알려 줍니다. 또한 근거가 부족한 내용을 단정하지 말라고 요청합니다. LLM위키에서는 이 마지막 조건이 중요합니다. 위키 문서는 원본이 아니라 원본을 바탕으로 정리한 지식층이기 때문입니다.

맥락을 좁히는 질문

LLM 답변이 넓고 모호해지는 가장 흔한 이유는 질문의 맥락이 넓기 때문입니다. “우리 업무를 개선하려면?”처럼 묻는다면 LLM은 일반론으로 답할 가능성이 큽니다. 위키에 좋은 자료가 있어도 질문이 넓으면 자료의 장점을 살리기 어렵습니다.

맥락을 좁힌다는 말은 답변의 시야를 줄인다는 뜻이 아닙니다. 오히려 답변이 필요한 지점에 집중하게 만드는 일입니다. 좋은 질문은 다음 네 가지 경계를 정합니다.

  • 시간 범위: 이번 주, 지난 2주, 2026년 5월 회의록
  • 자료 범위: 특정 위키 문서, 원천 자료 폴더, 회의록 묶음
  • 판단 기준: 비용, 반복 빈도, 고객 영향, 실행 난이도
  • 제외 범위: 아직 검토하지 않은 자료, 추측, 오래된 정책

학습자료: 질문이 답변으로 바뀌는 흐름

이 도해는 질문이 한 번에 완성되지 않아도 된다는 점을 보여 줍니다. 처음에는 넓게 묻고, 답변이 흐리면 자료 범위와 판단 기준을 추가해 다시 묻습니다. LLM위키를 쓸 때는 질문을 고쳐 가는 과정도 업무 지식의 일부입니다.

실습: 질문에 경계 넣기

목표
넓은 질문을 자료 범위와 판단 기준이 있는 질문으로 좁힙니다.

실행 전제
다음과 같은 위키 구조가 있다고 가정합니다.

raw/
  meeting-notes/
    2026-05-01.md
    2026-05-08.md
wiki/
  customer-inquiry-labeling.md
  automation-rules.md
output/

성공 기준
질문이 “자료 범위”, “시간 범위”, “판단 기준”, “제외 범위”를 포함합니다.

넓은 질문:
자동화할 만한 업무를 찾아 줘.

맥락을 좁힌 질문:
raw/meeting-notes/2026-05-01.md, raw/meeting-notes/2026-05-08.md,
wiki/customer-inquiry-labeling.md를 기준으로 자동화 후보를 찾아 줘.

시간 범위는 2026년 5월 첫째 주와 둘째 주 회의록으로 제한해.
판단 기준은 반복 빈도, 고객 영향, 실행 난이도야.
근거가 없는 추정은 제외하고, 자료에서 확인되지 않은 내용은 '확인 필요'로 표시해 줘.

출력은 다음 표 형식으로 해 줘.
- 자동화 후보
- 근거
- 기대 효과
- 실행 난이도
- 확인 필요

이 질문은 답변의 범위를 좁힙니다. 동시에 답변의 쓸모를 높입니다. LLM은 “자동화할 만한 업무”를 일반적으로 말하는 대신, 특정 회의록과 위키 문서를 기준으로 후보를 추립니다.

질문을 좁힐 때 피해야 할 표현

“알아서”, “전체적으로”, “좋게”, “중요한 것 위주로” 같은 표현은 편해 보이지만 답변을 흐리게 만듭니다. 이런 표현을 꼭 써야 한다면 기준을 함께 적어야 합니다.

흐린 표현 더 나은 표현
전체적으로 정리해 줘 지난 2주 회의록에서 결정 사항과 미결 쟁점을 나눠 정리해 줘
중요한 것 위주로 고객 영향이 크고 이번 달 안에 실행 가능한 항목을 우선해 줘
알아서 표로 만들어 줘 후보, 근거, 담당자, 기한, 확인 필요 열로 표를 만들어 줘
실행 가능하게 써 줘 오늘 할 일, 이번 주 할 일, 다음 회의에서 결정할 일을 나눠 줘

질문을 좁히면 LLM이 답을 덜 창의적으로 만든다고 느낄 수도 있습니다. 하지만 업무에서는 창의성보다 재현성이 먼저 필요할 때가 많습니다. 특히 위키에 있는 자료를 근거로 판단해야 한다면, 질문은 명확할수록 좋습니다.

바로 실행 가능한 답변 요청하기

좋은 질문의 마지막 단계는 답변을 행동으로 바꾸는 것입니다. LLM에게 설명을 요청하면 설명이 돌아옵니다. 실행 계획을 요청하면 할 일 목록이 돌아옵니다. 검증 가능한 산출물을 요청하면 검토할 수 있는 초안이 돌아옵니다.

바로 실행 가능한 답변에는 보통 다음 요소가 들어갑니다.

  • 누가 읽을 답변인지
  • 어떤 형식으로 받을지
  • 어떤 순서로 실행할지
  • 무엇을 확인해야 하는지
  • 근거와 한계를 어떻게 표시할지

예를 들어 “고객 문의 자동화 계획을 알려 줘”보다 다음 질문이 더 좋습니다.

wiki/customer-inquiry-labeling.md와 raw/meeting-notes/2026-05-*.md를 기준으로
고객 문의 자동화 2주 실험 계획을 작성해 줘.

대상 독자는 팀장이고, 목적은 다음 주 회의에서 실험 승인 여부를 결정하는 것이야.

다음 형식으로 작성해 줘.
1. 한 문장 결론
2. 실험 목표
3. 2주 실행 일정
4. 필요한 담당자와 입력 자료
5. 성공 기준
6. 근거가 있는 항목
7. 확인 필요한 항목

위키나 원천 자료에서 확인되지 않는 내용은 단정하지 말고 '확인 필요'로 표시해 줘.

이 질문은 답변을 회의 자료로 바로 옮기기 쉽게 만듭니다. 또한 검토자가 어디를 확인해야 하는지도 드러납니다.

학습자료: 바로 실행 가능한 답변 요청 템플릿

구성 요소 질문에 넣을 문장 이유
역할 대상 독자는 팀장입니다 답변의 깊이와 표현을 맞춥니다
목적 다음 회의에서 승인 여부를 결정하려고 합니다 설명보다 판단에 필요한 답을 유도합니다
자료 범위 wiki/...와 raw/...를 기준으로 답하세요 근거 없는 일반론을 줄입니다
출력 형식 표 또는 1~7번 구조로 작성하세요 복사해 업무 문서로 옮기기 쉽습니다
검증 조건 확인되지 않은 내용은 확인 필요로 표시하세요 추정과 사실을 구분합니다
다음 행동 오늘 할 일과 이번 주 할 일을 나눠 주세요 답변을 실행으로 연결합니다

이 템플릿은 모든 질문에 그대로 붙이는 만능 문구가 아닙니다. 업무에 따라 줄여서 써야 합니다. 다만 중요한 요청일수록 목적, 자료 범위, 출력 형식, 검증 조건은 남기는 편이 안전합니다.

실습: 답변 형식을 먼저 정하기

목표
LLM위키에 질문하기 전에 원하는 답변 형식을 먼저 정합니다.

실행 전제
업무 주제 하나를 정합니다. 예시는 “고객 문의 자동화”입니다.

성공 기준
질문이 결과물 형식과 검증 조건을 포함합니다.

질문 초안:
고객 문의 자동화 계획을 만들어 줘.

답변 형식을 정한 질문:
고객 문의 자동화 계획을 만들어 줘.
단, 설명문이 아니라 실행 계획으로 작성해 줘.

자료 범위:
- wiki/customer-inquiry-labeling.md
- wiki/automation-rules.md
- raw/meeting-notes/2026-05-01.md
- raw/meeting-notes/2026-05-08.md

출력 형식:
| 할 일 | 담당자 후보 | 기한 | 필요한 자료 | 근거 | 확인 필요 |

조건:
- 근거 열에는 위키 문서명 또는 원천 자료명을 적어 줘.
- 자료에서 확인되지 않은 담당자는 '확인 필요'로 표시해 줘.
- 마지막에 오늘 바로 할 일 3개만 따로 정리해 줘.

이 질문은 결과물을 표로 제한합니다. 표는 완벽한 형식은 아니지만 업무 검토에는 유리합니다. 빈칸, 근거 부족, 담당자 미정 같은 문제가 눈에 잘 보이기 때문입니다.

답변을 받은 뒤 다시 물을 질문

좋은 질문은 한 번으로 끝나지 않습니다. 첫 답변을 받은 뒤에는 다음 질문으로 답의 품질을 높입니다.

방금 답변에서 근거가 약한 항목만 골라 줘.
각 항목마다 왜 근거가 약한지 설명하고,
추가로 확인해야 할 원천 자료나 질문을 제안해 줘.

위 답변을 실행 계획으로 쓰기 전에 위험한 가정을 찾아 줘.
자료에 있는 사실, 자료에서 추정한 내용, 확인되지 않은 내용을 나눠 줘.

팀장에게 보낼 1페이지 요약으로 줄여 줘.
단, 확인 필요 항목은 삭제하지 말고 별도 섹션으로 남겨 줘.

이런 후속 질문은 6.2에서 다룰 답변 검증으로 이어집니다. 6.1의 목표는 좋은 첫 질문을 만드는 것입니다. 6.2의 목표는 그 답을 믿어도 되는지 확인하는 것입니다.

6.1의 검증 포인트

좋은 질문은 멋진 문장이 아니라 검증 가능한 업무 요청입니다. 위키에 질문하기 전에 다음 항목을 확인합니다.

점검 항목 확인 질문
자료 범위 어떤 wiki/ 문서와 raw/ 자료를 기준으로 답해야 하는가?
업무 목적 이 답변을 보고, 결정하고, 실행하는 사람은 누구인가?
판단 기준 무엇을 기준으로 중요하다고 볼 것인가?
출력 형식 표, 목록, 실행 계획, 보고서 초안 중 무엇이 필요한가?
검증 조건 근거 없는 내용과 확인 필요한 내용을 표시하라고 요청했는가?
다음 행동 답변이 오늘 할 일이나 다음 회의 안건으로 이어지는가?

이 절에서 익힌 방식대로 질문하면 LLM위키는 단순한 자료 저장소가 아니라 업무 판단을 돕는 도구가 됩니다. 다음 절에서는 이렇게 받은 답변의 근거를 확인하는 방법을 다룹니다.

근거와 추가 확인

  • Andrej Karpathy, LLM Wiki 아이디어 문서, https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f, 확인일: 2026-05-16. 원천 자료, 위키, 스키마 계층과 ingest → query → lint 흐름의 근거입니다.
  • nvk/llm-wiki README, https://github.com/nvk/llm-wiki, 확인일: 2026-05-16. LLM위키를 질의와 연구 흐름에 활용하는 구현체 사례입니다.
  • OpenAI Codex AGENTS.md 문서, https://developers.openai.com/codex/guides/agents-md, 확인일: 2026-05-16. Codex에서 프로젝트 지침을 활용할 수 있다는 근거입니다.
  • Anthropic Claude Code memory 문서, https://docs.anthropic.com/en/docs/claude-code/memory, 확인일: 2026-05-16. Claude Code에서 CLAUDE.md 같은 메모리 파일을 활용할 수 있다는 근거입니다.
  • WiCER: Iterative Knowledge Compilation for LLM Wiki Systems, https://arxiv.org/abs/2605.07068, 확인일: 2026-05-16. LLM위키형 시스템에서 무검증 컴파일이 위험할 수 있다는 초기 연구 근거입니다. 프리프린트이므로 본문에서는 제한된 근거로만 반영했습니다.
