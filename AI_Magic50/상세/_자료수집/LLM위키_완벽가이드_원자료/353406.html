8.1 위키에도 점검이 필요한 이유

LLM위키는 한 번 만들고 끝나는 문서함이 아닙니다. 원천 자료를 읽고, 위키 문서로 정리하고, 다시 업무 산출물로 꺼내 쓰는 지식 관리 흐름입니다. 그래서 시간이 지나면 자연스럽게 낡은 내용, 출처 없는 주장, 서로 맞지 않는 설명이 생깁니다.

문제는 이런 오류가 대개 눈에 잘 띄지 않는다는 점입니다. LLM이 만든 요약은 문장이 매끄럽습니다. 문장이 매끄러우면 내용도 맞는 것처럼 보입니다. 하지만 위키 문서가 원본은 아닙니다. LLM위키에서 믿어야 할 것은 “위키에 적혀 있다”는 사실이 아니라, 그 문장이 어떤 원천 자료와 어떤 확인 절차로 뒷받침되는지입니다.

이 절에서는 LLM위키를 오래 믿고 쓰기 위해 왜 점검이 필요한지 살펴봅니다. 핵심은 세 가지입니다. 그럴듯한 요약을 그대로 믿지 않기, 출처가 빠지거나 오래된 주장을 찾기, 검증을 별도 이벤트가 아니라 업무 루틴에 넣기입니다.

그럴듯한 요약의 위험

LLM위키의 장점은 원천 자료를 다시 쓰기 좋은 형태로 정리해 준다는 점입니다. 회의록, 웹 문서, 보고서, 메모가 흩어져 있어도 LLM은 핵심 내용을 뽑아 문서로 묶을 수 있습니다. 하지만 바로 그 장점 때문에 위험도 생깁니다.

요약은 원문보다 짧습니다. 짧아지는 과정에서 빠지는 것이 있습니다. 날짜, 조건, 예외, 반대 의견, 불확실한 표현이 사라질 수 있습니다. 원문에는 “이번 분기에는 임시로 적용한다”라고 되어 있었는데, 위키에는 “이 방식으로 적용한다”라고 남을 수 있습니다. 원문에는 “A안과 B안 중 아직 결정하지 않았다”라고 되어 있었는데, 위키에는 “A안을 검토한다”가 아니라 “A안을 추진한다”로 정리될 수도 있습니다.

LLM위키 패턴의 원문 설명에서도 원천 자료와 위키 문서는 다른 층으로 구분됩니다. 원천 자료는 기준점이고, 위키 문서는 LLM이 만든 파생 지식입니다. 따라서 위키 문서는 읽기 쉬운 업무용 문서이지만, 최종 근거는 아닙니다.

학습자료: 요약이 왜곡되는 흐름

이 흐름에서 중요한 지점은 B와 C입니다. LLM이 원천 자료를 읽고 정리하는 순간, 내용은 더 편해집니다. 동시에 더 위험해집니다. 원문보다 읽기 쉬운 문장은 원문보다 검증하기 어려울 수 있습니다.

그래서 LLM위키를 운영할 때는 “좋은 요약인가?”만 묻지 않습니다. 다음 질문을 함께 던져야 합니다.

점검 질문 확인할 것 위험한 상태
이 문장은 어디에서 왔는가 원천 자료 파일명, URL, 확인 날짜 출처 없이 자연스러운 설명만 있음
조건이 빠지지 않았는가 기간, 대상, 예외, 전제 임시 결정을 일반 원칙처럼 씀
추정이 단정으로 바뀌지 않았는가 “가능성”, “검토 중”, “확인 필요” 표현 아직 모르는 내용을 확정처럼 씀
최신성이 필요한가 제품 버전, 정책 날짜, 가격, 일정 오래된 정보를 현재 기준처럼 씀

실습: 요약 문장에 신뢰도 표시하기

목표
LLM이 만든 요약을 그대로 받아들이지 않고, 문장별로 근거 상태를 표시합니다.

실행 전제
아래 예제 문서만 읽고 따라 할 수 있습니다. 실제 위키가 있다면 자신의 문서 하나를 골라 같은 방식으로 점검합니다.

예제 원천 메모

# 2026-05-10 고객 문의 자동 분류 회의 메모

- 고객지원팀은 반복 문의 중 배송 상태 확인 요청이 많다고 말했다.
- 5월에는 FAQ 자동 응답 초안을 내부 테스트한다.
- 개인정보가 포함된 문의는 자동 응답 대상에서 제외해야 한다.
- 정확한 반복 문의 비율은 아직 집계하지 않았다.

예제 위키 요약

# 고객 문의 자동 분류

고객지원팀의 반복 문의 대부분은 배송 상태 확인이다. 5월부터 FAQ 자동 응답을 적용한다. 개인정보 문의는 자동 응답에서 제외한다.

점검 결과 예시

위키 문장 판정 이유 고친 문장
반복 문의 대부분은 배송 상태 확인이다 확인 필요 원천 메모에는 “많다”라고만 되어 있고 비율은 집계되지 않음 배송 상태 확인 요청이 반복 문의에서 많이 언급되었으나 정확한 비율은 확인 필요
5월부터 FAQ 자동 응답을 적용한다 확인 필요 원천 메모는 “내부 테스트”라고 함 2026년 5월에는 FAQ 자동 응답 초안을 내부 테스트한다
개인정보 문의는 자동 응답에서 제외한다 확인됨 원천 메모와 일치함 개인정보가 포함된 문의는 자동 응답 대상에서 제외한다

이 실습의 핵심은 틀린 문장을 찾는 것이 아닙니다. 더 정확한 문장으로 바꾸는 것입니다. LLM위키에서 점검은 비난 절차가 아니라 지식의 품질을 올리는 편집 절차입니다.

출처 누락과 오래된 주장 찾기

위키 문서가 많아지면 두 가지 문제가 자주 생깁니다. 하나는 출처가 빠지는 문제입니다. 다른 하나는 예전에는 맞았지만 지금은 확인해야 하는 주장이 계속 남는 문제입니다.

출처 누락은 단순한 형식 문제가 아닙니다. 출처가 없으면 그 문장을 고칠 수 없습니다. “누가 그렇게 말했는지”, “어떤 문서에서 나온 내용인지”, “언제 확인한 것인지”를 알 수 없기 때문입니다. 결국 위키는 다시 대화창처럼 변합니다. 읽을 수는 있지만 믿기는 어려운 상태가 됩니다.

오래된 주장도 비슷합니다. 특히 기술 도구, 제품 기능, 설치 명령, 가격, 일정, 정책은 빨리 바뀝니다. 2026년 5월 기준으로 맞는 설명도 몇 달 뒤에는 틀릴 수 있습니다. LLM위키는 오래 쓸수록 이런 주장을 찾아 표시해야 합니다.

학습자료: 점검할 주장 유형

주장 유형 예시 점검 방법 처리 방법
출처 없는 사실 “이 기능은 모든 도구에서 지원된다” 원천 자료 링크나 공식 문서가 있는지 확인 출처를 추가하거나 확인 필요로 표시
날짜가 필요한 주장 “최신 버전은 v0.9.0이다” 확인 날짜와 릴리스 문서를 확인 2026-05-16 확인 기준처럼 날짜를 붙임
조건이 있는 주장 “자동 응답을 적용한다” 적용 대상, 예외, 테스트 여부 확인 조건을 문장 안에 넣음
비교 평가 “A가 B보다 낫다” 평가 기준과 사용 환경 확인 “이 조건에서는 A가 유리하다”로 제한
내부 결정 “다음 달부터 시행한다” 회의록, 승인자, 결정 상태 확인 결정/검토/제안 상태를 구분

이 표는 위키 문서를 읽을 때의 렌즈입니다. 문장을 하나씩 보며 “이건 어떤 유형의 주장인가?”를 먼저 판단합니다. 그다음 출처, 날짜, 조건을 확인합니다.

실습: 출처 없는 문장과 오래된 주장 표시하기

목표
위키 문서에서 바로 믿으면 위험한 문장을 찾아 표시합니다.

실행 전제

수정 예시

# LLM위키 운영 메모

LLM위키는 일반적인 파일 업로드형 질의응답이나 RAG 경험과 다른 운영 패턴이다. 원천 자료를 보존하고, LLM이 정리한 Markdown 위키를 지속적으로 갱신하는 방식에 가깝다.

이 책의 기본 구조에서는 원천 자료를 `raw/`에 보관한다. 단, 실제 폴더명과 명령은 사용하는 구현체에 따라 다를 수 있다.

Codex는 공식 문서 기준으로 `AGENTS.md`를 지침 파일로 사용한다. Claude Code는 공식 문서 기준으로 `CLAUDE.md`를 프로젝트 메모리로 사용한다.

`nvk/llm-wiki`의 최신 릴리스는 2026-05-16 확인 기준 v0.9.0으로 조사되었다. 이 버전에는 주제 아카이브 생명주기 기능이 포함되어 있다.

수정된 문서는 더 길어졌습니다. 하지만 더 믿을 수 있습니다. 좋은 운영 문서는 짧은 문서가 아니라 나중에 고칠 수 있는 문서입니다. 출처, 날짜, 범위가 있으면 다음 점검자가 같은 판단을 다시 확인할 수 있습니다.

실무에서 쓰는 표시 규칙

LLM위키 문서에는 복잡한 신뢰도 체계를 처음부터 넣을 필요가 없습니다. 다음 네 가지 표시만으로도 충분히 시작할 수 있습니다.

표시 뜻 사용 예
확인됨 원천 자료와 일치함 회의록에 명시된 결정 사항
확인 필요 근거가 없거나 부족함 반복 문의 비율, 고객 수요 추정
날짜 필요 시간이 지나면 바뀔 수 있음 최신 버전, 가격, 정책, 일정
범위 제한 특정 조건에서만 맞음 “Codex 기준”, “내부 테스트 기준”

이 표시는 위키를 무겁게 만들기 위한 장식이 아닙니다. 나중에 LLM에게 다시 질문할 때 답변 품질을 높이는 재료입니다. 확인 필요가 붙은 문장은 다음 리서치 과제가 됩니다. 날짜 필요가 붙은 문장은 주간 점검 대상이 됩니다. 범위 제한이 붙은 문장은 보고서에서 과도한 단정을 막아 줍니다.

검증을 업무 루틴에 넣기

LLM위키 점검은 한 번에 몰아서 하면 부담이 큽니다. 몇 달 동안 쌓인 문서를 한꺼번에 검토하려고 하면 시작하기 어렵습니다. 더 나은 방법은 검증을 작은 루틴으로 나누는 것입니다.

가장 단순한 루틴은 세 번 확인하는 것입니다. 자료를 넣을 때 한 번, 산출물을 만들기 전에 한 번, 주기적으로 한 번입니다.

자료를 넣을 때는 출처와 확인 날짜를 남깁니다. 산출물을 만들기 전에는 핵심 주장만 다시 봅니다. 주기 점검에서는 오래된 주장, 출처 없는 문장, 연결되지 않은 문서를 찾습니다. 이 세 루틴만 있어도 위키의 신뢰도는 크게 달라집니다.

학습자료: 위키 검증 루틴

이 도해에서 검증은 마지막 단계가 아닙니다. 중간에 계속 끼어 있습니다. 자료를 넣을 때 검증하고, 산출물을 만들 때 검증하고, 주간 점검으로 다시 검증합니다. 이렇게 해야 위키가 “한때 잘 정리된 문서”가 아니라 “계속 믿고 쓸 수 있는 업무 시스템”이 됩니다.

실습: 15분 위키 점검 루틴 만들기

목표
매주 한 번 실행할 수 있는 작은 점검 루틴을 만듭니다.

실행 전제
위키 문서가 3개 이상 있으면 자신의 위키에 적용합니다. 아직 위키가 없다면 아래 체크리스트만 읽고, 나중에 첫 위키를 만든 뒤 사용합니다.

성공 기준
15분 안에 확인할 항목을 정하고, 점검 결과를 log.md나 운영 메모에 남깁니다.

15분 점검표

시간 할 일 확인 질문 결과 기록
3분 최근 추가 문서 보기 출처와 확인 날짜가 있는가 누락 문서 목록
4분 핵심 문서 1개 읽기 단정 문장에 근거가 있는가 확인 필요 표시
3분 오래된 주장 찾기 버전, 가격, 정책, 일정이 들어 있는가 재확인 날짜 기록
3분 연결 상태 보기 다른 문서와 링크되어 있는가 연결할 문서 후보
2분 다음 행동 정하기 무엇을 보완할 것인가 다음 점검 과제

점검 로그 예시

## [2026-05-16] weekly-check

- 점검 범위: `wiki/customer-support/` 문서 5개
- 출처 누락: `faq-automation.md`의 반복 문의 비율 문장
- 오래된 주장: `tool-setup.md`의 최신 버전 정보
- 확인 필요: 개인정보 포함 문의 자동 응답 제외 기준
- 다음 행동: 고객지원팀 회의록 원문 확인 후 `faq-automation.md` 수정

이 로그는 단순한 기록입니다. 하지만 다음 점검을 훨씬 쉽게 만듭니다. 무엇을 봤고, 무엇을 못 봤고, 다음에 무엇을 확인해야 하는지 남기기 때문입니다.

LLM에게 맡길 수 있는 점검과 사람이 해야 할 판단

LLM은 점검을 도울 수 있습니다. 출처 없는 문장을 찾고, 오래된 날짜 표현을 모으고, 서로 충돌하는 문장을 후보로 제시하는 일은 LLM에게 잘 맞습니다. 하지만 최종 판단까지 모두 맡기면 안 됩니다.

LLM은 문장이 그럴듯한지 잘 판단합니다. 그러나 실제 업무에서 그 문장이 맞는지, 조직 안에서 승인된 결정인지, 고객에게 말해도 되는 내용인지는 사람이 판단해야 합니다.

점검 작업 LLM에게 맡기기 좋은 부분 사람이 확인할 부분
출처 누락 찾기 출처 표시가 없는 문장 후보 추출 실제 원천 자료와 연결
오래된 주장 찾기 날짜, 버전, 정책 표현 탐지 최신 공식 문서 확인
모순 찾기 서로 다른 문장 후보 비교 어느 쪽이 최신 결정인지 판단
문장 고치기 단정 표현을 제한 표현으로 수정 업무상 의미가 바뀌지 않았는지 검토
산출물 검토 핵심 주장 목록화 제출해도 되는 결론인지 승인

점검 요청 프롬프트

다음 프롬프트는 특정 도구 명령이 아닙니다. Claude, Codex, ChatGPT 같은 LLM 도구에서 위키 문서를 열어 둔 뒤 사용할 수 있는 점검 요청 예시입니다.

다음 위키 문서를 점검해 주세요.

목표:
- 출처가 없는 사실 주장 찾기
- 오래되었을 가능성이 있는 주장 찾기
- 추정이 단정처럼 쓰인 문장 찾기
- 서로 충돌할 수 있는 문장 찾기

출력 형식:
| 문장 | 문제 유형 | 이유 | 수정 제안 | 확인할 원천 자료 |

규칙:
- 원천 자료나 공식 문서로 확인되지 않은 내용은 단정하지 마세요.
- 버전, 가격, 정책, 일정, 제품 기능은 확인 날짜가 필요하다고 표시하세요.
- 문장을 고칠 때는 의미를 넓히지 말고, 근거가 있는 범위로 좁히세요.

이 프롬프트를 AGENTS.md나 CLAUDE.md 같은 지침 파일에 넣어 둘 수도 있습니다. 다만 지침 파일은 LLM의 행동을 유도하는 장치입니다. 결과를 보장하지는 않습니다. 따라서 점검 결과는 항상 사람이 다시 확인해야 합니다.

8.1의 검증 포인트

이 절에서 기억할 내용은 단순합니다.

  • 위키 문서는 원본이 아니라 LLM이 만든 파생 지식입니다.
  • 매끄러운 요약일수록 조건, 날짜, 예외가 빠졌는지 확인해야 합니다.
  • 출처 없는 문장은 나중에 고칠 수 없으므로 위험합니다.
  • 최신성이 필요한 주장에는 확인 날짜를 붙입니다.
  • 검증은 한 번에 몰아서 하지 말고 자료 추가, 산출물 작성, 주간 점검에 나눠 넣습니다.
  • LLM은 점검 후보를 찾는 데 유용하지만 최종 판단은 사람이 해야 합니다.

다음 절에서는 이 원칙을 바탕으로 실제 정리와 감사 흐름을 만듭니다. 형식 점검, 근거 점검, 구조 점검을 나누어 위키를 관리 가능한 상태로 유지하는 방법을 다룹니다.
