5.1 자료를 넣기 전에 정할 기준

자료를 많이 넣는다고 좋은 LLM위키가 되지는 않습니다. 오히려 원본, 요약, 추측, 오래된 정보가 한곳에 섞이면 나중에 답을 검증하기 어려워집니다.

5.1에서는 자료를 넣기 전에 정해야 할 기준을 다룹니다. 이 기준이 있어야 5.2에서 웹 문서, 업무 메모, 회의록을 넣을 때 흔들리지 않습니다. 목표는 단순합니다. “무엇을 넣을지”보다 먼저 “어떤 상태로 넣고, 무엇은 넣지 않을지”를 정하는 것입니다.

원천 자료와 요약문 분리하기

LLM위키에서 가장 먼저 지켜야 할 원칙은 원천 자료와 요약문을 섞지 않는 것입니다. 원천 자료는 판단의 기준점입니다. 요약문은 원천 자료를 읽고 다시 쓰기 좋게 정리한 파생 문서입니다.

예를 들어 회의록 원문, 웹 문서 캡처, PDF에서 추출한 텍스트, 인터뷰 메모는 원천 자료입니다. 반면 “이번 회의의 결정 사항”, “고객 문의 자동화의 핵심 개념”, “도입 검토 요약”은 요약문입니다.

둘을 같은 파일에 섞으면 다음 문제가 생깁니다.

  • 원문에 있던 말과 LLM이 정리한 말을 구분하기 어렵습니다.
  • 나중에 요약이 틀렸는지 확인할 기준이 사라집니다.
  • 오래된 요약이 최신 원문처럼 읽힐 수 있습니다.
  • 다른 사람이 위키를 볼 때 무엇을 믿어도 되는지 판단하기 어렵습니다.

Karpathy의 LLM Wiki 아이디어 문서도 원천 자료, 위키, 스키마를 분리된 층으로 설명합니다. 이 책에서는 이를 실무적으로 raw/, wiki/, rules 또는 지침 파일로 나누어 다룹니다. 단, 이 폴더 이름은 패턴을 설명하기 위한 예시입니다. 특정 구현체의 필수 구조라고 단정하지 않습니다.

학습자료: 원천 자료와 요약문의 위치

아래 도해는 자료가 LLM위키 안에서 어떤 경로로 움직이는지 보여 줍니다.

이 흐름에서 raw/는 원본을 보관하는 곳입니다. 가능한 한 원문을 그대로 둡니다. 오탈자를 고치거나 문장을 다듬고 싶어도 원본 파일을 직접 고치지 않는 편이 안전합니다. 수정이 필요하면 별도 메모를 남깁니다.

wiki/는 다시 쓰기 좋은 지식층입니다. 원문을 그대로 복사하는 공간이 아닙니다. 여기에는 핵심 개념, 결정 사항, 반복 질문에 대한 답, 업무 규칙, 확인 필요 항목을 정리합니다.

중요한 점은 wiki/ 문서가 언제나 raw/로 돌아갈 수 있어야 한다는 것입니다. 위키 문서에 “근거: raw/meeting-2026-05-16.md”처럼 원천 자료를 남기면 나중에 답변을 검증할 수 있습니다.

실습: 원본과 요약을 분리하는 최소 구조 만들기

이 실습은 도구 설치 없이 폴더와 Markdown 파일만 사용합니다. macOS, Linux, WSL처럼 bash 또는 zsh를 쓸 수 있는 환경을 전제로 합니다.

목표
회의록 원문과 요약문을 다른 위치에 저장합니다.

실행 전제
터미널에서 $HOME 아래에 폴더를 만들 수 있어야 합니다. 이미 같은 폴더가 있으면 덮어쓰지 않도록 중단합니다.

실행 코드

BASE="$HOME/llm-wiki-5-1-source-separation"

if [ -e "$BASE" ]; then
  echo "이미 실습 폴더가 있습니다. BASE 값을 바꾸고 다시 실행하세요." >&2
  exit 1
fi

mkdir -p "$BASE/raw/meetings" "$BASE/wiki/decisions"

cat > "$BASE/raw/meetings/2026-05-16-weekly.md" <<'EOF'
# 주간 회의 원문

일시: 2026-05-16
참석자: 기획, 운영, 개발

논의:
- 고객 문의 분류 기준이 팀마다 다르다.
- 반복 문의는 자동 응답 후보로 모은다.
- 단, 환불과 개인정보 요청은 자동 응답에서 제외한다.
- 다음 주까지 최근 문의 30건을 샘플로 검토한다.
EOF

cat > "$BASE/wiki/decisions/customer-inquiry-automation.md" <<'EOF'
# 고객 문의 자동화 기준

## 한 문장 요약

반복 문의는 자동 응답 후보로 모으되, 환불과 개인정보 요청은 제외한다.

## 근거

- 원천 자료: `raw/meetings/2026-05-16-weekly.md`
- 확인 날짜: 2026-05-16
- 자료 성격: 내부 회의록 예시

## 확인된 내용

- 팀마다 고객 문의 분류 기준이 다르다.
- 반복 문의는 자동 응답 후보로 모은다.
- 환불과 개인정보 요청은 자동 응답에서 제외한다.
- 최근 문의 30건을 샘플로 검토한다.

## 확인 필요

- 자동 응답 후보의 구체적인 분류표
- 환불 문의와 개인정보 요청의 세부 처리 기준
EOF

find "$BASE" -maxdepth 3 -type f | sort

예상 결과

/Users/사용자명/llm-wiki-5-1-source-separation/raw/meetings/2026-05-16-weekly.md
/Users/사용자명/llm-wiki-5-1-source-separation/wiki/decisions/customer-inquiry-automation.md

예상 결과의 사용자명 부분은 실행 환경에 따라 다릅니다. 중요한 것은 원문이 raw/meetings/에 있고, 요약문이 wiki/decisions/에 있다는 점입니다.

이 실습을 끝내면 LLM에게 “이 회의록을 요약해 줘”라고만 요청하지 않게 됩니다. 대신 “원문은 보존하고, 요약문에는 근거와 확인 필요 항목을 남겨 줘”라고 요청할 수 있습니다.

소제목: 요약문에 반드시 남길 정보

요약문에는 최소한 다음 정보가 있어야 합니다.

항목 이유 예시
한 문장 요약 문서의 용도를 빠르게 파악합니다. 반복 문의 자동화 기준
원천 자료 검증할 기준점을 남깁니다. raw/meetings/2026-05-16-weekly.md
확인 날짜 정보의 시점을 드러냅니다. 2026-05-16
확인된 내용 원문에서 근거를 찾을 수 있는 내용을 둡니다. 환불 문의는 자동 응답 제외
확인 필요 아직 단정하면 안 되는 내용을 분리합니다. 개인정보 요청 세부 기준

이 표는 위키 문서를 길게 만들기 위한 형식이 아닙니다. 나중에 질문할 때 LLM이 근거가 있는 내용과 없는 내용을 구분하도록 돕는 장치입니다.

특히 “확인 필요” 항목은 중요합니다. LLM위키에서 위험한 문서는 틀린 문서만이 아닙니다. 근거가 약한데도 확정된 것처럼 보이는 문서가 더 위험할 수 있습니다.

신뢰할 자료 고르기

LLM위키에 넣을 자료는 모두 같은 무게를 갖지 않습니다. 공식 문서, 내부 정책, 회의록, 개인 메모, 블로그 글은 성격이 다릅니다. 자료의 성격을 구분하지 않으면 LLM이 약한 근거를 강한 주장처럼 사용할 수 있습니다.

신뢰할 자료를 고른다는 말은 “유명한 자료만 넣는다”는 뜻이 아닙니다. 업무에 필요한 자료를 고르되, 자료마다 신뢰도를 표시하자는 뜻입니다.

예를 들어 도구의 설치 방법, 명령어, 버전, 보안 정책은 공식 문서나 릴리스 노트를 우선해야 합니다. 반면 사용 후기, 실패 사례, 팀의 불편함은 블로그나 내부 메모도 중요한 자료가 될 수 있습니다. 다만 이 경우에는 “공식 사실”이 아니라 “경험 사례”로 표시해야 합니다.

학습자료: 자료 신뢰도 판단표

다음 표는 LLM위키에 넣을 자료를 고를 때 사용할 수 있는 간단한 기준입니다.

자료 유형 신뢰도 판단 위키에서 쓰는 방식 주의할 점
공식 문서 가장 우선 확인 기능, 명령, 정책 설명의 근거 갱신일과 버전 확인
릴리스 노트 버전 변화 확인 최신 변경점, 제거된 기능 확인 구버전 설명과 충돌 가능
표준 문서, 논문 개념과 한계 설명 기술 배경과 비교 근거 적용 범위를 과장하지 않기
내부 정책 문서 조직 기준 확인 업무 규칙, 승인 기준 최신본 여부 확인
회의록 결정과 맥락 확인 누가 무엇을 결정했는지 기록 발언과 결정 구분
개인 메모 문제 발견 질문 후보, 가설, 불편함 기록 사실처럼 단정하지 않기
블로그, 튜토리얼 사용 사례 참고 보조 설명, 실무 팁 공식 자료와 대조

이 표는 자료를 넣을지 말지 판단하는 필터입니다. 모든 자료를 버리자는 뜻이 아닙니다. 자료마다 “어떤 종류의 근거로 쓸 수 있는가”를 정하자는 뜻입니다.

예를 들어 어떤 블로그에서 “이 도구의 A 명령은 더 이상 쓰지 않는다”고 설명했다면, 그 문장만으로 책이나 위키에 단정하면 위험합니다. 공식 릴리스 노트나 README에서 같은 변경을 확인해야 합니다. 반대로 “A 명령을 쓰다가 이런 오류를 만났다”는 경험 사례라면 블로그도 쓸모가 있습니다. 이때는 “공식 변경 사항”이 아니라 “사용자가 겪은 문제 사례”로 분류합니다.

소제목: 신뢰도 등급을 너무 복잡하게 만들지 않기

처음부터 5단계, 10단계 신뢰도 체계를 만들 필요는 없습니다. LLM 도구를 가볍게 써 본 독자라면 다음 3단계로 충분합니다.

등급 의미 문서에 쓰는 표현
높음 공식 문서, 릴리스 노트, 원문 자료로 확인됨 “공식 문서 기준”, “회의록 원문 기준”
중간 신뢰할 만한 보조 자료이나 원문 대조가 필요함 “보조 자료 기준”, “추가 확인 필요”
낮음 개인 경험, 추정, 미확인 메모 “가설”, “확인 필요”, “참고 의견”

LLM위키의 목적은 모든 자료를 학술 논문처럼 평가하는 것이 아닙니다. 나중에 LLM이 답을 만들 때 “이 문장은 강하게 말해도 되는가?”를 판단할 수 있게 하는 것입니다.

실습: 자료 후보에 신뢰도 붙이기

이번 실습은 코드가 아니라 표를 채우는 작업입니다. 아직 자료를 실제로 모으지 않아도 됩니다. 앞으로 넣을 자료 후보를 먼저 분류합니다.

목표
자료 후보를 신뢰도와 용도에 따라 나눕니다.

실행 전제
자신의 업무에서 자주 참고하는 자료 5개를 떠올릴 수 있으면 됩니다.

작성 예시

| 자료 후보 | 자료 유형 | 신뢰도 | 위키에서 쓸 용도 | 확인 필요 |
|---|---|---|---|---|
| 제품 공식 도움말 | 공식 문서 | 높음 | 기능 설명, 제한 사항 | 갱신일 |
| 2026-05-16 주간 회의록 | 회의록 | 높음 | 팀 결정 사항 | 참석자 확인 |
| 고객 문의 샘플 30건 | 내부 데이터 | 중간 | 분류 기준 만들기 | 개인정보 제거 여부 |
| 동료가 작성한 자동화 메모 | 개인 메모 | 낮음 | 아이디어 후보 | 실제 적용 결과 |
| 외부 블로그의 도구 사용기 | 블로그 | 중간 | 실패 사례 참고 | 공식 문서 대조 |

이 표를 만들면 자료를 넣을 때 LLM에게 더 정확히 지시할 수 있습니다.

다음 자료 후보를 LLM위키에 넣기 전에 분류해 주세요.
공식 문서, 내부 결정, 개인 메모, 보조 사례를 구분하고
각 항목에 신뢰도와 확인 필요 사항을 표시해 주세요.

이 요청은 단순 요약보다 안전합니다. LLM이 자료를 읽기 전에 자료의 성격부터 나누게 만들기 때문입니다.

소제목: 최신성이 중요한 자료 표시하기

모든 자료가 같은 속도로 낡지는 않습니다. 팀의 회의 결정, 제품 가격, API 명령어, 설치 방법, 법적 기준, 보안 정책은 빠르게 바뀔 수 있습니다. 이런 자료는 위키에 넣을 때 최신성 표시가 필요합니다.

반대로 업무 원칙, 문제 배경, 고객 불편 유형, 개념 정의는 비교적 천천히 바뀔 수 있습니다. 물론 이 경우에도 출처는 필요합니다. 다만 매번 최신 릴리스를 확인해야 하는 자료와 같은 방식으로 다룰 필요는 없습니다.

다음처럼 표시하면 충분합니다.

## 최신성

- 최신성 중요도: 높음
- 마지막 확인 날짜: 2026-05-16
- 다시 확인할 시점: 도구 업그레이드 전, 실습 원고 배포 전

이런 표시가 있으면 나중에 “이 명령어가 아직 맞는가?”를 빠르게 점검할 수 있습니다. 특히 LLM위키 구현체는 변경 속도가 빠를 수 있으므로, 명령어와 설치 방법은 작성 시점과 확인 출처를 함께 남겨야 합니다.

수집 범위와 제외 범위 정하기

자료를 넣기 전에 가장 자주 빠지는 기준이 범위입니다. 어떤 자료를 넣을지는 정하지만, 어떤 자료를 넣지 않을지는 정하지 않는 경우가 많습니다.

범위가 없으면 위키는 금방 넓어집니다. “업무 자동화”라는 주제로 시작했는데, 생산성 앱, 프롬프트 모음, 고객 지원 정책, 개발 환경 설정, 팀 운영 방식이 모두 들어올 수 있습니다. 자료가 많아졌지만 질문에는 더 약해지는 상태가 됩니다.

LLM위키는 처음부터 크게 만들 필요가 없습니다. 작은 질문 하나에 답할 수 있는 범위부터 시작하는 편이 좋습니다.

예를 들어 “업무 자동화 위키”보다 “고객 문의 분류 자동화 위키”가 낫습니다. “회사 지식 위키”보다 “주간 회의록에서 실행 항목을 뽑는 위키”가 낫습니다.

학습자료: 수집 범위 결정 흐름

아래 도해는 자료를 넣기 전 범위를 정하는 순서입니다.

이 흐름에서 출발점은 자료가 아니라 질문입니다. “무엇을 모을까?”보다 “이 위키가 어떤 질문에 답해야 하는가?”를 먼저 정합니다.

예를 들어 질문이 “반복 고객 문의를 자동 응답 후보로 분류하려면 어떤 기준이 필요한가?”라면 필요한 자료는 다음처럼 좁아집니다.

  • 최근 고객 문의 샘플
  • 현재 사용 중인 문의 분류표
  • 자동 응답에서 제외해야 할 정책
  • 관련 회의록의 결정 사항
  • 고객 응대 품질 기준

반대로 다음 자료는 당장 제외할 수 있습니다.

  • 전체 고객 데이터베이스
  • 상담원 개인 평가 자료
  • 제품 로드맵 전체
  • 자동화와 관련 없는 마케팅 문서
  • 개인정보가 제거되지 않은 원문

제외 범위는 위키의 품질을 떨어뜨리는 제약이 아닙니다. 오히려 질문에 집중하게 만드는 장치입니다.

소제목: 포함 범위와 제외 범위 예시

다음 표는 “고객 문의 분류 자동화”라는 작은 LLM위키를 만들 때의 기준 예시입니다.

기준 포함 제외
주제 반복 문의 분류, 자동 응답 후보, 제외 기준 전체 고객 지원 전략
기간 최근 3개월 문의 샘플 1년 이상 지난 예외 사례
자료 회의록, 분류표, FAQ, 정책 문서 개인 메신저 대화, 확인 안 된 구두 전달
민감 정보 개인정보 제거 후 요약된 샘플 이름, 전화번호, 이메일, 주문번호 원문
산출물 분류 기준표, 확인 질문, 실행 계획 자동 응답 문구 전체 배포본
확인 필요 법무, 보안, 고객지원 책임자 검토 항목 검토 없이 확정된 운영 정책

이 표는 실제 조직의 정책을 대신하지 않습니다. 개인정보, 계약 정보, 고객 데이터, 내부 기밀은 조직의 보안 기준을 먼저 따라야 합니다. 기준을 모를 때는 LLM위키에 넣지 않는 편이 안전합니다.

실습: 내 위키의 수집 기준 카드 만들기

이번 실습에서는 앞으로 자료를 넣기 전에 볼 기준 카드를 만듭니다. 이 카드는 AGENTS.md, CLAUDE.md, 별도 rules.md 같은 운영 규칙 문서에 넣을 수 있습니다. 단, 도구별 지침 파일은 행동을 강제하지 않습니다. LLM이 따르도록 유도하는 장치이며, 결과는 사람이 검토해야 합니다.

목표
자료를 넣기 전에 포함 범위, 제외 범위, 민감 정보 기준을 한곳에 정리합니다.

실행 전제
위키 주제를 하나 정해야 합니다. 예시는 “고객 문의 분류 자동화”입니다.

작성 예시

# 자료 수집 기준 카드

## 위키 주제

고객 문의 분류 자동화

## 이 위키가 답해야 할 질문

반복 고객 문의를 자동 응답 후보로 분류하려면 어떤 기준이 필요한가?

## 포함 범위

- 최근 3개월 고객 문의 샘플
- 현재 문의 분류표
- 자동 응답 제외 기준
- 고객지원팀 회의록
- FAQ와 운영 정책 문서

## 제외 범위

- 개인정보가 제거되지 않은 원문
- 상담원 개인 평가 자료
- 자동화와 관련 없는 마케팅 문서
- 공식 확인이 끝나지 않은 구두 전달
- 1년 이상 지난 예외 사례

## 민감 정보 처리

- 이름, 전화번호, 이메일, 주문번호는 원문 그대로 넣지 않는다.
- 고객 발화는 필요한 경우 익명화한 예시로 바꾼다.
- 조직의 보안 기준이 불명확하면 수집하지 않는다.

## 신뢰도 표시

- 공식 정책과 최신 분류표: 높음
- 회의록과 내부 메모: 중간 이상, 결정과 의견을 구분
- 개인 메모와 외부 블로그: 낮음 또는 보조 근거

## 요약문 작성 규칙

- 원천 자료 경로를 남긴다.
- 확인 날짜를 남긴다.
- 확인된 내용과 확인 필요를 분리한다.
- 최신성이 필요한 내용은 다시 확인할 시점을 적는다.

성공 기준
이 카드만 보고도 어떤 자료를 넣고, 어떤 자료를 보류해야 하는지 판단할 수 있어야 합니다.

이 실습을 끝내면 다음 절에서 자료를 수집할 때 기준이 생깁니다. 자료를 넣을 때마다 새로 고민하지 않아도 됩니다.

소제목: 범위가 흔들릴 때 묻는 세 가지 질문

자료를 넣다 보면 애매한 자료가 생깁니다. 넣자니 넓어지고, 빼자니 아쉬운 자료입니다. 이때는 다음 세 가지 질문을 사용합니다.

질문 넣어도 되는 신호 보류해야 하는 신호
이 자료가 현재 위키 질문에 직접 답하는가? 답변의 근거가 된다 배경지식 정도에 그친다
나중에 원문으로 검증할 수 있는가? 출처, 날짜, 작성자가 있다 전달자만 있고 원문이 없다
민감 정보 처리가 끝났는가? 익명화, 권한 확인이 끝났다 원문에 개인정보가 남아 있다

세 질문 중 하나라도 “아니오”라면 바로 넣지 않아도 됩니다. inbox/나 review-needed/ 같은 보류 공간을 따로 두고, 나중에 검토할 수 있습니다.

보류는 실패가 아닙니다. 오히려 위키가 섞이지 않도록 막는 운영 방법입니다.

5.1의 검증 포인트

자료를 넣기 전 기준은 복잡할 필요가 없습니다. 대신 매번 확인할 수 있어야 합니다.

  • 원천 자료와 요약문을 다른 위치에 두었는가?
  • 요약문에 원천 자료 경로와 확인 날짜가 있는가?
  • 자료 유형별 신뢰도를 표시했는가?
  • 공식 문서, 릴리스 노트, 내부 정책처럼 강한 근거를 우선했는가?
  • 블로그, 개인 메모, 추정은 보조 근거로 표시했는가?
  • 최신성이 중요한 자료에 다시 확인할 시점을 남겼는가?
  • 포함 범위와 제외 범위를 모두 적었는가?
  • 개인정보나 내부 기밀을 그대로 넣지 않도록 기준을 세웠는가?
  • 애매한 자료를 보류할 위치를 정했는가?

이 절의 핵심은 “많이 모으기”가 아니라 “나중에 믿고 다시 쓸 수 있게 모으기”입니다. 원천 자료는 기준점으로 남기고, 요약문은 검증 가능한 형태로 만듭니다. 이 기준이 있어야 다음 절에서 자료를 실제로 수집할 때 위키가 흐트러지지 않습니다.
