8.3 주제가 늘어날 때 관리하기

LLM위키는 처음에는 작게 시작해야 합니다. 회의록 몇 개, 업무 규칙 몇 줄, 자주 묻는 질문 몇 개만 있어도 충분합니다. 문제는 잘 쓰기 시작한 뒤에 생깁니다. 주제가 늘어나면 “어디에 넣어야 하지?”, “이 주제는 아직 쓰나?”, “비슷한 위키가 두 개 아닌가?” 같은 질문이 생깁니다.

이 절에서는 주제가 늘어난 LLM위키를 관리하는 방법을 다룹니다. 핵심은 세 가지입니다. 먼저 하나의 큰 위키와 여러 주제 위키를 구분합니다. 다음으로 인벤토리로 전체 현황을 봅니다. 마지막으로 오래된 주제는 삭제하지 않고 아카이브합니다.

이 절의 도구 설명은 2026-05-16 KST에 확인한 자료를 기준으로 합니다. LLM위키는 특정 제품 하나가 아니라 지식 관리 패턴으로 설명합니다. /wiki 명령 예시는 nvk/llm-wiki v0.9.0 문서 기준이며, 설치된 도구에 따라 다를 수 있습니다.

하나의 큰 위키와 여러 주제 위키

주제가 하나일 때는 폴더 하나로 충분합니다. 예를 들어 “반복 보고서 자동화”만 다룬다면 raw/, wiki/, output/ 구조를 한 곳에 두면 됩니다.

하지만 시간이 지나면 주제가 섞입니다. 보고서 자동화, 고객 문의 분류, 회의록 요약, 채용 문서 정리, 팀 온보딩이 한 위키 안에 들어올 수 있습니다. 이때 모든 문서를 한 위키에 계속 넣으면 LLM이 맥락을 넓게 잡습니다. 답변은 길어지고, 근거는 흐려집니다.

반대로 주제마다 위키를 너무 잘게 나누면 관리 비용이 늘어납니다. 비슷한 자료가 여러 곳에 복사되고, 어느 위키가 최신인지 알기 어려워집니다. 따라서 기준이 필요합니다.

학습자료: 하나의 큰 위키와 여러 주제 위키 비교

방식 적합한 상황 장점 위험
하나의 큰 위키 주제가 작고 서로 강하게 연결될 때 찾을 곳이 하나라 단순하다 주제가 늘면 답변 맥락이 흐려진다
여러 주제 위키 업무 흐름, 독자, 자료 출처가 다를 때 질문 범위를 좁히기 쉽다 중복 문서와 관리 누락이 생길 수 있다
큰 위키 + 주제 폴더 공통 규칙은 같고 세부 주제만 다를 때 공통 기준과 주제별 맥락을 함께 유지한다 폴더 규칙이 없으면 다시 뒤섞인다

이 표는 “무조건 나누기”가 아니라 “답변 품질과 관리 비용의 균형”을 보기 위한 기준입니다. LLM위키에서는 정보가 많을수록 좋은 것이 아닙니다. 질문에 필요한 맥락만 안정적으로 제공되는 것이 더 중요합니다.

이 흐름은 새 자료를 어디에 넣을지 판단하는 최소 규칙입니다. “같은 핵심 질문인가?”를 먼저 묻습니다. 핵심 질문이 다르면 같은 폴더에 두지 않는 편이 안전합니다.

주제를 나누는 기준

주제 위키를 나눌 때는 이름보다 질문을 봐야 합니다. 폴더 이름이 비슷해도 질문이 다르면 다른 위키가 될 수 있습니다.

예를 들어 meeting-notes라는 이름만 보면 회의록 전체를 한곳에 넣고 싶어집니다. 하지만 실제 질문은 다를 수 있습니다.

자료 겉보기 주제 실제 질문 권장 위치
주간 회의록 회의록 이번 주 실행 항목은 무엇인가? 팀 운영 위키
고객 인터뷰 회의록 회의록 고객이 반복해서 겪는 문제는 무엇인가? 고객 리서치 위키
자동화 검토 회의록 회의록 자동화할 업무 후보는 무엇인가? 업무 자동화 위키

자료 형식이 같아도 업무 질문이 다르면 다른 주제로 다루는 편이 좋습니다. LLM은 파일 이름보다 주변 맥락의 영향을 크게 받습니다. 질문의 목적이 다르면 정리 방식도 달라집니다.

실습: 주제 분리 기준 만들기

목표
현재 위키에 새 주제를 넣을지, 새 주제 위키로 나눌지 판단하는 기준을 만듭니다.

실행 전제
Markdown 편집기만 있으면 됩니다. 터미널을 사용하지 않아도 됩니다.

성공 기준
새 자료가 들어왔을 때 답할 수 있는 기준 질문 5개를 작성합니다.

# 주제 분리 기준

## 새 주제 위키로 나눌 조건

- 기존 위키의 핵심 질문과 다르다.
- 자료를 읽는 사람이 다르다.
- 출처나 보안 등급이 다르다.
- 산출물 형식이 다르다.
- 3개월 뒤에도 독립적으로 다시 물어볼 가능성이 높다.

## 기존 위키에 넣을 조건

- 같은 업무 판단에 계속 쓰인다.
- 같은 원천 자료 묶음에서 나온다.
- 기존 `index.md`에 자연스럽게 연결된다.
- 같은 검증 기준을 적용할 수 있다.

이 기준은 LLM에게도 줄 수 있습니다. 다만 규칙 파일은 행동을 보장하지 않습니다. AGENTS.md나 CLAUDE.md는 LLM이 따르도록 유도하는 문서입니다. 결과는 사용자가 다시 확인해야 합니다.

인벤토리로 전체 현황 보기

주제 위키가 세 개를 넘으면 기억으로 관리하기 어렵습니다. 이때 필요한 것이 인벤토리입니다. 인벤토리는 위키의 “전체 목록”입니다. 단순한 파일 목록이 아니라 각 주제가 어떤 상태인지 보여 주는 운영 문서입니다.

인벤토리에는 최소한 다음 항목이 있어야 합니다.

항목 의미 예시
주제 이름 위키를 부르는 이름 work-automation
핵심 질문 이 위키가 답해야 하는 질문 반복 업무를 줄이려면 무엇부터 자동화할까?
상태 운영 중, 점검 필요, 아카이브 후보 운영 중
마지막 갱신일 최근 자료가 반영된 날짜 2026-05-16
다음 행동 이어서 해야 할 일 오래된 회의록 출처 확인
대표 산출물 위키가 만든 결과물 output/automation-plan.md

인벤토리를 만들면 “문서가 많다”는 느낌이 “관리할 수 있는 목록”으로 바뀝니다. 특히 LLM에게 질문할 때 도움이 됩니다. “전체 위키를 보고 답해 줘”가 아니라 “인벤토리에서 운영 중인 주제만 보고 답해 줘”처럼 범위를 좁힐 수 있습니다.

학습자료: 주제 위키 운영 인벤토리 예시

주제 핵심 질문 상태 마지막 갱신 다음 행동
업무 자동화 반복 업무를 줄이려면 무엇부터 자동화할까? 운영 중 2026-05-16 자동화 후보 우선순위 갱신
고객 문의 분류 문의 유형을 어떻게 나누고 대응할까? 점검 필요 2026-04-28 최신 문의 샘플 추가
팀 온보딩 새 팀원이 무엇을 먼저 알아야 할까? 운영 중 2026-05-10 FAQ 문서 연결
2025년 캠페인 회고 작년 캠페인에서 무엇을 배웠나? 아카이브 후보 2025-12-20 보존 여부 결정

이 표에서 중요한 열은 상태와 다음 행동입니다. 마지막 갱신일만 있으면 오래된 주제를 알 수 있습니다. 하지만 다음 행동이 없으면 실제 운영으로 이어지지 않습니다.

실습: Markdown 인벤토리 만들기

목표
여러 주제 위키의 상태를 한눈에 볼 수 있는 inventory.md를 만듭니다.

실행 전제
macOS, Linux, Windows WSL 같은 셸 환경을 가정합니다. mkdir, printf, find 명령을 사용할 수 있어야 합니다.

성공 기준
llm-wiki-topics/inventory.md 파일이 만들어지고, 세 개의 주제가 표로 기록됩니다.

BASE="$HOME/llm-wiki-topics"

if [ -e "$BASE" ]; then
  echo "이미 실습 폴더가 있습니다. BASE 값을 바꾸고 다시 실행하세요." >&2
  exit 1
fi

mkdir -p "$BASE/topics/work-automation"
mkdir -p "$BASE/topics/customer-inquiry"
mkdir -p "$BASE/topics/team-onboarding"

printf '%s\n' \
'# LLM위키 인벤토리' \
'' \
'| 주제 | 핵심 질문 | 상태 | 마지막 갱신 | 다음 행동 |' \
'|---|---|---|---|---|' \
'| work-automation | 반복 업무를 줄이려면 무엇부터 자동화할까? | 운영 중 | 2026-05-16 | 자동화 후보 우선순위 갱신 |' \
'| customer-inquiry | 문의 유형을 어떻게 나누고 대응할까? | 점검 필요 | 2026-04-28 | 최신 문의 샘플 추가 |' \
'| team-onboarding | 새 팀원이 무엇을 먼저 알아야 할까? | 운영 중 | 2026-05-10 | FAQ 문서 연결 |' \
> "$BASE/inventory.md"

find "$BASE" -maxdepth 3 -print | sort

예상 결과는 다음과 비슷합니다.

/Users/사용자명/llm-wiki-topics
/Users/사용자명/llm-wiki-topics/inventory.md
/Users/사용자명/llm-wiki-topics/topics
/Users/사용자명/llm-wiki-topics/topics/customer-inquiry
/Users/사용자명/llm-wiki-topics/topics/team-onboarding
/Users/사용자명/llm-wiki-topics/topics/work-automation

이 실습은 단순한 목록 만들기처럼 보입니다. 하지만 실제 효과는 큽니다. 인벤토리가 있으면 “어떤 위키가 살아 있는가?”를 매번 기억하지 않아도 됩니다. LLM에게 작업을 맡길 때도 먼저 인벤토리를 읽히면 범위를 좁힐 수 있습니다.

LLM에게 인벤토리를 읽히는 요청 예시

인벤토리는 사람이 보기 위한 문서이면서 LLM에게 줄 운영 맥락이기도 합니다. 다음처럼 요청할 수 있습니다.

inventory.md를 읽고 상태가 "운영 중"인 주제만 골라 주세요.
각 주제마다 다음 행동이 구체적인지 평가해 주세요.
"점검 필요" 주제는 어떤 원천 자료가 부족한지 질문 목록으로 정리해 주세요.
단, inventory.md에 없는 주제는 새로 추측하지 마세요.

이 요청의 핵심은 “없는 주제를 새로 추측하지 말라”는 조건입니다. LLM위키 운영에서는 빠진 정보를 그럴듯하게 채우는 것이 가장 위험합니다. 인벤토리에 없는 것은 없는 것으로 남겨야 합니다.

도구형 인벤토리와 수동 인벤토리

nvk/llm-wiki 같은 구현체는 인벤토리 기능을 제공할 수 있습니다. 연구 자료 기준으로 nvk/llm-wiki v0.9.0에는 inventory, archive 같은 운영 기능이 포함되어 있습니다. 다만 /wiki 명령은 OpenAI나 Anthropic의 공식 내장 명령이 아닙니다. 해당 저장소의 플러그인 문서와 설치된 버전을 확인해야 합니다.

따라서 이 책에서는 수동 Markdown 인벤토리를 기본으로 둡니다. 도구형 인벤토리는 나중에 붙여도 됩니다.

구분 수동 Markdown 인벤토리 도구형 인벤토리
시작 난이도 낮다 도구 설치가 필요하다
투명성 파일을 직접 읽을 수 있다 도구 출력 형식을 확인해야 한다
자동화 직접 갱신해야 한다 일부 갱신을 명령으로 처리할 수 있다
권장 시점 처음부터 주제가 많아진 뒤

처음부터 도구 기능을 모두 쓰려고 하면 운영보다 설치에 시간이 더 걸릴 수 있습니다. 먼저 inventory.md 하나로 상태를 기록해 보세요. 기록 방식이 안정된 뒤 자동화를 붙이는 편이 안전합니다.

오래된 주제 아카이브하기

오래된 주제는 삭제하기보다 아카이브하는 편이 좋습니다. LLM위키에서 오래된 자료는 두 가지 위험을 만듭니다.

첫째, 현재 질문에 낡은 근거가 섞일 수 있습니다. 예를 들어 2025년 캠페인 회고가 2026년 실행 계획에 계속 영향을 주면 잘못된 판단이 나올 수 있습니다.

둘째, 오래된 주제가 목록을 어지럽힙니다. 운영 중인 주제와 끝난 주제가 섞이면 LLM에게 줄 맥락이 불필요하게 커집니다.

아카이브는 삭제가 아닙니다. 기본 작업 맥락에서 빼되, 필요할 때 다시 찾을 수 있게 보존하는 일입니다.

학습자료: 운영 중 주제와 아카이브 주제의 위치

이 도해에서 .archive/ 아래 주제는 사라진 것이 아닙니다. 기본 질문 맥락에서 빠졌을 뿐입니다. 필요하면 다시 찾아볼 수 있어야 합니다.

아카이브할 주제를 고르는 기준

아카이브 기준은 날짜 하나로만 정하면 안 됩니다. 오래됐지만 계속 쓰는 기준도 있고, 최근 문서지만 더 이상 의미 없는 실험 기록도 있습니다.

아카이브 후보 판단 기준 처리
끝난 프로젝트 산출물이 확정됐고 새 질문이 거의 없다 아카이브
예전 리서치 최신성이 중요하고 자료가 낡았다 아카이브 후 최신 조사 필요 표시
중복 주제 다른 위키에 흡수됐다 대표 문서만 남기고 아카이브
보안상 분리할 자료 접근 범위가 달라졌다 별도 저장소 또는 제한 공간으로 이동
자주 쓰는 기준 문서 오래됐지만 계속 참조한다 운영 중 유지, 확인 날짜 갱신

아카이브는 “이제 쓸모없다”는 판단이 아닙니다. “기본 맥락에 항상 넣을 필요는 없다”는 판단입니다.

실습: 오래된 주제 아카이브하기

목표
운영 중인 주제와 오래된 주제를 분리하고, 인벤토리에 상태를 남깁니다.

실행 전제
앞의 llm-wiki-topics 실습을 실행했거나, 같은 구조의 폴더가 있다고 가정합니다.

성공 기준
2025-campaign-review 주제가 .archive/ 아래로 이동하고, inventory.md에 아카이브 상태가 기록됩니다.

BASE="$HOME/llm-wiki-topics"

test -d "$BASE/topics" || {
  echo "먼저 인벤토리 실습을 실행하세요." >&2
  exit 1
}

mkdir -p "$BASE/topics/2025-campaign-review/wiki"
printf '%s\n' \
'# 2025년 캠페인 회고' \
'' \
'- 상태: 종료됨' \
'- 확인 필요: 2026년 계획에 그대로 적용하면 안 됨' \
> "$BASE/topics/2025-campaign-review/wiki/index.md"

mkdir -p "$BASE/topics/.archive"
mv "$BASE/topics/2025-campaign-review" "$BASE/topics/.archive/2025-campaign-review"

printf '%s\n' \
'' \
'## 아카이브 기록' \
'' \
'| 주제 | 아카이브 날짜 | 이유 | 다시 볼 조건 |' \
'|---|---|---|---|' \
'| 2025-campaign-review | 2026-05-16 | 프로젝트 종료 | 다음 캠페인 회고 비교가 필요할 때 |' \
>> "$BASE/inventory.md"

find "$BASE/topics" -maxdepth 3 -print | sort

예상 결과는 다음과 비슷합니다.

/Users/사용자명/llm-wiki-topics/topics
/Users/사용자명/llm-wiki-topics/topics/.archive
/Users/사용자명/llm-wiki-topics/topics/.archive/2025-campaign-review
/Users/사용자명/llm-wiki-topics/topics/.archive/2025-campaign-review/wiki
/Users/사용자명/llm-wiki-topics/topics/customer-inquiry
/Users/사용자명/llm-wiki-topics/topics/team-onboarding
/Users/사용자명/llm-wiki-topics/topics/work-automation

이 실습에서 중요한 부분은 mv 명령보다 아카이브 기록입니다. 주제를 옮기기만 하면 나중에 왜 옮겼는지 알 수 없습니다. 아카이브 날짜, 이유, 다시 볼 조건을 함께 남겨야 합니다.

도구형 아카이브를 쓸 때의 주의점

nvk/llm-wiki v0.9.0 릴리스에는 Topic Archive Lifecycle이 포함되어 있습니다. 조사 결과 기준으로 아카이브된 주제는 topics/.archive/ 아래에 보존되고, 기본 질의와 유지보수 맥락에서 제외됩니다. 다시 확인해야 할 때는 명시적으로 아카이브 포함 옵션이나 아카이브 조회 명령을 사용해야 합니다.

이 설명은 특정 구현체 기준입니다. 사용 중인 도구가 다르면 다음 세 가지를 확인해야 합니다.

확인할 것 이유
아카이브 위치 실제 파일이 어디로 이동하는지 알아야 백업할 수 있다
기본 검색 포함 여부 오래된 주제가 답변에 섞이는지 확인해야 한다
복구 방법 잘못 아카이브한 주제를 다시 운영 상태로 돌릴 수 있어야 한다

아카이브 기능이 있어도 삭제처럼 다루면 안 됩니다. LLM위키의 원칙은 원천 자료를 기준점으로 보존하는 것입니다. 아카이브는 맥락을 줄이는 방법이지, 근거를 없애는 방법이 아닙니다.

8.3의 검증 포인트

주제가 늘어난 LLM위키는 “문서가 많다”보다 “상태를 모른다”가 더 큰 문제입니다. 이 절을 마친 뒤에는 다음 항목을 확인합니다.

점검 항목 확인 질문
주제 분리 새 자료를 기존 위키에 넣을지 새 주제로 나눌지 판단 기준이 있는가?
인벤토리 운영 중, 점검 필요, 아카이브 후보를 한눈에 볼 수 있는가?
마지막 갱신 각 주제의 최근 갱신일이 기록되어 있는가?
다음 행동 각 주제에 이어서 할 일이 적혀 있는가?
아카이브 끝난 주제를 삭제하지 않고 기본 맥락에서 분리했는가?
재확인 조건 아카이브한 주제를 언제 다시 볼지 남겼는가?

운영 중인 위키만 LLM에게 읽히면 답변이 선명해집니다. 오래된 주제는 보존하되 기본 맥락에서 뺍니다. 인벤토리는 이 두 작업을 이어 주는 운영 장부입니다.
