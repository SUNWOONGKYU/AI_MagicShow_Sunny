3.3 이 책의 실습 환경 정하기

도구를 고르는 일은 중요하지만, 처음부터 완벽한 도구를 찾으려 하면 시작이 늦어집니다. 이 책의 실습은 특정 제품에 묶이지 않는 흐름을 먼저 익히는 데 초점을 둡니다. 작은 예제로 raw, wiki, output, 작업 규칙 파일이 제대로 작동하는지 확인한 뒤, Codex, Claude Code, 플러그인, CLI 같은 도구를 필요에 따라 얹습니다.

이 절을 끝내면 앞으로의 실습 환경을 스스로 정할 수 있습니다. 핵심은 간단합니다. 원본은 보존하고, 위키 문서는 원본을 가리키며, 작업 이력은 남깁니다. 도구가 바뀌어도 이 원칙은 유지됩니다.

작은 예제로 먼저 검증하기

LLM위키 실습은 큰 자료 묶음으로 시작하지 않습니다. 회의록 하나, 메모 하나, 짧은 웹 문서 하나면 충분합니다. 처음부터 많은 자료를 넣으면 도구 문제인지, 자료 문제인지, 질문 문제인지 구분하기 어렵습니다.

이 책의 기본 실습 환경은 다음처럼 정합니다.

항목 기본 선택 이유
저장 형식 Markdown 파일 대부분의 LLM 도구와 편집기에서 읽기 쉽습니다.
기본 구조 raw/, wiki/, output/, index.md, log.md 원본, 정리된 지식, 산출물을 분리합니다.
작업 규칙 AGENTS.md와 선택적 CLAUDE.md Codex와 Claude Code 모두에 대응하기 쉽습니다.
첫 자료 가상의 짧은 회의록 개인정보와 업무 기밀 노출을 피할 수 있습니다.
첫 검증 파일 구조, 출처, 확인 필요 항목 확인 도구보다 흐름이 제대로 잡혔는지 봅니다.

이 표에서 중요한 점은 “기능이 많은 도구”가 아니라 “작게 검증 가능한 환경”을 고른다는 것입니다. 실습 초반에는 수동 Markdown 방식으로도 충분합니다. Codex나 Claude Code를 이미 쓰고 있다면 같은 폴더를 열어 규칙 파일을 읽게 하면 됩니다.

실습: 10분짜리 미니 위키 만들기

목표
회의록 하나를 원본으로 보관하고, 그 원본을 가리키는 위키 문서를 만듭니다.

실행 전제
macOS 또는 Linux 계열 셸에서 실행합니다. Windows 사용자는 WSL, Git Bash, 또는 수동 파일 생성 방식으로 따라 할 수 있습니다. 터미널과 편집기는 UTF-8을 지원해야 합니다.

성공 기준
raw/에는 원본 회의록이 있고, wiki/에는 정리 문서가 있습니다. index.md와 log.md에는 문서 위치와 작업 이력이 남습니다.

set -eu

BASE="$HOME/llm-wiki-book-lab/tiny-meeting-wiki"

if [ -e "$BASE" ]; then
  echo "이미 실습 폴더가 있습니다: $BASE"
  echo "BASE 값을 바꾸거나 기존 폴더를 따로 보관한 뒤 다시 실행하세요."
  exit 1
fi

mkdir -p "$BASE/raw/meeting-notes" "$BASE/wiki/concepts" "$BASE/output"

cat > "$BASE/AGENTS.md" <<'EOF'
# LLM위키 실습 규칙

- raw/ 아래 원본은 임의로 수정하지 않습니다.
- wiki/ 문서는 raw/ 원본 경로를 근거로 남깁니다.
- 확인되지 않은 내용은 "확인 필요"로 표시합니다.
- 작업이 끝나면 log.md에 날짜, 작업, 바뀐 파일을 기록합니다.
EOF

cat > "$BASE/CLAUDE.md" <<'EOF'
@AGENTS.md

## Claude Code 추가 규칙

이 프로젝트에서는 AGENTS.md의 LLM위키 실습 규칙을 함께 따릅니다.
EOF

cat > "$BASE/raw/meeting-notes/2026-05-16-weekly.md" <<'EOF'
# 주간 회의 메모

날짜: 2026-05-16
주제: 고객 문의 분류 자동화

- 반복 문의가 늘어나 상담팀이 분류 기준을 매번 다시 설명하고 있다.
- 현재 분류는 환불, 배송, 계정, 기타 네 가지다.
- 다음 주에는 최근 문의 30건으로 분류 기준 초안을 검토한다.
- 개인정보가 포함된 원문은 외부 도구에 그대로 넣지 않는다.
EOF

cat > "$BASE/wiki/concepts/customer-inquiry-automation.md" <<'EOF'
# 고객 문의 분류 자동화

## 한 문장 요약

상담팀은 반복 문의를 환불, 배송, 계정, 기타로 나누는 기준을 정리하려고 한다.

## 근거

- 원천 자료: raw/meeting-notes/2026-05-16-weekly.md
- 확인 날짜: 2026-05-16
- 자료 성격: 가상 회의 메모

## 확인된 내용

- 현재 분류 후보는 환불, 배송, 계정, 기타 네 가지다.
- 다음 검토 자료는 최근 문의 30건이다.
- 개인정보가 포함된 원문은 외부 도구에 그대로 넣지 않는다.

## 확인 필요

- 최근 문의 30건의 실제 분포는 아직 확인하지 않았다.
- 자동화 도구나 모델은 아직 정하지 않았다.

## 다시 물어볼 질문

- 최근 문의 30건을 어떤 기준으로 익명화해야 할까?
- 네 가지 분류만으로 충분한지 어떻게 검증할까?
EOF

cat > "$BASE/index.md" <<'EOF'
# 미니 LLM위키 인덱스

## 개념 문서

- wiki/concepts/customer-inquiry-automation.md: 고객 문의 분류 자동화의 첫 기준 정리

## 원천 자료

- raw/meeting-notes/2026-05-16-weekly.md: 주간 회의 메모
EOF

cat > "$BASE/log.md" <<'EOF'
# 작업 로그

## [2026-05-16] ingest | 주간 회의 메모

- 원천 자료 추가: raw/meeting-notes/2026-05-16-weekly.md
- 위키 문서 추가: wiki/concepts/customer-inquiry-automation.md
- 인덱스 갱신: index.md
EOF

find "$BASE" -maxdepth 3 -print | sed "s|$BASE|.|" | sort

./CLAUDE.md

이 실습은 LLM위키의 가장 작은 단위를 보여 줍니다. 아직 자동화 도구를 쓰지 않았지만, 이미 중요한 구조가 생겼습니다. 원본은 raw/에 있고, 위키 문서는 wiki/에 있으며, 작업 이력은 log.md에 남았습니다.

Codex를 쓴다면 이 폴더를 프로젝트로 열고 AGENTS.md가 반영되는지 확인합니다. Claude Code를 쓴다면 CLAUDE.md가 AGENTS.md를 가져오도록 둡니다. 두 경우 모두 규칙 파일은 행동을 유도할 뿐입니다. 결과가 실제로 규칙을 지켰는지는 사용자가 확인해야 합니다.

도구가 바뀌어도 유지되는 핵심 흐름

LLM위키 도구는 계속 바뀝니다. 어떤 도구는 플러그인으로 동작하고, 어떤 도구는 CLI 명령을 제공합니다. 어떤 환경에서는 그냥 Markdown 파일과 LLM 대화만으로 충분합니다.

그래도 핵심 흐름은 거의 같습니다. 이 책에서는 그 흐름을 자료 넣기 → 묻기 → 점검하기로 다룹니다. Karpathy의 LLM Wiki 원문에서는 이를 ingest, query, lint라는 작업으로 설명합니다.

학습자료: 도구와 무관한 LLM위키 흐름

이 도해에서 raw/는 기준점입니다. LLM이 만든 위키 문서가 아무리 그럴듯해도 원본을 대신하지 않습니다. wiki/는 반복해서 읽고 묻기 좋은 정리층입니다. index.md와 log.md는 길을 잃지 않게 해 주는 안내판과 기록장입니다.

AGENTS.md나 CLAUDE.md는 작업 기준을 알려 줍니다. 예를 들어 “원본을 수정하지 말 것”, “출처를 남길 것”, “확인되지 않은 내용은 확인 필요로 표시할 것” 같은 규칙을 적습니다. 다만 이 파일들은 강제 장치가 아닙니다. 결과물 검증은 여전히 실습의 일부입니다.

실습: 같은 흐름을 세 가지 방식으로 말해 보기

목표
수동 Markdown, Codex, Claude Code, 플러그인 방식이 같은 흐름을 공유한다는 점을 확인합니다.

실행 전제
앞의 미니 위키 폴더가 있으면 좋습니다. 없으면 표만 읽고 자신의 도구에 맞는 열을 고르면 됩니다.

성공 기준
내가 사용할 도구에서 raw, wiki, log, 검증에 해당하는 행동을 말할 수 있습니다.

흐름 수동 Markdown Codex 사용 시 Claude Code 사용 시 nvk/llm-wiki 플러그인 사용 시
작업 기준 읽기 AGENTS.md를 직접 확인 AGENTS.md 기준으로 요청 CLAUDE.md 기준으로 요청 플러그인 지침과 주제 위키 규칙 확인
자료 넣기 raw/에 파일 저장 폴더를 열고 자료 처리 요청 폴더를 열고 자료 처리 요청 /wiki:ingest 계열 명령 사용
위키 정리 wiki/ 문서 직접 작성 LLM에게 문서 갱신 요청 LLM에게 문서 갱신 요청 /wiki:compile 또는 관련 흐름 사용
질문하기 문서를 읽고 질문 작성 위키 문서 근거로 답변 요청 위키 문서 근거로 답변 요청 /wiki:query 계열 명령 사용
점검하기 체크리스트로 수동 점검 출처, 확인 필요, 변경 파일 점검 요청 출처, 확인 필요, 변경 파일 점검 요청 /wiki:lint, /wiki:audit 계열 명령 사용
산출물 만들기 output/에 결과 저장 보고서나 계획 초안 요청 보고서나 계획 초안 요청 /wiki:output 계열 명령 사용

이 표는 도구의 우열을 가리기 위한 것이 아닙니다. 앞으로 책에서 설명할 작업을 어떤 환경에서도 번역할 수 있게 해 주는 기준표입니다.

예를 들어 다음 요청은 특정 도구에 덜 묶인 표현입니다.

이 폴더는 LLM위키 실습 폴더입니다.

작업 순서:
1. AGENTS.md 또는 CLAUDE.md의 규칙을 먼저 확인합니다.
2. raw/ 아래 원천 자료를 기준으로 wiki/ 문서를 점검합니다.
3. 위키 문서가 원천 자료 경로를 근거로 남겼는지 확인합니다.
4. 확인되지 않은 내용은 "확인 필요"로 표시합니다.
5. 변경한 파일과 이유를 log.md에 남길 항목으로 정리합니다.

질문:
고객 문의 분류 자동화 실습에서 다음에 확인해야 할 질문 3개를 제안해 주세요.
각 질문마다 근거 파일과 확인 필요 여부를 함께 써 주세요.

좋은 결과는 근거 파일을 함께 제시합니다. “고객 문의가 많다”처럼 넓은 말만 반복하지 않고, raw/meeting-notes/2026-05-16-weekly.md에서 확인한 내용과 아직 확인하지 않은 내용을 나눕니다.

이 실습을 끝내면 도구 설명을 읽을 때 덜 흔들립니다. 명령어가 바뀌어도 “이 명령은 자료 넣기인가, 질문하기인가, 점검하기인가?”라고 판단할 수 있기 때문입니다.

실습 전 준비 체크리스트

이제 4장부터 실제 주제 위키를 만들기 시작합니다. 그전에 실습 환경을 확정해야 합니다. 여기서 말하는 환경은 거창한 개발 환경이 아닙니다. “어디에 파일을 둘지”, “어떤 LLM 도구로 읽을지”, “민감한 자료를 어떻게 피할지”를 정하는 일입니다.

학습자료: 실습 전 준비 체크리스트

준비 항목 확인할 내용 통과 기준
실습 폴더 책 실습 전용 폴더를 만들었는가 예제와 실제 업무 자료가 섞이지 않는다
원천 자료 정책 어떤 자료를 raw/에 넣을지 정했는가 첫 실습에는 가상 자료나 익명화 자료만 쓴다
Markdown 편집기 .md 파일을 열고 수정할 수 있는가 index.md, log.md를 직접 확인할 수 있다
LLM 도구 Codex, Claude Code, 웹 기반 LLM 중 무엇을 쓸지 정했는가 폴더 접근 가능 여부를 알고 있다
작업 규칙 파일 AGENTS.md 또는 CLAUDE.md를 둘 것인가 도구에 맞는 규칙 파일을 하나 이상 둔다
출처 표기 방식 위키 문서가 원본 경로를 남기는가 원천 자료: raw/... 형식을 쓴다
확인 필요 표시 불확실한 내용을 따로 표시하는가 확인 필요 항목을 비워 두지 않는다
작업 로그 자료 추가와 문서 변경을 기록하는가 log.md에 날짜와 작업이 남는다
보안 고객 정보, 계약 정보, 개인정보를 그대로 넣지 않는가 실습 자료는 가상화하거나 익명화한다
버전 확인 플러그인이나 CLI를 쓴다면 문서를 확인했는가 README, 릴리스 노트, 설치된 도움말을 대조한다

체크리스트는 실습을 늦추기 위한 문서가 아닙니다. 중간에 막히는 지점을 줄이기 위한 장치입니다. 특히 보안과 출처 표기는 처음부터 습관으로 만들어야 합니다. LLM위키는 자료를 쌓는 방식이므로, 잘못 넣은 자료도 오래 남을 수 있습니다.

실습: 내 환경을 한 장으로 기록하기

목표
앞으로 사용할 실습 환경을 짧은 문서로 정리합니다.

실행 전제
앞의 미니 위키를 만들었거나, 자신이 사용할 실습 폴더를 정해 두었습니다.

성공 기준
어떤 도구를 쓰는지, 원천 자료는 어디에 두는지, 민감한 자료는 어떻게 처리하는지 한눈에 보입니다.

아래 템플릿을 wiki/concepts/practice-environment.md 같은 이름으로 저장해도 됩니다. 아직 폴더를 만들지 않았다면 개인 메모장에 먼저 적어도 됩니다.

## 폴더 구조

- 원천 자료: raw/
- 정리된 위키 문서: wiki/
- 산출물: output/
- 인덱스: index.md
- 작업 로그: log.md

## 작업 규칙

- Codex를 쓰는 경우: AGENTS.md를 사용한다.
- Claude Code를 쓰는 경우: CLAUDE.md를 사용한다.
- 둘 다 쓰는 경우: CLAUDE.md에서 @AGENTS.md를 가져온다.

## 자료 입력 기준

- 첫 실습에는 가상 자료 또는 익명화 자료만 사용한다.
- 개인정보, 계약 정보, 고객 원문은 그대로 넣지 않는다.
- 원본 파일은 raw/에 보관하고 임의로 수정하지 않는다.

## 검증 기준

- 위키 문서에 원천 자료 경로가 있는가?
- 확인되지 않은 내용이 "확인 필요"에 적혀 있는가?
- 작업 후 log.md에 기록할 내용이 남았는가?
- 도구가 만든 답변을 원본과 대조했는가?

## 현재 확인 필요

- 내 도구가 로컬 폴더를 직접 읽을 수 있는지 확인 필요
- 플러그인이나 CLI를 쓸 경우 최신 README 확인 필요

# 나의 LLM위키 실습 환경

## 기본 선택

- 실습 폴더: ~/llm-wiki-book-lab/work-automation
- 주로 사용할 LLM 도구: Codex
- Markdown 편집기: VS Code
- 터미널 사용 가능 여부: 가능

## 작업 규칙

- Codex 기준으로 AGENTS.md를 둔다.
- Claude Code도 사용할 수 있으므로 CLAUDE.md에서 @AGENTS.md를 가져온다.

## 자료 입력 기준

- 책 실습에서는 가상 회의록만 사용한다.
- 실제 고객 문의 원문은 넣지 않는다.
- 필요하면 이름, 이메일, 주문번호를 제거한 샘플만 만든다.

이 문서는 작지만 중요합니다. 앞으로 실습이 복잡해질수록 “내가 어떤 전제로 작업하고 있었는지”를 다시 확인할 일이 생깁니다. 환경 문서가 있으면 도구를 바꾸거나 새 실습을 시작할 때도 기준을 잃지 않습니다.

3.3의 검증 포인트

이번 절을 마치기 전에 다음 항목을 확인합니다.

  • raw/, wiki/, output/의 역할을 구분할 수 있다.
  • 원천 자료와 위키 문서를 같은 파일에 섞지 않는다.
  • 위키 문서에는 원천 자료: raw/... 형식의 근거가 있다.
  • 불확실한 내용은 확인 필요로 남긴다.
  • index.md는 문서를 찾기 위한 목록으로 쓴다.
  • log.md는 자료 추가, 질문, 점검 이력을 남기는 데 쓴다.
  • Codex를 쓰면 AGENTS.md, Claude Code를 쓰면 CLAUDE.md를 확인한다.
  • 플러그인이나 CLI 명령은 실습 전 README와 릴리스 노트를 다시 확인한다.
  • 실제 고객 정보나 비공개 업무 자료는 첫 실습에 넣지 않는다.

이 기준을 통과했다면 4장에서 첫 번째 주제 위키를 만들 준비가 된 것입니다. 다음 단계부터는 작은 업무 주제를 정하고, 자료를 하나씩 넣어 보며 위키가 어떻게 자라는지 확인합니다.
