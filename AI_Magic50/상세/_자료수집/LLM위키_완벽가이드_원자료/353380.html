1.3 이 책에서 만들 결과물

LLM위키는 설명만 읽으면 조금 추상적으로 느껴질 수 있습니다. 그래서 먼저 끝에 무엇이 남는지 봅니다. 이 책을 따라가면 작은 업무 주제 하나를 정하고, 원천 자료를 모으고, 위키 문서로 정리하고, 질문하고, 보고서나 실행 계획 같은 산출물까지 만듭니다.

이 절의 목표는 설치법을 외우는 것이 아닙니다. Claude, OpenAI Codex 같은 LLM 도구를 가볍게 써 본 독자가 “내 업무에 붙이면 어떤 결과물이 생기는가”를 먼저 그려 보는 것입니다.

라이트 사용자를 위한 최소 구성

처음부터 거대한 지식 관리 시스템을 만들 필요는 없습니다. 첫 LLM위키는 작아야 합니다. 중요한 목표는 하나입니다. 다음에도 다시 쓸 업무 맥락을 남기는 것입니다.

예를 들어 매주 회의록을 정리한다고 해 보겠습니다. 매번 LLM에게 “실행 항목은 담당자, 기한, 확인 방법으로 정리해 줘”라고 말한다면, 그 설명은 위키에 남길 가치가 있습니다. 반복되는 업무 기준, 자주 쓰는 출력 형식, 주의해야 할 정보가 첫 위키의 재료입니다.

이 책에서는 예제 주제로 work-automation을 사용합니다. 반복 업무 자동화를 뜻합니다. 회의록 정리, 고객 문의 분류, 주간 보고서 초안 작성처럼 자주 반복되는 일을 다룹니다.

학습자료: 최소 LLM위키 구조

work-automation/
├─ raw/
│  └─ 원천 자료
├─ wiki/
│  └─ 정리된 위키 문서
├─ output/
│  └─ 보고서, 요약문, 실행 계획
├─ inbox/
│  └─ 아직 정리하지 않은 메모
├─ index.md
│  └─ 위키 전체의 입구
├─ log.md
│  └─ 자료를 넣고 고친 기록
└─ AGENTS.md 또는 CLAUDE.md
   └─ LLM 도구가 따라야 할 작업 규칙

이 구조에서 가장 중요한 원칙은 원본과 정리본을 섞지 않는 것입니다. raw/에는 원천 자료를 둡니다. wiki/에는 LLM이 다시 읽기 좋게 정리한 문서를 둡니다. output/에는 실제 업무에 쓸 결과물을 둡니다.

AGENTS.md와 CLAUDE.md는 작업 규칙을 담는 파일입니다. Codex를 쓴다면 AGENTS.md가 기준이 될 수 있습니다. Claude Code를 쓴다면 CLAUDE.md가 기준이 될 수 있습니다. 도구별 지원 방식은 다르므로, 이 책에서는 먼저 “작업 규칙 문서”라는 개념을 익힙니다.

구성 요소 역할 확인할 것
raw/ 원천 자료 보관 원본이 임의로 바뀌지 않았는가
wiki/ 다시 읽고 질문하기 좋은 문서 출처와 핵심 개념이 남아 있는가
output/ 업무 산출물 보고서나 실행 계획으로 쓸 수 있는가
inbox/ 임시 입력 공간 정리 전 자료가 구분되어 있는가
index.md 위키 입구 전체 문서 위치를 찾을 수 있는가
log.md 처리 기록 언제 무엇을 넣고 고쳤는지 남아 있는가
작업 규칙 문서 LLM의 작업 기준 출처, 최신성, 확인 필요 규칙이 있는가

이 표는 첫 LLM위키에 필요한 최소 구성을 보여 줍니다. 폴더 이름 자체보다 역할이 더 중요합니다. 도구에 따라 실제 저장 위치는 달라질 수 있습니다. 그러나 원천 자료, 정리된 위키, 업무 산출물, 작업 규칙을 구분하는 원칙은 유지됩니다.

실습 미리보기: 빈 구조만 만들어 보기

목표
책에서 만들 결과물의 뼈대를 로컬 폴더로 확인합니다.

실행 전제
macOS, Linux, WSL, Git Bash처럼 Bash/Zsh 계열 셸을 사용할 수 있어야 합니다. 같은 경로에 파일이 있으면 index.md, log.md, AGENTS.md가 덮어써질 수 있습니다.

성공 기준
raw/, wiki/, output/, inbox/가 분리되어 보이면 됩니다.

BASE="$HOME/llm-wiki-preview/work-automation"

mkdir -p "$BASE/raw" "$BASE/wiki/concepts" "$BASE/output" "$BASE/inbox"

printf '%s\n' \
'# 업무 자동화 위키' \
'' \
'## 이 위키의 질문' \
'' \
'반복 업무를 LLM으로 줄이려면 무엇부터 해야 할까?' \
> "$BASE/index.md"

printf '%s\n' \
'# 처리 이력' \
'' \
'| 날짜 | 작업 | 결과 |' \
'|---|---|---|' \
'| 2026-05-16 | 위키 초기 구조 생성 | raw, wiki, output, inbox 생성 |' \
> "$BASE/log.md"

printf '%s\n' \
'# LLM위키 작업 규칙' \
'' \
'- raw/의 원천 자료는 임의로 고치지 않는다.' \
'- wiki/ 문서에는 가능한 한 출처를 남긴다.' \
'- 확인하지 못한 내용은 확인 필요로 표시한다.' \
> "$BASE/AGENTS.md"

find "$BASE" -maxdepth 2 -print | sort

이 실습은 아직 완성된 LLM위키를 만드는 단계가 아닙니다. 결과물의 모양을 미리 보는 단계입니다. 이후 장에서는 이 빈 구조에 실제 자료를 넣고, 위키 문서를 만들고, 산출물까지 연결합니다.

자료 수집에서 산출물 작성까지의 흐름

LLM위키는 한 번에 완성하는 문서 묶음이 아닙니다. 자료를 넣고, 정리하고, 질문하고, 결과물을 만들고, 다시 고치는 순환 구조입니다.

이 책에서는 흐름을 수집 → 보관 → 정리 → 질문 → 산출 → 검증 → 갱신으로 설명합니다. 일부 구현체는 이를 ingest, compile, query, lint, audit 같은 명령으로 나눕니다. 이 절에서는 명령어보다 각 단계의 역할을 먼저 이해합니다.

학습자료: LLM위키 작업 흐름

마지막 화살표가 핵심입니다. 산출물을 만든 뒤에도 작업은 끝나지 않습니다. 검증 결과와 새로 알게 된 내용을 다시 위키에 반영합니다. 그래야 다음 질문에서 같은 맥락을 다시 설명하지 않아도 됩니다.

단계 하는 일 남는 결과
수집 회의록, 업무 메모, 웹 문서, 기존 양식을 모읍니다 inbox/의 임시 자료
보관 원본을 가능한 한 그대로 둡니다 raw/의 원천 자료
정리 자료를 주제별 위키 문서로 바꿉니다 wiki/의 개념 문서와 요약
질문 위키를 기준으로 업무 질문을 던집니다 근거가 붙은 답변 초안
산출 답변을 보고서나 실행 계획으로 바꿉니다 output/의 산출물
검증 출처, 누락, 추정, 최신성을 점검합니다 수정 요청과 확인 필요 표시
갱신 검증 결과와 결정 사항을 반영합니다 다음 작업에 쓸 수 있는 위키

일반적인 파일 업로드나 RAG 기반 사용에서는 질문할 때마다 관련 자료 조각을 다시 찾는 경험이 많습니다. LLM위키는 자료를 읽을 때 정리된 위키 문서를 남기는 쪽에 더 가깝습니다. 다만 둘 중 하나가 항상 더 낫다고 볼 수는 없습니다. 자료가 부정확하거나 검증이 빠지면 LLM위키도 잘못된 지식을 누적할 수 있습니다.

작은 예제로 보는 입력과 출력

다음은 이 책에서 반복해서 사용할 예시 메모입니다. 실제 실습에서는 자신의 업무 메모로 바꿔도 됩니다.

# 팀 반복 업무 메모

## 관찰
- 매주 월요일 회의록에서 실행 항목을 다시 정리한다.
- 고객 문의를 유형별로 나눈 뒤 담당자에게 전달한다.
- 릴리스 노트를 쓸 때 변경 사항, 영향 범위, 확인 방법을 매번 다시 묻는다.

## 자동화 후보
- 회의록에서 실행 항목 초안 뽑기
- 고객 문의 유형 추천하기
- 릴리스 노트 초안 만들기

## 주의할 점
- 고객명, 계약 조건, 장애 원인은 외부 도구에 그대로 넣으면 안 된다.
- 최종 발송 문구는 담당자가 확인해야 한다.

이 메모가 raw/team-repeat-tasks.md에 보관되면, wiki/에는 다음과 같은 정리 문서가 생기는 것을 목표로 합니다.

# 반복 업무 자동화 후보

## 한 문장 요약

팀에서 반복되는 업무는 회의록 정리, 고객 문의 분류, 릴리스 노트 작성이다.

## 자동화 후보

| 후보 | 기대 효과 | 주의할 점 |
|---|---|---|
| 회의록 실행 항목 추출 | 회의 후 정리 시간을 줄인다 | 결정 사항과 할 일을 구분해야 한다 |
| 고객 문의 유형 추천 | 1차 분류 시간을 줄인다 | 개인정보와 오분류 위험을 검토해야 한다 |
| 릴리스 노트 초안 작성 | 반복되는 문서 작성 시간을 줄인다 | 변경 영향 범위는 담당자가 확인해야 한다 |

## 출처

- raw/team-repeat-tasks.md

## 확인 필요

- 실제로 가장 시간이 오래 걸리는 업무가 무엇인지는 추가 확인이 필요하다.

이 예시는 LLM위키가 하는 일을 보여 줍니다. 원본 메모를 없애지 않습니다. 대신 다시 쓰기 좋은 문서로 바꿉니다. 그리고 문서 끝에 출처와 확인 필요 항목을 남깁니다. 나중에 보고서를 만들 때도 “이 주장이 어디서 나왔는가?”를 확인할 수 있습니다.

각 장 실습 결과 미리 보기

이 책은 한 장씩 읽을 때마다 작은 결과물이 남도록 구성되어 있습니다. 1장에서는 왜 필요한지 이해합니다. 2장에서는 구조를 익힙니다. 3장 이후에는 실제로 위키를 만들고 자료를 넣고 산출물을 만듭니다.

학습자료: 장별로 남는 결과물

장 배우는 내용 남는 결과물
1장 LLM위키가 필요한 이유 만들 결과물의 전체 그림
2장 기본 구조 raw/, wiki/, output/, 작업 규칙의 역할 이해
3장 시작 방식 고르기 내 환경에 맞는 LLM위키 방식 선택
4장 첫 주제 위키 만들기 work-automation 위키 초안
5장 자료를 지식으로 바꾸기 회의록, 메모, 웹 문서에서 정리된 위키 문서 생성
6장 위키에 질문하고 검증하기 근거가 붙은 답변과 확인 필요 항목
7장 업무 산출물 만들기 보고서, 요약문, 실행 계획 초안
8장 오래 쓰는 운영법 점검 체크리스트와 갱신 루틴

이 표는 목차를 결과물의 흐름으로 다시 보여 줍니다. 독자는 각 장을 읽은 뒤 “무엇을 알게 되었는가”뿐 아니라 “무엇이 남았는가”를 확인할 수 있어야 합니다.

학습자료: 최종 산출물의 연결 관계

이 그림은 원천 자료가 바로 보고서로 바뀌지 않는다는 점을 보여 줍니다. 중간에 위키 문서가 있습니다. 위키 문서는 자료를 다시 읽기 좋은 형태로 정리한 중간 결과물입니다. 이 중간 결과물이 있어야 질문의 맥락이 안정됩니다. 산출물의 근거도 따라갈 수 있습니다.

책을 마치면 할 수 있는 일

이 책의 마지막 목표는 “LLM위키를 설치했다”가 아닙니다. 목표는 자신의 업무에서 반복되는 지식 작업을 더 체계적으로 처리하는 것입니다.

책을 마치면 다음 일을 할 수 있어야 합니다.

  • 새 업무 주제를 LLM위키로 만들 수 있습니다.
  • 원천 자료와 LLM이 정리한 문서를 구분할 수 있습니다.
  • 위키에 질문하고 답변의 근거를 확인할 수 있습니다.
  • 보고서, 요약문, 실행 계획 같은 산출물을 만들 수 있습니다.
  • 출처가 약한 주장과 확인이 필요한 내용을 표시할 수 있습니다.
  • 위키를 한 번 만들고 버려두지 않고 계속 갱신할 수 있습니다.

이 능력은 특정 도구 하나에만 묶이지 않습니다. Claude Code, OpenAI Codex, CLI 도구, 데스크톱 도구처럼 구현 방식은 달라질 수 있습니다. 하지만 자료를 모으고, 위키로 정리하고, 질문하고, 검증하고, 다시 반영하는 흐름은 계속 유지됩니다.

정리와 검증 포인트

이 절에서는 책 전체의 결과물을 먼저 확인했습니다. 아직 세부 도구를 다루지는 않았습니다. 대신 LLM위키가 어떤 형태로 남아야 하는지 살펴보았습니다.

검증 질문 확인 기준
이 책에서 만들 최종 결과물은 무엇인가? work-automation 같은 작은 업무 주제 위키와 업무 산출물
최소 구성은 무엇인가? 원천 자료, 위키 문서, 산출물, 작업 규칙 문서
raw/와 wiki/를 왜 나누는가? 원본 보존과 정리본 활용을 구분하기 위해
LLM위키의 기본 흐름은 무엇인가? 수집, 보관, 정리, 질문, 산출, 검증, 갱신
왜 검증이 필요한가? LLM이 만든 요약에는 누락, 추정, 오래된 정보가 섞일 수 있기 때문에

다음 절부터는 이 그림을 더 구체화합니다. 먼저 LLM위키가 지식을 어떤 층으로 쌓는지 살펴봅니다.

  • Andrej Karpathy, llm-wiki.md Gist, https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f, 확인일: 2026-05-16. LLM위키를 원천 자료, 위키, 스키마로 나누는 개념 근거로 사용했습니다.

  • nvk/llm-wiki README, https://github.com/nvk/llm-wiki, 확인일: 2026-05-16. ingest, compile, query, lint, audit 같은 구현체 흐름을 확인하는 근거로 사용했습니다.
