1.2 LLM위키는 무엇인가

LLM위키를 배우는 이유는 간단합니다. LLM에게 매번 같은 업무 배경을 다시 설명하지 않기 위해서입니다. 팀에서 쓰는 용어, 보고서 형식, 금지해야 할 표현, 이미 합의한 판단 기준은 한 번 쓰고 사라질 정보가 아닙니다. 다음 작업에서도 다시 써야 할 업무 지식입니다.

이 절에서는 LLM위키를 특정 제품이 아니라 지식 관리 패턴으로 봅니다. 원천 자료를 위키로 “컴파일한다”는 뜻을 살펴보고, RAG, 노트 앱, 일반 위키와 무엇이 다른지도 구분합니다.

제품이 아니라 지식 관리 패턴으로 보기

LLM위키라는 말을 처음 들으면 앱 이름부터 떠올리기 쉽습니다. “무엇을 설치해야 하지?”, “어떤 서비스를 가입해야 하지?” 같은 질문이 먼저 나옵니다. 하지만 2026년 5월 16일 KST 조사 기준으로, LLM위키는 단일 공식 제품명이라기보다 지식 관리 패턴으로 보는 편이 안전합니다.

이 패턴은 Andrej Karpathy가 2026년 4월 공개한 LLM Wiki 아이디어 문서에서 뚜렷하게 설명됩니다. 핵심은 특정 앱을 쓰라는 제안이 아닙니다. 원천 자료를 보존하고, LLM이 이를 구조화된 Markdown 위키로 정리하며, 이후 질문과 갱신을 그 위키에 누적하자는 방식입니다.

이 책에서는 LLM위키를 다음처럼 정의합니다.

LLM위키는 원천 자료를 보존하고, LLM이 이를 다시 쓰기 좋은 위키 문서로 정리하며, 질문·갱신·검증 결과를 계속 누적하는 지식 관리 패턴입니다.

여기서 중요한 단어는 “패턴”입니다. Markdown 파일만으로 작게 시작할 수 있습니다. Claude Code, OpenAI Codex 같은 에이전트 도구와 연결할 수도 있습니다. nvk/llm-wiki 같은 구현체를 사용할 수도 있습니다. 하지만 도구가 달라도 핵심 구조는 크게 변하지 않습니다.

LLM위키의 기본 구조는 세 층으로 볼 수 있습니다.

학습자료: LLM위키의 세 층

이 도해에서 raw는 사실의 출발점입니다. 회의록, 업무 메모, 웹 문서, 코드 리뷰 기록처럼 나중에 다시 확인해야 할 자료가 여기에 들어갑니다. 가능하면 원본 상태를 보존합니다.

wiki는 LLM이 정리한 활용 문서입니다. 단순 요약문이 아닙니다. 개념, 결정, 절차, 질문이 나뉘고 서로 연결됩니다. 독자와 LLM이 다음 작업에서 다시 읽기 쉬운 형태여야 합니다.

schema는 작업 규칙입니다. 실제 도구에서는 AGENTS.md, CLAUDE.md 같은 파일이 이 역할을 할 수 있습니다. 예를 들어 “원천 자료를 덮어쓰지 않는다”, “확인되지 않은 주장은 확인 필요로 표시한다”, “모든 위키 문서에 출처를 남긴다” 같은 기준을 적습니다.

작은 업무 장면으로 이해하기

매주 회의록을 정리하는 사용자를 생각해 보겠습니다. 일반적인 LLM 사용 방식에서는 회의록을 붙여 넣고 이렇게 요청합니다.

이 회의록에서 실행 항목을 정리해 줘.
담당자, 기한, 확인 방법을 표로 만들어 줘.

결과는 바로 얻을 수 있습니다. 하지만 다음 주 회의록을 정리할 때 같은 기준을 다시 설명해야 합니다. 실행 항목의 형식, 제외할 내용, 팀에서 쓰는 용어가 새 대화창에는 없기 때문입니다.

LLM위키 방식은 다릅니다.

  1. 회의록 원문을 원천 자료로 보관합니다.
  2. LLM이 결정 사항, 실행 항목, 반복 이슈를 위키 문서로 정리합니다.
  3. 다음 회의록이 들어오면 기존 위키와 비교해 바뀐 점을 갱신합니다.
  4. 나중에 “최근 한 달 동안 반복된 이슈는?”이라고 물으면 위키를 기준으로 답합니다.

한 번의 답변을 얻는 방식에서, 계속 자라는 업무 지식을 만드는 방식으로 바뀝니다. 이것이 LLM위키의 출발점입니다.

학습자료: 일반 대화와 LLM위키의 차이
구분 일반 대화형 사용 LLM위키 사용
업무 맥락 매번 프롬프트에 다시 씀 위키와 작업 규칙에 남김
자료 대화창에 붙여 넣고 소비함 원천 자료로 보존함
답변 그 순간의 결과물 다음 작업의 재료
검증 대화 기록을 다시 찾아야 함 원천 자료와 위키 문서로 추적함
위험 좋은 답변이 일회성으로 끝남 잘못 정리된 내용이 누적될 수 있음

LLM위키는 일반 대화를 없애는 방법이 아닙니다. 반복되는 대화의 배경을 문서로 남기는 방법입니다. 그래서 한 번 묻고 끝나는 질문보다, 같은 맥락을 여러 번 써야 하는 업무에 더 잘 맞습니다.

원천 자료를 위키로 컴파일한다는 뜻

LLM위키에서 “컴파일”은 중요한 표현입니다. 프로그래밍에서 컴파일은 소스 코드를 실행 가능한 다른 형태로 바꾸는 일입니다. LLM위키에서는 원천 자료를 다시 쓰기 좋은 위키 문서로 바꾸는 일을 뜻합니다.

여기서 컴파일은 단순 요약이 아닙니다. 여러 자료에 흩어진 내용을 모읍니다. 중복을 줄입니다. 관련 문서를 연결합니다. 출처와 갱신일을 남깁니다. 확인되지 않은 내용은 단정하지 않고 “확인 필요”로 표시합니다.

좋은 컴파일 결과는 읽기 좋은 문장보다 더 많은 것을 갖춰야 합니다. 나중에 다시 질문할 수 있어야 합니다. 보고서와 실행 계획으로 바꿀 수 있어야 합니다. 틀렸을 때 원천 자료로 돌아갈 수 있어야 합니다.

학습자료: 원천 자료가 위키로 바뀌는 흐름

이 흐름에서 가장 중요한 원칙은 원천 자료와 위키 문서를 섞지 않는 것입니다. 원천 자료는 근거입니다. 위키 문서는 해석과 정리입니다. 둘을 섞으면 나중에 어떤 내용이 원문이고 어떤 내용이 LLM의 재구성인지 알기 어렵습니다.

실습: 회의 메모를 위키 문서 후보로 바꾸기

목표
원천 자료가 어떻게 업무 지식 문서로 바뀌는지 확인합니다.

실행 전제
Markdown 문서를 읽을 수 있으면 됩니다. 특정 플러그인이나 CLI 설치는 필요하지 않습니다.

성공 기준
원천 자료의 내용이 요약, 근거, 위험, 다음 질문으로 나뉘는지 확인합니다.

# 고객 문의 라벨 추천 실험

## 근거

- 개인정보가 포함된 원문은 외부 도구에 그대로 넣지 않는다.

## 확인 필요

- 현재 사용 중인 문의 라벨 목록
- 익명화된 샘플 문의 20건 확보 가능 여부
- 라벨 추천 결과를 평가할 기준

## 다음 질문

- 고객 문의 라벨 기준을 먼저 문서화할 수 있는가?
- 개인정보를 제거한 실험용 샘플을 만들 수 있는가?

예상 결과는 분명합니다. 회의 메모는 시간순 기록입니다. 위키 문서 후보는 업무 판단에 맞게 재구성된 지식입니다. 같은 내용이라도 역할이 달라졌습니다.

이 예에서 LLM이 할 일은 문장을 줄이는 것이 아닙니다. 자료를 다시 쓰기 좋은 지식으로 재구성하는 것입니다. 회의 메모는 근거로 남고, 위키 문서는 다음 질문과 산출물의 재료가 됩니다.

학습자료: 좋은 컴파일 결과 점검표

조건 확인 질문 부족할 때 생기는 문제
출처 이 문장은 어느 원천 자료에서 왔는가? 근거 없는 단정이 생김
구조 요약, 근거, 확인 필요가 구분되어 있는가? 다시 읽을 때 판단하기 어려움
연결 관련 문서나 다음 질문이 남아 있는가? 지식이 파일 하나에 갇힘
갱신 기준 언제 다시 확인해야 하는가? 오래된 주장을 계속 믿게 됨

이 표는 LLM위키를 요약 도구와 구분하는 기준입니다. 요약만 잘 된 문서는 읽기에는 편합니다. 하지만 출처와 확인 필요 항목이 없으면 실무에서 다시 쓰기 어렵습니다.

최근 WiCER 프리프린트는 LLM이 원천 자료를 위키로 컴파일할 때 중요한 사실을 빠뜨릴 수 있다고 보고합니다. 다만 이 자료는 2026년 5월 arXiv 프리프린트입니다. 따라서 확정된 결론이라기보다 “검증 없는 컴파일은 위험할 수 있다”는 제한된 근거로 읽는 편이 안전합니다.

RAG, 노트 앱, 일반 위키와의 차이

LLM위키는 기존 도구와 겹치는 부분이 많습니다. 그래서 RAG, 노트 앱, 일반 위키와 구분하지 않으면 “검색이 잘 되는 노트 앱” 정도로 오해하기 쉽습니다.

RAG는 보통 질문을 받았을 때 관련 문서 조각을 찾아 LLM 답변에 붙여 주는 방식입니다. 원문 기반 답변을 만들 때 유용합니다. 다만 일반적인 파일 업로드나 RAG 사용 경험에서는 질문할 때마다 필요한 조각을 다시 찾고 조합하는 흐름이 많습니다.

LLM위키는 자료를 먼저 위키로 정리해 둡니다. 이후 질문은 원문 조각만이 아니라 정리된 위키 구조를 바탕으로 이어집니다. 그렇다고 LLM위키가 RAG보다 항상 낫다는 뜻은 아닙니다. 둘은 대체 관계라기보다 다른 운영 패턴에 가깝습니다. 실제 시스템에서는 함께 쓰일 수도 있습니다.

노트 앱은 사용자가 직접 기록하고 연결하는 데 강합니다. Obsidian 같은 Markdown 기반 노트 앱은 LLM위키의 보기 도구로도 쓸 수 있습니다. 하지만 노트 앱 자체가 LLM위키는 아닙니다. LLM위키에서는 LLM이 원천 자료를 읽고 문서 구조를 제안하거나 갱신하는 역할을 합니다.

일반 위키는 사람이 지식을 문서화하고 링크를 쌓는 데 강합니다. LLM위키는 여기에 LLM의 읽기, 요약, 재구성 능력을 붙입니다. 회의록, 리서치 자료, 업무 메모처럼 사람이 매번 정리하기 번거로운 자료를 구조화하는 데 초점을 둡니다.

학습자료: 네 가지 방식 비교

구분 중심 질문 강점 약점 LLM위키와의 관계
RAG 지금 질문에 필요한 문서 조각은 무엇인가? 원문 기반 답변에 유용함 검색 품질과 조각 선택에 의존함 함께 쓰일 수 있음
노트 앱 내가 무엇을 기록했는가? 개인 기록과 연결에 강함 정리와 갱신을 사용자가 직접 해야 함 원천 자료 저장소나 보기 도구가 될 수 있음
일반 위키 조직 지식을 어떻게 문서화할 것인가? 사람이 읽는 지식 체계에 강함 입력과 유지보수 비용이 큼 LLM이 정리와 갱신을 보조할 수 있음
LLM위키 원천 자료를 어떻게 재사용 가능한 지식으로 바꿀 것인가? 반복 맥락 축적과 산출물 생성에 유용함 컴파일 오류와 출처 누락 위험이 있음 검증 규칙과 함께 운영해야 함

이 표에서 중요한 차이는 시점입니다. RAG는 주로 질문할 때의 검색에 초점이 있습니다. LLM위키는 자료를 넣을 때 정리하고, 이후 질문에서 그 정리 결과를 다시 씁니다.

학습자료: 질문할 때 찾기와 미리 정리해 두기의 차이

두 흐름 중 어느 쪽이 항상 우수하다고 말할 수는 없습니다. 빠르게 한 번 답을 얻고 끝낼 작업이면 일반 대화나 RAG가 더 단순합니다. 반대로 같은 배경을 반복해서 쓰고, 시간이 지나며 자료가 쌓이는 업무라면 LLM위키가 더 잘 맞을 수 있습니다.

아래 표는 자신의 현재 사용 방식이 어디에 가까운지 확인하기 위한 간단한 진단표입니다.

학습자료: 사용 방식 자가진단

내 사용 모습 가까운 방식 다음 행동
매번 파일을 올리고 질문한다 RAG 또는 파일 업로드형 사용 반복 질문이 있는지 확인합니다.
생각나는 내용을 노트에 적는다 노트 앱 자주 다시 쓰는 노트를 위키 후보로 고릅니다.
팀 문서를 사람이 직접 갱신한다 일반 위키 갱신 비용이 큰 문서를 찾습니다.
회의록, 메모, 웹 문서를 LLM이 정리하고 갱신하게 한다 LLM위키 출처와 검증 기준을 함께 둡니다.

LLM 도구를 가볍게 써 본 독자에게 가장 좋은 시작점은 작지만 반복되는 업무입니다. 고객 문의 분류, 회의록 실행 항목 정리, 주간 보고서 초안 작성이 적합합니다. 처음부터 회사 전체 지식베이스를 만들려고 하면 범위가 커집니다. 그러면 검증과 갱신도 어려워집니다.

잘 맞는 상황과 신중해야 하는 상황

LLM위키가 잘 맞는 상황은 다음과 같습니다.

상황 LLM위키가 도움이 되는 이유
같은 배경 설명을 반복한다 업무 맥락을 위키에 남겨 재사용할 수 있습니다.
자료가 여러 곳에 흩어져 있다 회의록, 문서, 메모를 주제별로 묶을 수 있습니다.
답변의 근거를 확인해야 한다 위키 문서에서 원천 자료로 돌아갈 수 있습니다.
보고서나 실행 계획을 반복해서 만든다 정리된 지식을 산출물로 바꾸기 쉽습니다.
시간이 지나며 내용이 바뀐다 갱신 이력과 오래된 주장을 점검할 수 있습니다.

반대로 신중해야 하는 상황도 있습니다.

상황 이유
원천 자료가 거의 없다 LLM이 추측으로 빈칸을 채울 수 있습니다.
정보가 매우 민감하다 외부 LLM 호출, 플러그인 권한, 저장 위치를 먼저 확인해야 합니다.
정답이 실시간으로 바뀐다 위키가 금방 오래된 정보가 될 수 있습니다.
수치 정확도가 핵심이다 원본 데이터와 계산 절차를 별도로 검증해야 합니다.
검토할 사람이 없다 잘못 컴파일된 내용이 그대로 누적될 수 있습니다.

특히 개인정보, 계약 정보, 비공개 코드, 고객 원문은 그대로 넣지 않는 편이 안전합니다. 일부 구현체는 위키 파일을 로컬에 저장합니다. 그러나 URL 수집, 웹 검색, LLM 호출은 사용하는 도구와 조직 정책을 따릅니다. 실제 업무에 쓰기 전에는 보안 기준을 먼저 확인해야 합니다.

정리와 검증 포인트

이 절의 핵심은 LLM위키를 앱 이름으로 외우지 않는 것입니다. LLM위키는 원천 자료를 오래 쓸 수 있는 업무 지식으로 바꾸는 방식입니다.

확인 질문 답
LLM위키는 특정 제품인가? 단일 제품이 아니라 지식 관리 패턴에 가깝습니다.
원천 자료와 위키 문서는 어떻게 다른가? 원천 자료는 근거이고, 위키 문서는 활용을 위한 재구성 결과입니다.
컴파일은 단순 요약과 어떻게 다른가? 출처, 구조, 연결, 갱신 기준을 남기는 정리 작업입니다.
RAG와 LLM위키의 차이는 무엇인가? RAG는 질문할 때의 검색에 가깝고, LLM위키는 미리 정리한 지식 구조를 계속 갱신합니다.
가장 큰 위험은 무엇인가? 출처 누락, 잘못된 컴파일, 오래된 주장, 민감 정보 입력입니다.

다음 절에서는 이 책에서 실제로 만들 결과물을 미리 봅니다. 중요한 것은 거창한 시스템을 한 번에 만드는 일이 아닙니다. 반복해서 다시 설명하던 업무 맥락 하나를 위키 문서로 남기는 것부터 시작합니다.
