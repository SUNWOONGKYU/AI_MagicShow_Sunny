6.2 답변의 근거 확인하기

LLM위키에 질문하면 답은 빠르게 나옵니다. 문제는 그 답이 무엇을 근거로 했는지, 어디까지 확실한지, 지금도 유효한지입니다. 위키에 정리된 문장은 원본이 아닙니다. 원본 자료를 바탕으로 만든 파생 지식입니다.

이 절에서는 답변을 그대로 믿기 전에 세 가지를 확인합니다. 첫째, 출처가 있는 답과 없는 답을 구분합니다. 둘째, 확인된 내용과 추정을 나눕니다. 셋째, 최신성이 필요한 주장에는 표시를 남깁니다. 이 습관이 있어야 LLM위키를 보고서, 회의 준비, 실행 계획에 안전하게 쓸 수 있습니다.

출처가 있는 답과 없는 답 구분하기

LLM위키에서 나온 답변은 보통 세 종류의 문장으로 섞여 있습니다. 원천 자료에 근거한 문장, 위키 문서에는 있지만 원본 연결이 약한 문장, 그리고 LLM이 문맥상 보충한 문장입니다. 이 셋을 구분하지 않으면 “위키에 있으니 사실”이라는 착각이 생깁니다.

Karpathy의 LLM Wiki 아이디어 문서와 nvk/llm-wiki 문서는 공통적으로 원천 자료와 정리된 위키를 나눕니다. 이 구분은 단순한 폴더 정리가 아닙니다. 답변을 검증할 때 돌아갈 기준점을 남기는 장치입니다.

학습자료: 답변 문장의 근거 상태 구분표

답변 문장 유형 판단 기준 원고나 보고서에 쓸 때
출처가 있는 답 원천 자료 경로, URL, 회의록 날짜, 문서명이 함께 제시됨 단정 가능. 단, 출처의 날짜와 범위를 함께 남김
위키 근거만 있는 답 wiki/ 문서에는 있으나 raw/나 외부 URL 연결이 없음 “위키 정리 기준”으로 제한해 표현
출처가 없는 답 답변에는 나오지만 근거 파일이나 링크가 없음 단정 금지. 확인 필요로 표시
추정 답 “아마”, “가능성이 높다”, “보통” 같은 표현이 붙음 추정으로 분리하고 후속 확인 질문을 남김

이 표의 핵심은 답변의 문장마다 근거의 깊이가 다르다는 점입니다. 출처가 있는 문장은 원본으로 돌아가 확인할 수 있습니다. 출처가 없는 문장은 당장 버릴 필요는 없지만, 업무 결정의 근거로 쓰면 위험합니다.

실습: 답변에 근거 라벨 붙이기

다음 답변은 업무 자동화 위키에 질문했을 때 나온 예시입니다.

질문: 고객 문의 분류 자동화를 먼저 해야 할까?

답변:
1. 고객 문의 중 반복 문의가 많아 자동화 우선순위가 높습니다.
2. 회의록에 따르면 2026-05-10 회의에서 "배송 지연", "환불 절차", "계정 잠김"이 반복 문의로 언급되었습니다.
3. 자동 분류를 도입하면 응답 시간이 크게 줄어들 것입니다.
4. 다만 현재 위키에는 최근 3개월 문의량 통계가 없습니다.
5. 따라서 먼저 문의 유형별 건수를 확인한 뒤 자동화 대상을 정하는 것이 좋습니다.

이 답변을 바로 믿지 말고 문장마다 라벨을 붙입니다.

| 번호 | 문장 요약 | 라벨 | 이유 |
|---|---|---|---|
| 1 | 반복 문의가 많아 자동화 우선순위가 높다 | 추정 포함 | 반복 문의 근거는 있으나 우선순위 판단 기준이 부족함 |
| 2 | 특정 회의에서 반복 문의 3종이 언급됨 | 출처 있음 | 회의 날짜와 항목이 제시됨 |
| 3 | 응답 시간이 크게 줄어들 것 | 출처 없음 | 효과 수치나 이전 사례가 없음 |
| 4 | 최근 3개월 통계가 없음 | 위키 상태 확인 | 위키에 자료가 없다는 범위 안에서만 유효 |
| 5 | 건수 확인 뒤 대상을 정하자 | 실행 제안 | 앞의 한계를 반영한 다음 행동 |

이 실습에서 가장 중요한 문장은 3번입니다. “응답 시간이 크게 줄어들 것”은 그럴듯하지만 근거가 없습니다. 이런 문장은 보고서에 그대로 넣지 않습니다. “응답 시간 개선 가능성은 있으나, 현재 위키에는 정량 근거가 없다”처럼 바꿔야 합니다.

출처 요청 프롬프트

LLM위키에 질문할 때는 처음부터 근거를 함께 요구하는 편이 좋습니다.

다음 질문에 답하세요.

질문: 고객 문의 분류 자동화를 먼저 해야 할까?

답변 형식:
- 결론
- 결론의 근거
- 근거가 있는 문장과 출처
- 출처가 없는 문장
- 확인이 필요한 내용
- 다음 확인 질문

주의:
출처가 없는 내용은 단정하지 말고 "확인 필요"로 표시하세요.

이 프롬프트는 답을 더 길게 만들기 위한 것이 아닙니다. 답변을 업무에 쓰기 전에 검토할 수 있는 모양으로 받기 위한 요청입니다.

확실한 내용과 추정 구분하기

출처가 있다고 해서 모든 문장이 같은 수준으로 확실한 것은 아닙니다. 회의록에 “고객 문의가 늘었다”는 말이 있어도 실제 문의량이 얼마나 늘었는지는 별도 통계가 필요합니다. 공식 문서에 기능이 있다고 적혀 있어도, 내가 쓰는 버전에서 동작하는지는 다시 확인해야 합니다.

확실한 내용은 원본에 직접 적힌 내용입니다. 추정은 그 내용을 바탕으로 해석하거나 앞으로의 결과를 예상한 내용입니다. LLM은 이 둘을 자연스럽게 이어서 말합니다. 독자는 그 연결부를 끊어 봐야 합니다.

이 흐름은 답변 전체를 평가하지 않습니다. 문장 단위로 나눠 봅니다. 한 답변 안에서도 어떤 문장은 확실하고, 어떤 문장은 추정이며, 어떤 문장은 확인이 필요할 수 있습니다.

확실성 등급 붙이기

다음처럼 세 단계로 나누면 충분합니다.

등급 의미 예시 표현
확인됨 원천 자료에 직접 근거가 있음 “2026-05-10 회의록에는 배송 지연 문의가 반복 항목으로 기록되어 있다.”
제한적 확인 일부 근거는 있으나 범위가 좁음 “회의록 기준으로는 배송 지연 문의가 반복적으로 언급되었다.”
추정 직접 근거 없이 가능성을 말함 “배송 지연 문의 자동화가 응답 시간을 줄일 가능성이 있다.”
확인 필요 근거가 없거나 최신 확인이 필요함 “자동화 도입 후 응답 시간이 30% 줄어든다.”

등급을 붙이면 문장이 자연스럽게 조심스러워집니다. “자동화가 효과적이다”라는 문장은 강합니다. “회의록 기준으로 반복 문의가 확인되므로 자동화 후보로 검토할 수 있다”는 문장은 더 안전합니다.

실습: 답변을 검토용 문장으로 바꾸기

아래 문장을 검토용으로 바꿔 보겠습니다.

원문:
고객 문의 자동 분류를 도입하면 응답 시간이 크게 줄어듭니다.

검토 후:
현재 위키에는 응답 시간 감소를 입증할 정량 근거가 없습니다.
다만 2026-05-10 회의록에 반복 문의 유형이 기록되어 있으므로,
고객 문의 자동 분류는 자동화 후보로 검토할 수 있습니다.

바뀐 문장은 덜 화려합니다. 대신 안전합니다. 검토자는 어떤 근거가 있고, 무엇이 부족한지 바로 알 수 있습니다.

추정 표현을 숨기지 않기

LLM 답변에서 추정은 나쁜 것이 아닙니다. 업무에서는 추정이 필요합니다. 문제는 추정을 사실처럼 쓰는 것입니다. 따라서 추정은 다음처럼 표시합니다.

## 확인된 내용

- 2026-05-10 회의록에는 반복 문의로 "배송 지연", "환불 절차", "계정 잠김"이 기록되어 있다.
- 현재 위키에는 최근 3개월 문의량 통계가 없다.

## 추정

- 반복 문의가 많은 항목은 자동화 효과가 있을 가능성이 있다.
- 단, 효과 크기는 문의량, 현재 처리 시간, 자동 분류 정확도에 따라 달라진다.

## 확인 필요

- 문의 유형별 최근 3개월 건수
- 유형별 평균 처리 시간
- 자동 분류 결과를 사람이 재검토해야 하는 비율

이 형식은 회의 준비에도 좋습니다. 회의에서 논쟁할 대상을 분명히 나눌 수 있기 때문입니다. 확인된 내용은 합의의 출발점으로 두고, 추정은 실험 계획으로 바꿉니다.

최신성이 필요한 주장 표시하기

일부 주장은 시간이 지나도 크게 바뀌지 않습니다. “LLM위키는 원천 자료와 정리된 위키를 구분한다”는 개념 설명은 비교적 안정적입니다. 반면 설치 명령, 플러그인 기능, 최신 릴리스, 가격, 정책, API 동작, 보안 설정은 빠르게 바뀔 수 있습니다.

리서치 결과에 따르면 nvk/llm-wiki는 2026년 5월 기준 릴리스가 빠르게 이어졌고, Pratiyush/llm-wiki의 변경 로그에는 제거된 명령어가 문서에 남아 있던 사례도 있었습니다. 따라서 도구 명령과 버전 정보는 본문에서 단정하더라도 반드시 확인 날짜와 기준 버전을 함께 둬야 합니다.

학습자료: 최신성 표시가 필요한 주장

주장 유형 최신성 필요도 표시 방법
개념 정의 낮음 출처와 원문 기준만 표시
폴더 구조 원칙 낮음 구현체별 차이가 있으면 조건 표시
설치 명령 높음 확인 날짜, 도구명, 버전 또는 README 기준 표시
플러그인 기능 높음 “2026-05-16 확인 기준”처럼 날짜 표시
릴리스 번호 높음 최신 여부를 단정하기 전에 릴리스 페이지 확인
보안·권한 정책 높음 공식 문서 기준, 조직 정책 확인 필요 표시
성능 개선 효과 높음 측정 환경과 데이터 범위 표시

이 표는 “무엇을 의심해야 하는가”를 알려 줍니다. 최신성이 필요한 주장은 틀리면 독자의 실행이 막히거나 보안 문제가 생길 수 있습니다.

최신성 라벨 만들기

위키 문서와 답변에 다음 라벨을 붙이면 관리가 쉬워집니다.

라벨 뜻 예시
확인됨 원천 자료로 확인함 회의록, 공식 문서, 내부 정책 문서
확인 필요 아직 근거가 부족함 수치, 효과, 원인 분석
최신성 확인 필요 시간이 지나면 바뀔 수 있음 설치 명령, 버전, 가격, 정책
제한된 근거 근거는 있으나 범위가 좁음 단일 회의록, 소수 인터뷰, 초기 연구
추정 가능성을 제시함 예상 효과, 우선순위 판단

라벨은 복잡할 필요가 없습니다. 중요한 것은 답변이 “검토 가능한 상태”로 남는 것입니다.

이 도해를 실제로 적용하면 답변 검토 시간이 줄어듭니다. 문장을 읽을 때마다 “맞나?”라고 막연히 묻지 않고, “최신성 문제인가, 근거 문제인가, 추정 문제인가”로 나눠 볼 수 있습니다.

실습: 최신성 표시가 들어간 답변 만들기

다음은 LLM위키 도구 설명을 위키 문서에 남길 때의 예시입니다.

## Codex에서 LLM위키 플러그인 사용

- 상태: 최신성 확인 필요
- 확인 날짜: 2026-05-16
- 기준 자료: nvk/llm-wiki README, OpenAI Codex Plugins 문서

2026-05-16 확인 기준, `nvk/llm-wiki`는 Codex 플러그인 방식의 사용을 문서화하고 있다.
설치와 활성화 흐름은 해당 저장소 README와 Codex 플러그인 문서를 함께 확인해야 한다.

주의:
- 이 명령은 OpenAI의 기본 내장 명령이 아니라 `nvk/llm-wiki` 구현체 문서 기준이다.
- 플러그인 설치, 네트워크 접근, 로컬 파일 접근 범위는 Codex와 플러그인 설정에 따라 달라질 수 있다.
- 실습 전 최신 README와 설치된 플러그인의 도움말을 다시 확인한다.

이 문서는 일부러 단정하지 않습니다. 도구 명령은 독자가 실행하는 순간의 환경에 영향을 받기 때문입니다. 대신 확인 날짜와 기준 자료를 남깁니다.

최신성 확인 질문 예시

최신성이 필요한 주장을 발견하면 다음 질문으로 다시 확인합니다.

다음 답변에서 최신성 확인이 필요한 문장만 골라 주세요.

각 문장에 대해 다음 형식으로 정리하세요.
- 문장
- 왜 최신성 확인이 필요한가
- 확인해야 할 공식 자료
- 확인하지 못하면 원고에서 어떻게 표현해야 하는가

예상 결과는 다음과 비슷해야 합니다.

| 문장 | 이유 | 확인 자료 | 원고 표현 |
|---|---|---|---|
| nvk/llm-wiki 최신 버전은 v0.9.0이다 | 릴리스는 바뀔 수 있음 | GitHub Releases | 2026-05-16 확인 기준으로 제한 |
| Codex에서 플러그인은 @wiki로 호출한다 | 플러그인 동작이 바뀔 수 있음 | nvk README, Codex Plugins 문서 | 구현체 문서 기준으로 설명 |
| 자동 분류를 도입하면 응답 시간이 줄어든다 | 성능 효과는 데이터에 따라 다름 | 내부 측정 자료 | 가능성으로 표현하고 확인 필요 표시 |

이 실습을 끝내면 “지금도 맞는 말인가?”를 따로 확인할 문장을 빠르게 찾을 수 있습니다.

6.2의 검증 포인트

답변을 검토할 때는 다음 순서로 확인합니다.

점검 질문 통과 기준
답변의 핵심 주장에 출처가 있는가? 원천 자료 경로, URL, 회의록 날짜, 공식 문서명이 남아 있음
출처가 없는 문장이 표시되어 있는가? “확인 필요” 또는 “출처 없음”으로 분리됨
확인된 내용과 추정이 섞이지 않았는가? 확인된 내용, 추정, 확인 필요가 나뉘어 있음
최신성이 필요한 주장이 표시되어 있는가? 확인 날짜와 기준 자료가 함께 있음
업무 결정에 써도 되는 문장인가? 근거 범위와 한계를 함께 설명함

가장 좋은 답변은 가장 자신 있게 말하는 답변이 아닙니다. 검토자가 어느 문장을 믿어도 되는지, 어느 문장을 다시 확인해야 하는지 바로 알 수 있는 답변입니다.
