5.3 위키 문서로 정리하기

자료를 모으는 것만으로는 LLM위키가 완성되지 않습니다. 회의록, 웹 문서, 개인 메모가 raw/에 쌓여 있어도 주제별 문서로 정리하지 않으면 다음 질문에 다시 쓰기 어렵습니다.

이 절에서는 흩어진 자료를 위키 문서로 바꾸는 방법을 다룹니다. 목표는 “읽기 좋은 요약”이 아닙니다. 나중에 LLM에게 다시 물을 때 근거를 찾을 수 있고, 사람이 보아도 빠르게 판단할 수 있는 지식 문서를 만드는 것입니다.

LLM위키 패턴의 핵심은 원천 자료와 정리된 위키를 구분하는 데 있습니다. Karpathy의 LLM Wiki 아이디어 문서도 원본 자료, 위키, 스키마 또는 작업 규칙을 나누어 설명합니다. 이 절에서는 그 구조를 실무 문서 정리에 맞게 적용합니다.

흩어진 자료를 주제별 문서로 묶기

업무 자료는 보통 주제별로 정리되어 들어오지 않습니다. 회의록에는 결정 사항, 이슈, 고객 요청, 일정 변경이 한꺼번에 섞입니다. 웹 문서에는 배경 설명과 세부 조건이 함께 들어 있습니다. 개인 메모에는 아직 확인하지 않은 생각도 들어갑니다.

LLM위키에서는 이 자료를 그대로 한 문서에 요약하지 않습니다. 먼저 “다음에 어떤 질문에 다시 쓰일 것인가”를 기준으로 나눕니다. 예를 들어 고객 문의 자동화 위키라면 다음과 같은 주제 문서를 만들 수 있습니다.

원천 자료 조각 위키 문서로 묶을 주제 다시 쓸 질문
회의록의 반복 문의 목록 wiki/customer-inquiry-types.md 어떤 문의부터 자동화해야 하는가
상담팀 메모의 예외 처리 내용 wiki/escalation-rules.md 자동 응답에서 상담사에게 넘겨야 할 조건은 무엇인가
제품 문서의 환불 정책 wiki/refund-policy-summary.md 환불 관련 답변을 만들 때 지켜야 할 기준은 무엇인가
개인 메모의 실험 아이디어 wiki/automation-experiment-ideas.md 이번 주에 작게 검증할 자동화 실험은 무엇인가

이 표에서 중요한 점은 “자료 종류”가 아니라 “다시 물을 질문”입니다. 같은 회의록에서 나온 내용이라도 고객 문의 유형과 예외 처리 기준은 다른 문서로 나누는 편이 좋습니다. 그래야 나중에 필요한 문서만 불러와 답변을 만들 수 있습니다.

실습: 회의록을 세 개의 주제 문서로 나누기

목표
하나의 회의록에서 위키 문서 후보를 나눕니다.

실행 전제
Markdown 파일을 만들 수 있는 편집기만 있으면 됩니다. 터미널을 쓰는 경우 macOS, Linux, Git Bash 환경에서 실행할 수 있습니다.

성공 기준
원천 자료는 raw/에 남고, 정리 문서는 wiki/ 아래에 주제별로 생성됩니다. 각 위키 문서에는 원천 자료 경로와 확인 날짜가 들어갑니다.

다음 코드는 작은 실습용 LLM위키 폴더를 만듭니다. 이미 같은 폴더가 있으면 덮어쓰지 않고 중단합니다.

BASE="$HOME/llm-wiki-ch5-3/customer-support"

if [ -e "$BASE" ]; then
  echo "이미 실습 폴더가 있습니다. BASE 값을 바꾸고 다시 실행하세요." >&2
  exit 1
fi

mkdir -p "$BASE/raw/meeting-notes" "$BASE/wiki" "$BASE/output"

cat > "$BASE/raw/meeting-notes/2026-05-16-support-automation.md" <<'EOF'
# 고객지원 자동화 회의록

날짜: 2026-05-16
참석자: 지원팀, 제품팀, 운영팀

## 논의 내용

- 최근 한 달 동안 배송 상태 문의가 가장 많았다.
- 환불 문의는 정책 예외가 많아 자동 응답만으로 처리하기 어렵다.
- 비밀번호 재설정 문의는 기존 도움말 문서로 대부분 해결 가능하다.
- VIP 고객의 환불 요청은 상담사가 직접 확인해야 한다.
- 다음 주에는 배송 상태 문의 자동 응답을 먼저 실험하기로 했다.
- 실험 성공 기준은 상담사에게 넘어오는 반복 문의가 줄었는지 확인하는 것이다.

이 실습에서 회의록은 하나지만 위키 문서는 세 개입니다. 이렇게 나누면 다음 작업이 쉬워집니다. 자동화 우선순위를 물을 때는 inquiry-types.md를 중심으로 보고, 상담사 연결 조건을 물을 때는 escalation-rules.md를 보면 됩니다.

주제 문서를 나누는 기준

자료를 나눌 때는 문서 제목부터 정하지 않는 편이 좋습니다. 먼저 질문을 정합니다. “이 자료로 나중에 무엇을 판단할 것인가?”를 묻고, 답이 다르면 문서를 나눕니다.

이 도해는 원천 자료가 위키 문서로 바뀌는 흐름을 보여 줍니다. 한 자료가 한 문서로만 바뀌는 것이 아닙니다. 자료 안의 의미 단위가 다른 질문에 쓰이면 다른 위키 문서가 됩니다.

주의할 점도 있습니다. 원천 자료를 쪼개면서 원문을 지우면 안 됩니다. raw/는 기준점입니다. 위키 문서가 잘못 정리되었는지 확인하려면 언제든 원문으로 돌아갈 수 있어야 합니다.

중복과 모순 줄이기

위키 문서가 늘어나면 같은 내용이 여러 문서에 반복됩니다. 어느 정도의 반복은 괜찮습니다. 문제는 반복된 문장이 서로 다르게 바뀔 때 생깁니다.

예를 들어 한 문서에는 “환불 문의는 자동 응답 대상”이라고 쓰고, 다른 문서에는 “환불 문의는 상담사 확인 대상”이라고 쓰면 LLM은 어느 쪽을 따라야 할지 알기 어렵습니다. 더 위험한 경우는 두 문장이 모두 그럴듯해서 사람이 놓치는 것입니다.

중복과 모순을 줄이는 기본 원칙은 세 가지입니다.

점검 대상 나쁜 상태 좋은 상태
같은 사실의 반복 문서마다 같은 기준을 따로 설명한다 기준 문서를 하나 두고 다른 문서에서 링크한다
서로 다른 결론 자동화 가능 여부가 문서마다 다르다 근거 날짜와 조건을 비교해 최신 판단을 표시한다
확인 안 된 주장 “대부분 해결된다”처럼 근거 없이 단정한다 “회의록 기준”, “확인 필요”로 표시한다

이 표는 문장을 줄이라는 뜻이 아닙니다. 판단 기준을 한곳에 모으라는 뜻입니다. 반복 설명이 필요하면 짧게 요약하고, 원래 기준 문서로 연결합니다.

실습: 모순 후보를 표시하고 정리하기

목표
위키 문서 안의 중복과 모순을 찾아 정리합니다.

실행 전제
앞의 실습에서 만든 customer-support 폴더가 있으면 그대로 씁니다.

성공 기준
모순 후보가 확인 필요로 표시되고, 기준 문서가 하나 정해집니다.

다음 예시는 일부러 모순되는 문서를 하나 추가합니다.

BASE="$HOME/llm-wiki-ch5-3/customer-support"

test -d "$BASE/wiki" || {
  echo "먼저 앞의 실습을 실행하세요." >&2
  exit 1
}

cat > "$BASE/wiki/refund-automation.md" <<'EOF'
# 환불 문의 자동화

## 한 문장 요약

환불 문의는 자동 응답 대상으로 검토할 수 있다.

## 근거

- 원천 자료: `raw/meeting-notes/2026-05-16-support-automation.md`
- 확인 날짜: 2026-05-16
- 자료 성격: 내부 회의록

## 확인된 내용

- 환불 문의는 자동 응답 대상으로 검토할 수 있다.

## 확인 필요

- 환불 문의가 실제로 자동 응답 대상인지 확인 필요
- `wiki/escalation-rules.md`의 상담사 연결 기준과 충돌 가능성이 있다

## 다시 물어볼 질문

- 환불 문의 중 자동 응답 가능한 범위와 상담사 확인이 필요한 범위는 어떻게 나눌 수 있는가?
EOF

grep -R "환불 문의" "$BASE/wiki" | sort

예상 결과는 다음과 비슷합니다.

.../wiki/escalation-rules.md:- 환불 문의는 정책 예외가 많다.
.../wiki/refund-automation.md:환불 문의는 자동 응답 대상으로 검토할 수 있다.
.../wiki/refund-automation.md:- 환불 문의가 실제로 자동 응답 대상인지 확인 필요

이 결과만 보면 두 문서가 완전히 충돌한다고 단정할 수는 없습니다. 환불 문의 중 일부는 자동 응답할 수 있고, 일부는 상담사 확인이 필요할 수 있습니다. 그래서 바로 고치기보다 모순 후보로 표시합니다.

다음처럼 기준 문서를 정리하면 더 안전합니다.

# 환불 문의 처리 기준

## 한 문장 요약

현재 회의록 기준으로 환불 문의는 자동 응답보다 상담사 확인 기준을 먼저 정해야 한다.

## 근거

- 원천 자료: `raw/meeting-notes/2026-05-16-support-automation.md`
- 확인 날짜: 2026-05-16
- 자료 성격: 내부 회의록

## 확인된 내용

- 환불 문의는 정책 예외가 많다.
- VIP 고객의 환불 요청은 상담사가 직접 확인해야 한다.

## 확인 필요

- 자동 응답 가능한 단순 환불 문의가 따로 있는지 확인 필요
- 환불 정책 최신 문서 확인 필요

## 관련 문서

- `wiki/escalation-rules.md`
- `wiki/refund-automation.md`

## 다시 물어볼 질문

- 환불 문의를 자동 응답 가능, 상담사 확인 필요, 정책 확인 필요로 나누려면 어떤 기준이 필요한가?

이 정리 방식의 핵심은 “하나의 정답으로 억지 통합하지 않는 것”입니다. 근거가 부족하면 확인 필요로 남깁니다. LLM위키에서 좋은 문서는 모든 것을 아는 문서가 아니라, 무엇을 알고 무엇을 모르는지 구분하는 문서입니다.

모순을 줄이는 편집 흐름

중복과 모순을 줄일 때는 다음 순서로 편집합니다.

이 흐름에서 가장 중요한 단계는 조건과 날짜를 확인하는 것입니다. 서로 다른 시점의 자료가 다른 결론을 말할 수 있습니다. 그럴 때 예전 문서를 지워 버리면 판단 변화의 이유를 잃습니다. 대신 기준 문서에는 현재 판단을 쓰고, 관련 문서에는 이전 판단이나 확인 필요 항목을 남깁니다.

LLM에게 이 작업을 맡길 때도 “중복을 모두 제거해 줘”라고만 요청하면 위험합니다. 더 안전한 요청은 다음과 같습니다.

wiki/ 폴더의 문서를 검토해 주세요.

목표:
- 같은 사실이 반복된 곳을 찾습니다.
- 서로 충돌할 수 있는 문장을 찾습니다.
- 근거가 부족한 단정은 "확인 필요"로 표시합니다.

주의:
- raw/ 원천 자료는 수정하지 마세요.
- 충돌 여부가 애매하면 삭제하지 말고 모순 후보로 남기세요.
- 기준 문서가 필요하면 새 문서 이름을 제안하세요.

이 요청은 LLM에게 삭제보다 표시를 먼저 하게 만듭니다. AGENTS.md나 CLAUDE.md 같은 작업 규칙 파일에 비슷한 원칙을 적어 두면 반복 작업에 도움이 됩니다. 다만 이런 지침 파일은 행동을 강제하지 않습니다. 결과 문서는 사람이 다시 확인해야 합니다.

링크와 인덱스로 다시 찾기 쉽게 만들기

잘 정리된 문서도 찾지 못하면 다시 쓰기 어렵습니다. LLM위키에서는 링크와 인덱스가 탐색 장치 역할을 합니다. 링크는 문서 사이의 관계를 보여 줍니다. 인덱스는 위키 전체에서 어디를 먼저 봐야 하는지 알려 줍니다.

작은 위키라면 index.md 하나만으로도 충분합니다. 주제가 커지면 주제별 인덱스를 추가할 수 있습니다. 예를 들어 고객지원 자동화 위키라면 다음과 같이 나눌 수 있습니다.

인덱스 문서 역할 포함할 링크
index.md 위키 전체 입구 핵심 주제, 최근 변경, 자주 묻는 질문
wiki/support-index.md 고객지원 관련 문서 입구 문의 유형, 상담사 연결 기준, 환불 처리 기준
wiki/experiment-index.md 실험과 산출물 입구 자동화 실험 계획, 측정 기준, 결과 보고서
log.md 처리 이력 언제 어떤 자료를 넣고 어떤 문서를 바꿨는지

인덱스는 목차와 다릅니다. 목차는 문서 목록에 가깝지만, 인덱스는 사용자의 다음 행동을 돕습니다. “자동화 우선순위를 정하려면 여기부터 보세요”처럼 길을 안내해야 합니다.

실습: 인덱스와 링크 만들기

목표
위키 문서 사이를 링크로 연결하고, 다시 찾기 쉬운 인덱스를 만듭니다.

실행 전제
앞의 실습에서 만든 customer-support 폴더가 필요합니다.

성공 기준
index.md에서 핵심 문서로 이동할 수 있고, 각 문서에는 관련 문서 링크가 있습니다.

BASE="$HOME/llm-wiki-ch5-3/customer-support"

test -d "$BASE/wiki" || {
  echo "먼저 앞의 실습을 실행하세요." >&2
  exit 1
}

cat > "$BASE/index.md" <<'EOF'
# 고객지원 자동화 위키

## 이 위키로 답할 질문

- 어떤 고객 문의부터 자동화해야 하는가?
- 자동 응답에서 상담사에게 넘겨야 할 조건은 무엇인가?
- 첫 자동화 실험은 어떻게 설계해야 하는가?

## 먼저 볼 문서

| 질문 | 문서 |
|---|---|
| 문의 유형을 보고 싶다 | `wiki/inquiry-types.md` |
| 상담사 연결 기준을 보고 싶다 | `wiki/escalation-rules.md` |
| 환불 처리 기준을 보고 싶다 | `wiki/refund-automation.md` |
| 다음 실험 계획을 보고 싶다 | `wiki/automation-experiment.md` |

## 확인 필요

- 문의 유형별 실제 건수
- 환불 정책 최신 문서
- VIP 고객 정의
EOF

cat > "$BASE/log.md" <<'EOF'
# 처리 이력

| 날짜 | 작업 | 원천 자료 | 변경 문서 |
|---|---|---|---|
| 2026-05-16 | 회의록을 주제별 문서로 정리 | `raw/meeting-notes/2026-05-16-support-automation.md` | `wiki/inquiry-types.md`, `wiki/escalation-rules.md`, `wiki/automation-experiment.md` |
| 2026-05-16 | 환불 문의 모순 후보 표시 | `raw/meeting-notes/2026-05-16-support-automation.md` | `wiki/refund-automation.md` |
EOF

cat >> "$BASE/wiki/automation-experiment.md" <<'EOF'

## 관련 문서

- `wiki/inquiry-types.md`
- `wiki/escalation-rules.md`
EOF

cat >> "$BASE/wiki/escalation-rules.md" <<'EOF'

## 관련 문서

- `wiki/inquiry-types.md`
- `wiki/refund-automation.md`
EOF

find "$BASE" -maxdepth 2 -type f | sort

예상 결과는 다음과 비슷합니다.

/Users/사용자명/llm-wiki-ch5-3/customer-support/index.md
/Users/사용자명/llm-wiki-ch5-3/customer-support/log.md
/Users/사용자명/llm-wiki-ch5-3/customer-support/wiki/automation-experiment.md
/Users/사용자명/llm-wiki-ch5-3/customer-support/wiki/escalation-rules.md
/Users/사용자명/llm-wiki-ch5-3/customer-support/wiki/inquiry-types.md
/Users/사용자명/llm-wiki-ch5-3/customer-support/wiki/refund-automation.md

이제 위키의 입구가 생겼습니다. index.md를 보면 어떤 질문을 어디서 시작해야 하는지 알 수 있습니다. log.md를 보면 언제 어떤 자료를 넣고 어떤 문서를 바꿨는지 추적할 수 있습니다.

좋은 링크는 문서 관계를 설명한다

링크는 많을수록 좋은 것이 아닙니다. 모든 문서가 서로를 가리키면 탐색이 쉬워지는 대신 구조가 흐려집니다. 좋은 링크는 관계가 분명합니다.

링크 방식 예 판단
의미 있는 링크 자동화 실험 계획에서 문의 유형으로 연결 실험의 근거를 찾는 데 도움이 된다
확인용 링크 환불 자동화에서 상담사 연결 기준으로 연결 충돌 후보를 검토하는 데 도움이 된다
장식성 링크 모든 문서 끝에 전체 문서 목록을 붙임 문서가 커지고 탐색 의도가 흐려진다
죽은 링크 아직 만들지 않은 문서로 연결하고 표시 없음 나중에 혼란을 만든다

문서가 늘어날수록 링크는 검증 도구가 됩니다. 연결되지 않은 문서는 중요한데 잊힌 문서일 수도 있고, 더 이상 필요 없는 문서일 수도 있습니다. 어느 쪽인지 판단하려면 인덱스와 처리 이력이 필요합니다.

다음은 위키 문서의 관계를 단순하게 그린 예입니다.

이 도해에서 index.md는 탐색의 입구입니다. log.md는 작업 이력입니다. 주제 문서들은 서로 필요한 만큼만 연결됩니다. 이 정도 구조만 있어도 나중에 LLM에게 “배송 상태 문의 자동화 실험 계획을 만들어 줘. 근거 문서를 함께 표시해 줘”라고 요청하기 쉬워집니다.

5.3의 검증 포인트

위키 문서 정리는 요약 작업이 아니라 재사용 구조를 만드는 작업입니다. 이 절의 결과물을 점검할 때는 다음 질문을 사용합니다.

점검 질문 통과 기준
원천 자료가 raw/에 남아 있는가 위키 문서를 고쳐도 원문을 다시 확인할 수 있다
주제 문서가 질문 기준으로 나뉘었는가 문서 제목만 보고 어떤 질문에 쓰일지 알 수 있다
중복 문장이 기준 문서로 모였는가 같은 판단 기준이 여러 문서에서 다르게 쓰이지 않는다
모순 후보가 삭제되지 않고 표시되었는가 애매한 내용이 확인 필요로 남아 있다
index.md에서 핵심 문서를 찾을 수 있는가 처음 보는 사람도 어디서 시작할지 알 수 있다
log.md에 처리 이력이 남아 있는가 언제 어떤 자료를 넣고 무엇을 바꿨는지 추적할 수 있다
관련 문서 링크가 의미를 가지는가 링크를 눌렀을 때 근거, 예외, 다음 행동 중 하나를 확인할 수 있다

이 절의 실습을 끝내면 자료를 단순히 쌓아 두는 상태에서 벗어납니다. 다음 회의록을 넣을 때도 “어느 문서를 갱신해야 하는가”, “어떤 모순이 생겼는가”, “다음에 어디서 찾아야 하는가”를 판단할 수 있습니다.
