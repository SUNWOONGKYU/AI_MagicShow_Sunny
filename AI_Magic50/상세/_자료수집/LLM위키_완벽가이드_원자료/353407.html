8.2 정리와 감사 흐름 만들기

LLM위키는 한 번 만들고 끝나는 문서함이 아닙니다. 새 자료를 넣고, 정리하고, 다시 질문하는 동안 조금씩 변합니다. 이 변화가 관리되지 않으면 위키는 금세 “그럴듯하지만 믿기 어려운 요약 묶음”이 됩니다.

이번 절에서는 LLM위키를 오래 믿고 쓰기 위한 정리와 감사 흐름을 만듭니다. 여기서 감사는 거창한 보안 감사가 아닙니다. 문서 형식이 일정한지, 중요한 주장에 근거가 있는지, 같은 내용이 여러 곳에 흩어져 있지 않은지 주기적으로 확인하는 일입니다.

LLM위키의 기본 흐름은 ingest → query → lint로 볼 수 있습니다. 원천 자료를 넣고, 위키에 질문하고, 다시 위키 상태를 점검합니다. 이 절에서는 그중 lint에 해당하는 운영 습관을 다룹니다.

이 도해는 LLM위키 운영이 한 방향으로 끝나지 않는다는 점을 보여 줍니다. 위키는 “작성한 문서”가 아니라 “계속 정리되는 업무 지식”입니다. 그래서 감사 흐름을 작게라도 만들어 두어야 합니다.

형식 점검하기

형식 점검은 문서의 겉모양을 예쁘게 맞추는 일이 아닙니다. LLM과 사람이 같은 방식으로 문서를 읽게 만드는 일입니다. 문서마다 제목, 요약, 근거, 확인 필요 항목이 제각각이면 나중에 검색과 검토가 어려워집니다.

좋은 형식 점검의 기준은 단순해야 합니다. 라이트 사용자는 처음부터 복잡한 린터나 자동화 도구를 만들 필요가 없습니다. 먼저 모든 위키 문서가 같은 질문에 답하는지 확인하면 됩니다.

  • 이 문서가 무엇을 설명하는가?
  • 어떤 원천 자료를 근거로 삼았는가?
  • 언제 확인했는가?
  • 아직 확인하지 못한 내용은 무엇인가?
  • 다음 질문이나 업무에 어떻게 다시 쓸 수 있는가?

다음 표는 위키 문서의 최소 형식입니다.

항목 역할 없을 때 생기는 문제
한 문장 요약 문서의 핵심을 빠르게 확인합니다 문서를 열어도 쓸모를 바로 알기 어렵습니다
근거 원천 자료와 확인 날짜를 남깁니다 위키 문장을 원본처럼 믿게 됩니다
확인된 내용 근거가 있는 사실을 정리합니다 추정과 사실이 섞입니다
확인 필요 아직 단정할 수 없는 내용을 분리합니다 불확실한 주장이 보고서로 넘어갑니다
다시 물어볼 질문 다음 활용 방향을 남깁니다 문서가 읽고 끝나는 메모가 됩니다

이 표는 “모든 문서를 길게 쓰라”는 뜻이 아닙니다. 오히려 반대입니다. 짧은 문서라도 이 다섯 항목만 있으면 나중에 LLM에게 다시 맡기기 쉽습니다.

실습: 위키 문서 형식 점검표 만들기

목표
내 LLM위키에 들어 있는 Markdown 문서가 최소 형식을 갖췄는지 확인합니다.

실행 전제
Markdown 문서를 보관한 wiki/ 폴더가 있다고 가정합니다. 아직 실제 위키가 없다면 아래 예제 폴더를 만들어 실습할 수 있습니다. macOS, Linux, Windows의 WSL에서 실행할 수 있습니다. Python 3이 필요합니다.

성공 기준
형식이 부족한 문서와 빠진 항목을 목록으로 확인합니다.

BASE="$HOME/llm-wiki-audit-demo"

if [ -e "$BASE" ]; then
  echo "이미 실습 폴더가 있습니다. BASE 값을 바꾸고 다시 실행하세요." >&2
  exit 1
fi

mkdir -p "$BASE/wiki"

cat > "$BASE/wiki/good-note.md" <<'MD'
# 고객 문의 자동 분류

## 한 문장 요약

고객 문의를 유형별로 나누면 반복 답변 시간을 줄일 수 있다.

## 근거

- 원천 자료: raw/meeting-2026-05-16.md
- 확인 날짜: 2026-05-16
- 자료 성격: 회의록

## 확인된 내용

- 문의 유형은 결제, 환불, 사용법, 장애 신고로 나눌 수 있다.

## 확인 필요

- 자동 분류 정확도 기준은 아직 정하지 않았다.

## 다시 물어볼 질문

- 문의 유형별 답변 템플릿은 어떻게 나누면 좋을까?
MD

cat > "$BASE/wiki/weak-note.md" <<'MD'
# 주간 보고 자동화

주간 보고는 자동화할 수 있다.

## 확인된 내용

- 매주 금요일에 보고서를 만든다.
MD

python3 - "$BASE/wiki" <<'PY'
from pathlib import Path
import sys

wiki_dir = Path(sys.argv[1])
required = [
    "## 한 문장 요약",
    "## 근거",
    "## 확인된 내용",
    "## 확인 필요",
    "## 다시 물어볼 질문",
]

for path in sorted(wiki_dir.glob("*.md")):
    text = path.read_text(encoding="utf-8")
    missing = [item for item in required if item not in text]
    if missing:
        print(f"{path.name}: missing {', '.join(missing)}")
    else:
        print(f"{path.name}: ok")
PY

예상 결과는 다음과 비슷합니다.

good-note.md: ok
weak-note.md: missing ## 한 문장 요약, ## 근거, ## 확인 필요, ## 다시 물어볼 질문

이 실습은 문서의 내용이 맞는지 판단하지 않습니다. 먼저 “검토 가능한 모양”인지 확인합니다. 형식이 맞아야 다음 단계인 근거 점검도 쉬워집니다.

형식 점검은 주간 루틴에 넣기 좋습니다. 새 문서를 많이 만든 날에는 바로 확인하고, 평소에는 일주일에 한 번만 확인해도 충분합니다. 중요한 점은 완벽한 자동화가 아니라 누락을 빨리 발견하는 습관입니다.

형식 점검 프롬프트 예시

LLM 도구를 함께 쓴다면 다음처럼 요청할 수 있습니다. 이 요청은 Codex나 Claude Code 같은 도구에서 프로젝트 폴더를 열어 둔 상태를 가정합니다.

wiki/ 폴더의 Markdown 문서를 검토해 주세요.

다음 항목이 없는 문서를 표로 정리해 주세요.
- 한 문장 요약
- 근거
- 확인된 내용
- 확인 필요
- 다시 물어볼 질문

문서를 직접 고치기 전에, 먼저 빠진 항목과 고쳐야 하는 이유만 보고해 주세요.

이 프롬프트에서 중요한 부분은 “먼저 보고해 달라”는 요청입니다. LLM에게 바로 고치게 하면 잘못된 내용을 그럴듯하게 채울 수 있습니다. 형식 점검 단계에서는 빈칸을 발견하는 것이 목적입니다. 실제 보강은 원천 자료를 다시 확인한 뒤 진행합니다.

근거 점검하기

근거 점검은 LLM위키 운영에서 가장 중요한 단계입니다. LLM이 만든 위키 문서는 원본이 아닙니다. 위키 문서는 원천 자료를 읽기 좋게 정리한 파생 지식입니다. 따라서 중요한 주장은 반드시 원천 자료로 돌아갈 수 있어야 합니다.

근거가 부족한 문장은 세 가지로 나눠 처리합니다.

문장 상태 처리 방법 예시
원천 자료로 확인됨 근거 경로와 확인 날짜를 둡니다 raw/meeting-2026-05-16.md 기준
그럴듯하지만 원천 자료 없음 확인 필요로 내립니다 “고객 만족도가 높아질 것이다”
원천 자료와 충돌함 충돌 사실을 기록하고 결론을 보류합니다 회의록 A와 B의 일정이 다름

근거 점검에서 피해야 할 표현은 “위키에 있으므로 맞다”입니다. 올바른 표현은 “위키 문서가 가리키는 원천 자료에서 확인했다”입니다.

다음 도해는 근거 점검의 판단 흐름을 보여 줍니다.

이 흐름에서 핵심은 결론을 빨리 내리는 것이 아닙니다. 근거가 약하면 문장을 약하게 쓰고, 근거가 없으면 확인 필요로 내리는 것입니다. LLM위키의 신뢰도는 강한 문장을 많이 쓰는 데서 생기지 않습니다. 확인된 것과 확인할 것을 구분할 때 생깁니다.

실습: 근거 없는 주장 찾기

목표
위키 문서에서 근거가 없는 강한 주장을 찾아 확인 필요로 분리합니다.

실행 전제
앞 실습에서 만든 ~/llm-wiki-audit-demo 폴더를 사용합니다. 앞 실습을 하지 않았다면 먼저 형식 점검 실습을 실행하세요.

성공 기준
근거 없는 주장을 보고서나 업무 계획에 바로 쓰지 않도록 표시합니다.

다음 문서를 하나 추가합니다.

BASE="$HOME/llm-wiki-audit-demo"

test -d "$BASE/wiki" || {
  echo "먼저 형식 점검 실습을 실행하세요." >&2
  exit 1
}

cat > "$BASE/wiki/claim-check.md" <<'MD'
# 자동화 우선순위

## 한 문장 요약

고객 문의 자동 분류는 가장 먼저 자동화해야 한다.

## 근거

- 원천 자료: raw/meeting-2026-05-16.md
- 확인 날짜: 2026-05-16
- 자료 성격: 회의록

## 확인된 내용

- 고객 문의는 매주 반복해서 발생한다.
- 담당자는 문의 유형을 결제, 환불, 사용법, 장애 신고로 나누고 싶어 한다.
- 고객 문의 자동 분류는 가장 먼저 자동화해야 한다.

## 확인 필요

- 각 문의 유형의 실제 건수
- 자동화했을 때 줄어드는 시간

## 다시 물어볼 질문

- 우선순위를 정하려면 어떤 지표가 더 필요할까?
MD

python3 - "$BASE/wiki/claim-check.md" <<'PY'
from pathlib import Path
import sys

path = Path(sys.argv[1])
text = path.read_text(encoding="utf-8")

strong_markers = ["가장", "반드시", "항상", "최고", "완전히"]
for line_no, line in enumerate(text.splitlines(), start=1):
    if any(marker in line for marker in strong_markers):
        print(f"line {line_no}: {line}")
PY

예상 결과는 다음과 비슷합니다.

line 5: 고객 문의 자동 분류는 가장 먼저 자동화해야 한다.
line 15: - 고객 문의 자동 분류는 가장 먼저 자동화해야 한다.

이 스크립트는 단순한 예제입니다. “가장”이라는 단어가 있다고 모두 틀린 문장은 아닙니다. 하지만 라이트 사용자가 위키를 점검할 때는 이런 강한 표현부터 보는 것이 효과적입니다.

위 예제에서 “고객 문의 자동 분류는 가장 먼저 자동화해야 한다”는 문장은 근거가 부족합니다. 회의록에 반복 발생과 분류 욕구가 있다고 해서 자동화 우선순위 1위라고 단정할 수는 없습니다. 다음처럼 고치는 편이 안전합니다.

## 확인된 내용

- 고객 문의는 매주 반복해서 발생한다.
- 담당자는 문의 유형을 결제, 환불, 사용법, 장애 신고로 나누고 싶어 한다.

## 확인 필요

- 고객 문의 자동 분류가 다른 자동화 후보보다 우선순위가 높은지 확인해야 한다.
- 각 문의 유형의 실제 건수와 처리 시간을 확인해야 한다.

이렇게 바꾸면 문서의 가치가 줄어드는 것이 아닙니다. 오히려 다음 행동이 분명해집니다. 이제 독자는 “자동화하자”가 아니라 “우선순위를 판단할 자료를 더 모으자”라고 말할 수 있습니다.

근거 점검 체크리스트

중요 문서를 검토할 때는 다음 순서로 확인합니다.

점검 질문 통과 기준 보완 방법
근거 경로가 있는가 raw/... 또는 출처 URL이 남아 있습니다 원천 자료 위치를 추가합니다
확인 날짜가 있는가 YYYY-MM-DD 형식으로 남아 있습니다 마지막 확인일을 씁니다
원문을 다시 열 수 있는가 파일이나 URL이 접근 가능합니다 깨진 링크를 고치거나 보존본을 찾습니다
주장이 원문보다 강하지 않은가 원문 범위 안에서만 말합니다 “가능성이 있다”, “확인 필요”로 낮춥니다
최신성이 필요한가 버전, 가격, 정책, 명령어를 구분합니다 공식 문서와 릴리스 노트를 다시 봅니다

특히 명령어, 설치 방법, 제품 기능, 버전 정보는 오래되기 쉽습니다. nvk/llm-wiki, Codex, Claude Code 같은 도구는 변경 속도가 빠를 수 있습니다. 원고 작성 기준으로 확인된 내용이라도, 독자가 실행하기 전에는 공식 README와 릴리스 노트를 다시 확인해야 합니다.

구조와 중복 점검하기

형식과 근거를 점검했다면 다음은 구조입니다. 구조 점검은 문서가 많아질수록 중요해집니다. 같은 개념이 여러 파일에 흩어져 있거나, 어떤 문서는 아무 곳에서도 연결되지 않거나, 오래된 문서가 최신 문서처럼 남아 있을 수 있습니다.

작은 위키에서는 index.md만 잘 관리해도 충분합니다. 하지만 문서가 늘어나면 다음 문제가 생깁니다.

  • 같은 개념이 다른 이름으로 반복됩니다.
  • 예전 결정과 최신 결정이 함께 남습니다.
  • 새 문서가 index.md에 연결되지 않습니다.
  • 원천 자료는 있는데 정리 문서가 없습니다.
  • 정리 문서는 있는데 원천 자료가 없습니다.

구조 점검의 목적은 모든 문서를 하나로 합치는 것이 아닙니다. 독자가 다시 찾을 수 있게 만드는 것입니다. LLM도 마찬가지입니다. 문서 관계가 분명할수록 필요한 맥락을 더 안정적으로 사용할 수 있습니다.

다음 표는 구조 문제와 처리 방법을 정리한 것입니다.

문제 발견 신호 처리 방법
중복 문서 제목이나 요약이 비슷합니다 대표 문서 하나로 합치고 나머지는 링크로 남깁니다
연결되지 않은 문서 index.md나 다른 문서에서 링크되지 않습니다 색인에 추가하거나 아카이브 후보로 표시합니다
오래된 문서 확인 날짜가 오래됐고 최신 문서와 다릅니다 최신성 확인 필요 또는 아카이브 후보로 표시합니다
근거 없는 정리 문서 raw/... 경로가 없습니다 근거를 찾거나 확인 필요로 낮춥니다
원천 자료 미처리 raw/에는 있는데 wiki/에 반영되지 않았습니다 ingest 후보로 기록합니다

구조 점검은 LLM위키가 커질 때 생기는 피로를 줄입니다. 문서를 찾는 시간이 줄고, 같은 질문을 다시 정리하는 일도 줄어듭니다.

실습: 연결되지 않은 문서와 중복 후보 찾기

목표
index.md에 연결되지 않은 문서와 제목이 비슷한 중복 후보를 찾습니다.

실행 전제
Python 3이 필요합니다. 아래 예제는 ~/llm-wiki-structure-demo 폴더를 새로 만듭니다.

성공 기준
연결되지 않은 문서와 중복 가능성이 있는 문서 목록을 확인합니다.

BASE="$HOME/llm-wiki-structure-demo"

if [ -e "$BASE" ]; then
  echo "이미 실습 폴더가 있습니다. BASE 값을 바꾸고 다시 실행하세요." >&2
  exit 1
fi

mkdir -p "$BASE/wiki"

cat > "$BASE/wiki/index.md" <<'MD'
# 업무 자동화 위키

## 주요 문서

- [고객 문의 자동 분류](customer-inquiry-classification.md)
- [주간 보고 자동화](weekly-report-automation.md)
MD

cat > "$BASE/wiki/customer-inquiry-classification.md" <<'MD'
# 고객 문의 자동 분류

## 한 문장 요약

고객 문의를 유형별로 나누는 기준을 정리한다.
MD

cat > "$BASE/wiki/customer-support-labeling.md" <<'MD'
# 고객 지원 문의 라벨링

## 한 문장 요약

고객 문의를 라벨로 나누는 기준을 정리한다.
MD

cat > "$BASE/wiki/weekly-report-automation.md" <<'MD'
# 주간 보고 자동화

## 한 문장 요약

반복되는 주간 보고서 작성을 자동화한다.
MD

python3 - "$BASE/wiki" <<'PY'
from pathlib import Path
import re
import sys

wiki = Path(sys.argv[1])
index = wiki / "index.md"
index_text = index.read_text(encoding="utf-8") if index.exists() else ""

docs = [p for p in sorted(wiki.glob("*.md")) if p.name != "index.md"]

print("[연결되지 않은 문서]")
for path in docs:
    if path.name not in index_text:
        print(f"- {path.name}")

print()
print("[중복 후보]")
titles = []
for path in docs:
    text = path.read_text(encoding="utf-8")
    match = re.search(r"^#\s+(.+)$", text, re.MULTILINE)
    title = match.group(1) if match else path.stem
    tokens = set(re.findall(r"[가-힣A-Za-z0-9]+", title))
    titles.append((path.name, title, tokens))

for i, left in enumerate(titles):
    for right in titles[i + 1:]:
        common = left[2] & right[2]
        if len(common) >= 2:
            print(f"- {left[0]} <-> {right[0]}: 공통어 {', '.join(sorted(common))}")
PY

예상 결과는 다음과 비슷합니다.

[연결되지 않은 문서]
- customer-support-labeling.md

[중복 후보]

이 예제에서 customer-support-labeling.md는 색인에 연결되지 않았습니다. 또 제목만 보면 중복 후보가 나오지 않을 수 있습니다. 하지만 사람은 두 문서가 모두 “고객 문의를 유형이나 라벨로 나누는 기준”을 다룬다는 점을 알 수 있습니다.

자동 점검은 시작점일 뿐입니다. 마지막 판단은 사람이 해야 합니다. 이때 LLM에게 다음처럼 요청하면 좋습니다.

wiki/customer-inquiry-classification.md와 wiki/customer-support-labeling.md를 비교해 주세요.

다음 기준으로 표를 만들어 주세요.
- 겹치는 내용
- 서로 다른 내용
- 하나로 합칠 수 있는 내용
- 별도 문서로 유지해야 하는 이유
- 병합한다면 대표 문서 제목 제안

근거가 문서 안에 없으면 추측이라고 표시해 주세요.

이 요청은 LLM에게 “합쳐라”가 아니라 “비교해 달라”고 말합니다. 구조 점검에서는 자동 병합보다 비교 보고가 안전합니다. 병합은 원천 자료와 업무 맥락을 확인한 뒤 진행합니다.

구조 점검의 주간 흐름

구조 점검은 매번 깊게 할 필요가 없습니다. 다음처럼 가볍게 나누면 유지하기 쉽습니다.

주기 점검 항목 결과물
매일 또는 자료 추가 직후 새 문서가 index.md에 연결됐는지 확인 색인 링크 추가
주 1회 연결되지 않은 문서와 중복 후보 확인 정리 후보 목록
월 1회 오래된 문서와 상충 주장 확인 아카이브 후보 또는 재검증 목록
큰 산출물 작성 전 근거 없는 주장과 최신성 필요한 정보 확인 제출 전 검토 메모

이 표를 그대로 따라야 하는 것은 아닙니다. 중요한 것은 “자료를 넣는 일”과 “정리 상태를 보는 일”을 분리하는 것입니다. 자료를 넣는 날에는 빠르게 쌓고, 점검하는 날에는 천천히 정리합니다.

nvk/llm-wiki 같은 구현체에는 감사, 린트, 아카이브와 관련된 기능이 있을 수 있습니다. 다만 이런 명령은 구현체와 버전에 따라 달라집니다. 이 책의 원고 기준 자료에서는 nvk/llm-wiki가 2026-05-16 확인 기준 v0.9.0 릴리스에서 주제 아카이브 생명주기를 다룹니다. 실제 사용 전에는 설치된 버전의 README, Releases, 도움말을 다시 확인해야 합니다.

정리 후보 기록 템플릿

자동 점검이든 수동 점검이든 발견한 문제는 바로 고치지 말고 후보로 기록하는 편이 안전합니다. 특히 오래된 문서나 중복 문서는 바로 삭제하지 않습니다. LLM위키에서 원천 자료와 처리 이력은 나중에 중요한 단서가 됩니다.

# 정리 후보 기록

## 확인 날짜

2026-05-16

## 형식 보완 후보

| 문서 | 빠진 항목 | 조치 |
|---|---|---|

| 문장 | 현재 상태 | 조치 |

## 구조 보완 후보

| 문서 | 문제 | 조치 |
|---|---|---|
| wiki/customer-support-labeling.md | index.md에 연결되지 않음 | 기존 문서와 비교 후 링크 또는 병합 |

이 템플릿은 점검 결과를 업무 기록으로 남깁니다. 다음 주에 다시 열어도 무엇을 봤고 왜 보류했는지 알 수 있습니다. LLM에게 후속 작업을 맡길 때도 이 기록이 좋은 프롬프트 재료가 됩니다.

8.2의 검증 포인트

정리와 감사 흐름은 복잡한 도구보다 단순한 반복이 중요합니다. 이번 절에서 만든 흐름은 다음 기준으로 확인합니다.

점검 영역 확인할 질문
형식 모든 주요 위키 문서에 요약, 근거, 확인된 내용, 확인 필요가 있는가
근거 중요한 주장이 원천 자료나 공식 출처로 돌아갈 수 있는가
최신성 버전, 명령어, 정책, 가격처럼 바뀌기 쉬운 정보가 표시되어 있는가
구조 새 문서가 index.md나 관련 문서에 연결되어 있는가
중복 같은 개념이 여러 문서에 흩어져 있지 않은가
보류 바로 고치기 어려운 문제를 정리 후보로 남겼는가

이 기준을 통과하면 위키가 완벽해지는 것은 아닙니다. 대신 다음에 무엇을 믿고, 무엇을 다시 확인해야 하는지 분명해집니다. 오래 쓰는 LLM위키의 신뢰도는 여기서 나옵니다.
